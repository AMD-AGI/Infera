# InferaSim：在投入 GPU 前模拟服务栈

服务部署不是一项决策，而是一系列决策构成的栈。张量、专家和流水线的并行形态。prefill 和 decode 是共享 GPU，还是位于独立的资源池中。调度器每一步的 token 预算，以及它会让多少序列常驻。引擎可以占用多少 HBM，以及 KV cache 如何在其中分页。请求如何路由到各个副本，以及某个副本已经缓存了多少 prompt 内容。而在所有这些因素之下，还有流量本身的形态。

这些因素彼此影响。提高 token 预算会改善 prefill 吞吐量，却会损害 token 间延迟。按缓存局部性进行路由会提高前缀复用率，同时把 decode 压力集中到持有热门前缀的副本上。降低张量并行度会改善单 GPU 吞吐量，直到模型再也放不下为止。局部改进通常只是转移瓶颈，而不是消除瓶颈；只有测量整个系统，你才能发现瓶颈转移到了哪里。

问题就在于如何测量整个系统。在大模型上，一次真实实验就会占用整个节点数分钟，而真正值得研究的问题数以千计。InferaSim 的存在，就是为了让搜索在模拟中完成，只把硬件投入到入围的少量方案上。

## 它是什么

本文档说明其工作原理。有关安装和面向任务的用法，请参阅 [README.zh-CN.md](README.zh-CN.md)。

InferaSim 是一个由工作负载驱动的服务栈模拟器和投影器。它有意在同一个实测基础之上构建两个相互耦合的模型：

- 一个**解析投影器**，以闭式形式求解服务配置，回答稳态问题——首 token 延迟、token 间延迟、吞吐量、KV 和权重内存，以及配置是否能够容纳；
- 一个**离散事件模拟器**（DES），它在虚拟时钟上运行同一个成本模型，回答闭式形式在结构上无法回答的问题——延迟*分布*、给定负载下的排队，以及共享缓存和路由器的一组副本所表现出的行为。

它既不是纯粹的解析估算，也不是逐比特精确的硬件模拟器。它所追求的是前向传递粒度的保真度：从测量或校准后的成本模型中取得每次前向传递的持续时间，用真实的调度策略决定每次前向传递中*包含什么*，然后让其上层的一切行为自然涌现。

其核心理念是**稀疏测量，解析迁移**。将少量、低成本的小规模基准测试采集为锚点；其他所有配置都从最近的适用锚点投影得出，而无需逐一测量。

## 架构：一条时间线，多个组合部件

这里不存在单体模型。系统由四个关注点组合而成：

| 层 | 它所回答的问题 |
|---|---|
| 成本内核 | *这一次*前向传递需要多长时间？ |
| 调度器 | 每次前向传递中*包含什么*？ |
| 集群 | 哪个副本为请求提供服务，它已经缓存了什么？ |
| 工作负载 | 请求何时到达，其中包含什么？ |

成本内核是其上所有组件的时间轴。解析投影器直接使用它；DES 则在每个模拟步骤中使用一次。由于二者建立在同一个内核之上，为其中一方加载的实测锚点会自动被另一方采用。

### 虚拟时钟

DES 为模拟提供虚拟时钟和事件队列。任何过程都不会按真实时间等待。一个步骤会以模型给出的持续时间进行调度，时钟跳转到下一个时间戳，状态随之推进，受影响的组件再调度后续工作。一次路由决策会改变某个副本的队列；一次准入决策会改变 decode 可以开始的时间；一次驱逐会改变下一个请求必须重新计算的内容。

### 请求的旅程

1. **到达。** 使用重放 trace 中的时间戳，或从配置的到达过程中采样。
2. **路由。** 策略选择副本——轮询、随机、前缀感知哈希或 KV 重叠度评分。
3. **缓存查找。** prompt 是一个由内容寻址块哈希组成的有序序列。命中是指该副本上已经常驻的、从序列开头起*连续且最长的一段*块；匹配的 token 会被初始化为已经计算完成。
4. **准入。** 调度器从等待集合中准入请求，同时受常驻序列上限约束，并针对有限的 token 池按完整 ISL 预留 KV。无法容纳的请求会继续等待。
5. **打包。** 每次前向传递首先推进所有正在运行的请求，然后准入新工作，所有工作共享同一个每步 token 预算。分块 prefill 不需要特殊处理——它从预算中自然*涌现*，因此一个步骤会自然地混合 prefill 分块与 decode。
6. **持续时间。** 步骤成本来自成本内核，后者会区分均匀的 decode 步骤与混合的 prefill+decode 步骤。
7. **完成。** 每个请求的延迟进入收集器；如果有要求，每个步骤的批次组成也会一并记录。

### 驱动模拟：工作负载

系统提供两种请求内容来源，以及多种到达过程。

**Trace 重放**使用 Mooncake 格式的 trace——包含 `timestamp`、`input_length`、`output_length` 和 `hash_ids` 的 JSONL 或 JSON。由于共享同一个 system prompt 的连续请求也会共享开头的 `hash_ids`，重放所驱动的是真正的内容寻址复用，而不是假定的命中率。trace 自带到达信息，因此不需要提供负载速率。

**合成前缀池**以参数化方式生成相同的结构：`P` 个不同的共享前缀，每个长度为 `L` 个 token，并按配置的块大小划分为块；同时使用 Zipf 参数使热门程度发生倾斜，以模拟少数热门 system prompt 主导真实流量的情形。

**到达过程**涵盖闭环（无队列，仅限稳态）、Poisson、确定性，以及通过突发性形状参数控制的 gamma 突发过程。开环过程运行 DES 以获得百分位数；所有过程仍会同时报告解析排队均值，使闭式形式与模拟彼此可见，而不是成为二选一的替代方案。各请求的长度会围绕配置的 ISL/OSL 按范围比例呈现异构性。负载扫描会在最大可持续速率的不同分数下重新运行工作负载，并生成吞吐量-延迟曲线；通过该曲线可以找到拐点，而不必假定它位于何处。

## 单引擎：关键在于调度器

单个引擎不能用一个每秒 token 数来概括。主导尾延迟的是请求如何等待、组成批次、分块并进入 prefill，因此这里对调度器本身进行建模，而不是将其归结为摘要指标。

DES 实现了以 vLLM V1 为建模参照的统一批处理策略：每次前向传递都会在共享的每步 token 预算内，先推进已在运行的工作（decode 和进行中的 prefill 分块），再依据常驻上限和 KV 预留准入新的等待请求。两个阶段共享同一预算，正因如此，分块 prefill 和混合步骤会从模型中自然产生，而不是作为附加功能拼接上去。

解析路径通过服务模型选择器以更低成本提供同样的区分：`continuous` 计入混合 prefill+decode 步骤的 token 间成本，而 `static` 将 decode 视为理想化的纯 decode 批次，并把 prefill 作为 TTFT 的一次性成本计入。前者是真实连续批处理引擎的工作方式；后者则是值得用来比较的明确上界。

若干会显著影响延迟的引擎行为，都被建模为一等项，而非忽略不计：

- 引擎可以占用的 HBM 比例，它限制可用内存，进而限制最大并发度；
- 分页 KV 的块大小，包括仅部分填充的最后一个块所产生的内部碎片；
- 流式刷新间隔，它会将客户端收到首个 token 的时间——因而也就是测得的 TTFT——推迟到已经 decode 出若干 token 之后；
- decode 调度器的准入粒度，即 prefill 完成后到请求加入运行批次之间的延迟；这是一个纯 TTFT 项，并且在 prefill 不处于关键路径上的解耦服务中占主导地位；
- 混合步骤的惩罚，用于反映其 CUDA graph 路径相较于均匀 decode 步骤效率更低；
- 前缀缓存复用，在解析路径上表示为静态命中比例，在 DES 中则表示为块缓存的涌现属性。

## 时间轴：稀疏测量，解析迁移

成本内核以三种模式之一运行：`simulate`（无 GPU，使用 GEMM 和 attention 的解析后端）、`benchmark`（在真实 GPU 上测量）或 `both`（分别运行两者并并列报告）。

纯模拟是快速路径，完全不需要加速器。校准是使其结果可信的关键，而其机制就是**锚点存储**：一个按照**执行区间签名**索引实测基准产物的目录。

配方参数分为两类。**执行区间定义型**参数会更换内核或执行路径——dtype、backend、所用的 graph 或 attention library——任何此类参数不同的两个配方都不能相互迁移；每个执行区间都需要自己的锚点。**可迁移**参数——层数、并行形态、批次、序列长度——则可以从已有测量中进行解析迁移。重建过程会选择同一执行区间内最近的锚点，并通过驱动同一个投影器将其迁移到目标配方，从而让物理规律只存在于一个位置。

单 GPU 锚点无法观测跨 GPU 通信，而这恰恰是大规模运行时最重要的成本。因此，warmup 会在 `min(tp, 4)` 个 GPU 上进行测量——既足以观察集合通信，又足够低廉，无需占用整个节点——投影器随后从这一个锚点还原每个目标。这里不进行扫描：之所以选择四，是因为在一次实测的 TP1/2/4/8 扫描中，将每个并行度分别作为其他未测并行度的锚点进行评分后，四明确胜出，而且第二个锚点也从未带来更优结果。与锚点相比，目标如果超出一次翻倍以上，就会被报告为外推，而不是还原；这样可以让这一区别保持可见，避免无声地产生过度自信。

## 多引擎：集群行为

路由器后的副本会被共同模拟，因为真正值得关注的行为只存在于副本之间。

每个副本都拥有一个**内容寻址、分页式 KV 块缓存**，其容量有限并采用 LRU 驱逐。因此，命中率是*涌现*的——它由工作负载内容、容量和路由共同决定，而不是由用户提供的数值。各路由策略的差异恰好体现在这一点上：

- **KV 感知评分**最小化已部署路由器自身的成本函数：重叠权重乘以某副本必须计算的块数，再加上它当前已经承载的负载。该权重是在复用与均衡之间调节的旋钮，因此模拟器可以回答在生产环境中重新调节它会付出什么代价。
- **前缀感知哈希**将开头的块一致地映射到一个归属副本，使具有相同前缀的请求共置，从而让 miss 随不同前缀的数量扩展，而不是随集群规模扩展。
- **轮询**和**随机**完全忽略局部性，因此每个副本都会重新预热相同的前缀。

模拟全部四种策略的意义在于，这种权衡是真实存在且并非单向的：追求局部性的策略能最大化复用，却可能把一个热门前缀过度集中到单个副本上，提高其 decode 压力并延长 makespan。集群报告会同时呈现权衡的两面——汇总的延迟分布，以及各副本命中率的离散程度——从而让这种权衡直接可见，而不是停留在争论中。

将集群设置为单个副本，可以研究单个引擎的自动前缀缓存如何在请求流中实现时间复用；限制块容量，则可以研究驱逐压力。

## 解耦

prefill 和 decode 可以建模为独立的 worker 池，各自拥有自己的并行形态；请求从 prefill worker 迁移到 decode worker 时，会计入 KV-cache 传输成本。禁用此功能时，投影器运行标准的共置两阶段模型。上文的 decode 准入项在这里最为重要，因为 prefill 计算不在关键路径上，TTFT 中仍然可见的就是等待时间。

## 输出结果

解析路径报告 TTFT、token 间延迟、总 decode 吞吐量和单 GPU decode 吞吐量、单 GPU 内存以及可行性。不可行的配置会被*保留*并标注原因，而不是被丢弃，这样搜索就能区分“无法容纳”和“从未尝试”。

给定每 GPU 小时价格后，它还会报告每百万 token 的成本，并按整个副本计费。单 GPU 吞吐量已经针对规模做了归一化，但预算以货币计价，正是在转换之后，那些靠增加 GPU 换取速度的配方才不再显得毫无成本。系统不会假定价格：如果未提供价格，该指标就会缺省，而不是使用默认值，因为虚构的费率看起来会像实测值。

DES 报告给定请求速率和实际达到的请求速率、利用率、makespan、系统吞吐量，以及配置是否达到饱和；此外还会报告完整分布，包括从准入时刻开始测量的 TTFT、从到达时刻开始测量的 TTFT（包含排队等待）、排队等待本身、token 间延迟、每输出 token 耗时和端到端延迟。区分两种 TTFT 定义至关重要：一个反映引擎行为，另一个反映客户端体验；在负载下，它们并不是同一个数值。报告还会附带批次组成和前缀复用摘要，并可选择记录每个步骤，以检查调度器究竟如何打包每次前向传递。

## 搜索：以模拟作为评分函数

一旦无需硬件就能为配置评分，搜索就变成了围绕该评分展开的循环。

内置扫描会枚举并行形态和并发度，并应用调用方提供的有效性过滤器，以表达成本模型本不应了解的规则——例如专家并行度不得超过张量并行度、固定 GPU 预算——然后投影所有通过筛选的配置。结果可以按目标进行排名并形成候选名单。

在此之上还有一个将投影器作为 oracle 的调优 agent。它先执行确定性的种子扫描以实现 warm start，然后运行由 LLM 驱动的搜索，在 warm start 得到的当前最佳方案基础上继续推进，提出配方并通过投影器为其评分；默认路径不使用 GPU。搜索空间庞大且难以枚举，因此 agent 采用导航式探索，而不是网格式遍历。

## 先模拟，再验证

目标不是取代硬件验证，而是让硬件验证有的放矢。模拟是内循环：广泛扫描、排名、筛选候选。硬件是外循环：验证候选名单，并将测得的结果采集回锚点存储，使下一次扫描获得比上一次更好的校准。这个循环之所以能够闭合，是因为锚点是产物，而非一次性运行。

内存被有意置于这个循环之外。权重和 KV 字节数根据模型形态与并行布局计算，而不是拟合得到，因此锚点对它们没有任何贡献；在并行度降低的 warmup 上测得的容量也不能代表目标配置。内存投影在每一种并行度下都是解析式的，其正确性取决于公式，而不是校准。

这正是并行布局必须包含 attention 本身如何切分的原因。张量并行会对 GQA 模型的缓存进行分片，因为它对 KV head 进行分片；但 MLA 缓存的是所有 head 都会读取的一个压缩 latent，因此张量并行反而会复制它。数据并行 attention 才是真正缩小它的维度：每个 rank 负责一部分正在处理的请求，并持有这些请求的完整缓存；在 tp/dp 个 head 上，它看到的是批次的 1/dp。对于 head 并行的工作，这两个除法会相互抵消，因此 GQA 不会从中受益；MLA 的 latent 不是 head 并行的，所以对 MLA 而言二者不会抵消。如果一个 rank 的 attention 输出是完整输出而非分片，它之后也无需执行 all-reduce；而当专家完全采用专家并行时，MoE 层的张量并行集合通信会彻底消失。这个维度并非没有代价——在更窄的形态中执行相同工作会导致更差的 GEMM——但在 MLA 模型上，它决定了缓存是每个 rank 一份还是每个副本一份，进而决定了长上下文容量规划问题究竟能否得到答案。

## 边界

一个工具不建模什么，与它建模什么同样重要。

- **一种调度策略。** DES 实现统一批处理策略。具有显著不同准入机制的引擎系列——Radix 缓存感知准入、保留前缀的 decode retraction——并未被建模为独立的调度器核心，但它们的预算和内存调节项仍会生效。
- **无容量控制。** 没有 autoscaler，没有 SLA 驱动的副本扩缩容，也没有 worker 启动延迟模型。集群规模就是用户设定的值。
- **一个缓存层级。** KV 位于设备内存中。没有 host-memory 或 SSD 层级，没有卸载或载入流量，也没有分布式缓存目标。
- **仅限进入服务规格的内容。** 投影基于并行形态、并发度、序列长度和精度构建。不进入该规格的服务器 flag 会原样透传，并得到相同的投影结果，因此该工具无法对 kernel 或 scheduler 层级的 flag 相互排名。这些 flag 应当在硬件上进行评估；把投影结果当作它们的排名，只会产生看似自信的噪声。
- **校准按执行区间进行。** 一个锚点只认证它自身的执行区间。更改 dtype 或 kernel backend 后，之前的锚点无法迁移；需要采集新的锚点。

以上是该工具真实且明确的边界。在边界内，它足够快，可以让穷举搜索成为常规操作；在边界之外，答案仍然来自 GPU。
