# Patch 0001 — `free_tcp_port_block` picked the same port block for every caller

**File:** `infera/common/net.py`
**Patch:** `0001-free_tcp_port_block-randomise-scan-start.patch`
**Test:** `test_net_port_block.py` → install to `tests/unit/common/`
**Status:** fixed, tested, **not yet committed** (sits in the working tree of
branch `yihou.dev.glm5.2.mxfp4.experiment`).

## Context — the symptom it cured

Bringing up a **1P1D pair on one host** with kv-aware enabled and `dp_size > 1`:
the prefill leg comes up, the decode leg's Rank-0 scheduler dies during init.

```
[DP1 TP1 EP1] Scheduler hit an exception: ...
zmq.error.ZMQError: Address already in use (addr='tcp://*:32765')
RuntimeError: Rank 0 scheduler died during initialization (exit code: -3)
```

Both legs' `--kv-events-config` carried the *same* endpoint port (32764). sglang
binds one publisher per DP rank at `base + attn_dp_rank`, so leg B collided with
leg A's 32765.

## What was wrong

`free_tcp_port_block()` scanned **downward from a fixed start**
(`ip_local_port_range.low − count`, i.e. 32764 here) and released its probe
sockets in `finally` before returning. Two callers therefore saw the identical
free block and both returned it. Not a rare race — **deterministic**.

Reached only from `worker.py:77`, i.e. only when `enable_kv_events` is on. It is
a kvaware-path bug.

MVP against the pre-fix code (`git show HEAD:infera/common/net.py`):

```
OLD bases: [32764, 32764, 32764, 32764, 32764, 32764, 32764, 32764, 32764, 32764]
distinct: 1 -> FAIL (bug reproduced)
```

## Why the fix is "randomise", and not the two more obvious options

Both alternatives were **tested on the node and rejected on evidence** — worth
recording so nobody re-proposes them:

1. **Hold the reservation until the child binds.** Rejected: the probe binds
   `127.0.0.1:P`, but the sglang child binds `0.0.0.0:P` (zmq `tcp://*`). Live
   MVP:
   ```
   reserved 127.0.0.1:29600
   child bind 0.0.0.0:29600 -> BLOCKED errno=98  <-- holding would break our own child
   ```
   Holding the block locks out the very process it was reserved for.

2. **Reserve on `0.0.0.0` with `SO_REUSEADDR`** so the child can take it over.
   Rejected: then the reservation isn't exclusive either. Live MVP:
   ```
   reserved 0.0.0.0:29700 (SO_REUSEADDR, no listen)
     other leg probe  -> OK   <-- BAD, collision still possible
     our child        -> OK
   ```

Exclusivity and let-the-child-take-over are mutually incompatible here, so the
reservation *must* be released before returning. What remains fixable is the
**determinism of the scan start**.

## How the fix works

Try `_PORT_BLOCK_TRIES = 64` randomly-chosen bases in `[1024, low − count]`
first, then fall back to the original exhaustive downward scan so the function
still never fails while a block is genuinely available. Signature and socket
semantics unchanged.

Post-fix, in-container:

```
>>> [free_tcp_port_block(4) for _ in range(6)]
[12457, 4265, 24310, 16567, 28874, 29547]
```

And live: the two legs registered `tcp://…:17213` and `tcp://…:31215`, both
reached "ready to roll".

## How it was applied

- In-repo: edit `infera/common/net.py` (this patch).
- On a running node without rebuilding the image: `docker cp` the fixed file to
  `/opt/infera/infera/common/net.py` inside the container. `scripts/glm52_up.sh`
  does this automatically from `scripts/net_fixed.py`.
