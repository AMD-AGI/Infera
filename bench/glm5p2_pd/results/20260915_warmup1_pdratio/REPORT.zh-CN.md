# GLM-5.2 AgentX warmup1 P:D 配比扫描（137/138/140/141）

## 这轮要回答什么

前一轮扫描（`../20260915_warmup1_sweep_137_138/REPORT.zh-CN.md`）给出的是**两段式**
瓶颈模型：

- **第一段（≤峰值）**：prefill 算力限制吞吐。prefill 的 `num_running_reqs`
  被钉在 DP 宽度（8）上、队列持续堆积，而它自己的 KV 只占 0.17；
  decode KV 只有 0.38–0.56，不具备反压能力。
- **第二段（远超峰值）**：在途请求随并发增多，把 decode KV 撑满，
  传输队列积压，吞吐坠崖。P8D8 的悬崖夹在 C96 与 C128 之间。

这个模型有一个**直接的、可证伪的推论**：既然第一段是 prefill 算力受限，
那么**加 prefill worker、其余一律不动**，第一段的吞吐就应该抬升。
本轮就是这个实验：同样的 P8+DPA / D8+DPA 单实例形态，只改实例数。

| 相 | 拓扑 | 并发 | 说明 |
|---|---|---|---|
| R1 | 2P1D | 64 | 1P1D 曲线的中段斜坡 |
| R2 | 2P1D | 128 | 1P1D 在此坠崖（per_gpu 5,358） |
| R3 | 3P1D | 64 | |
| R4 | 3P1D | 128 | |

C64 与 C128 这一对同时问两件事：加 prefill 能否抬高曲线，以及能否把峰值右移。

## 口径

与前一轮**完全一致**，否则点不可比：每点独立冷启动
（`max-running` 与 `cuda-graph-max-bs` 必须等于并发，冷前缀缓存避免点间互相继承），
`mem_fraction_static=0.85`，warmup1，`DURATION=1200`，
镜像固定在 `glm52-v518-c29bd17-b02ab81`（`sha256:6ff85f4a…`，四节点逐一核验
Image ID **和** sglang/aiter 源码 commit）。

`tok/s/GPU` 的分母随拓扑变化：1P1D = 8+8 = 16，2P1D = 16+8 = **24**，
3P1D = 24+8 = **32**。**这正是本轮必须同时看绝对吞吐的原因**——
加一个 prefill 节点会把分母抬高 50%，只看 `tok/s/GPU` 会把"有效果但不够"
和"完全没效果"混为一谈。`analyze.py` 两个都打。

**一句话结论：加一个 prefill 节点把 C128 从坠崖（85,729）救到 348,884 tok/s，
不仅是同并发下 1P1D 的 4.07 倍，还比此前全局最佳点（1P1D C80 的 260,297）
高出 34%。原先归因于 "decode KV 打满" 的坠崖，真正的原因是 prefill 排队
摧毁了前缀缓存的时间局部性。**

### R1（2P1D C64）：加 prefill 确实解了 prefill 的队列，但吞吐没跟上来

这一个点就已经对上面的推论构成了压力。

**prefill 侧，干预完全生效。** 队列峰值从 1P1D 同区间的 20–25 掉到 **7**，
prefill KV 从 0.24 掉到 0.15。第二个 prefill 节点确实在分担负载，
prefill 不再排队——干预本身没有失败。

**但吞吐没有相应提高。** 绝对吞吐 241,417 tok/s，用了 **24 张卡**；
而 1P1D 在 C80 用 **16 张卡**就做到 260,297 tok/s。
多 50% 的卡，绝对吞吐反而低 7%。

1P1D 没有 C64 这个点，按 C56（205,790）与 C72（250,003）线性插值，
C64 约 228K。据此 2P1D 在 C64 的增益约 **+6%**，代价是 +50% 的 GPU。

**decode 侧纹丝不动。** `D_run` 中位数 23，对比 1P1D C72 的 24——**基本一样**。
D_KV 峰 0.39 对 0.47，xfer 中位 4 对 8。也就是说：
prefill 不再是排队的那一方了，但**同时在解码的请求数没有变**。

**读法**：在固定并发 64 下，真正的约束不是 prefill 算力，而是**并发度本身**。
只有 64 个请求在系统里，其中约 23 个在解码；把 prefill 容量翻倍，
只是让这 64 个请求更快地通过 prefill 段，然后在 decode 段等更久。
两段式模型的第一段因此需要修正：**prefill 队列长 ≠ prefill 算力是吞吐上限**。
队列长只说明请求到达速率高于 prefill 服务速率，而系统总吞吐
还同时受在途请求数（= 并发）与 decode 服务速率约束。

这个修正能否成立，取决于 R2：如果 2P1D 在 C128 仍然坠崖，
那么坠崖就是 decode 侧的事，加 prefill 是错的杠杆；
如果 2P1D 在 C128 挺住了，那第一段模型基本正确，只是 C64 这个点并发不够高。

### R2（2P1D C128）：坠崖被完全消除，且刷新了全局最佳

R2 给出的是后一种答案，而且幅度远超预期。

| | 1P1D C80（旧峰值） | 1P1D C128（坠崖） | **2P1D C128** |
|---|---|---|---|
| 绝对吞吐 tok/s | 260,297 | 85,729 | **348,884** |
| tok/s/GPU | 16,268 | 5,358 | 14,537 |
| GPU 数 | 16 | 16 | 24 |
| **实测缓存命中率** | 0.949 | **0.691** | **0.937** |
| 理论缓存命中率 | 0.963 | 0.957 | 0.957 |
| 命中的 prompt token | 6.06 亿 | **1.60 亿** | **8.05 亿** |
| decode KV 占用 | 0.99 | 1.00 | 1.00 |
| prefill 队列峰 | 35 | 95–120 | **35** |
| decode 并发中位 | 28 | — | **65** |

- **绝对吞吐是同并发 1P1D 的 4.07 倍**，并且**比此前任何点都高 34%**。
- `tok/s/GPU` 14,537 已经接近 1P1D 的峰值 16,268，说明多出来的 8 张卡
  几乎被充分利用，而不是摊薄分母。
- **decode 第一次真正忙起来**：并发中位数 65，而此前所有点都卡在 23–28。

### 坠崖的真正机制：排队摧毁了前缀缓存的时间局部性

上一轮报告把 C128 坠崖归因于 "decode 侧 KV 接近打满、传输队列积压"。
**这个归因需要修正。** decode KV 在 1P1D C128 与 2P1D C128 上**同样是 1.00**，
但一个坠崖、一个刷新纪录。KV 打满本身不是坠崖的原因。

真正分开这两个点的是**实测缓存命中率：0.691 对 0.937**。
理论命中率（trace 自身的性质）两者都是 0.957，所以差的不是负载，
是引擎实际兑现了多少复用。

这个差值的杠杆极大。本 trace 约 99% 的 token 是 prefill 输入
（见上一轮报告第 2 节），所以命中率决定了实际要算多少 prefill：
未命中比例从 1−0.95 = 0.05 涨到 1−0.69 = 0.31，
**prefill 的实际计算量放大约 6.2 倍**。坠崖到 1/4 吞吐完全在这个量级内。

那么为什么 1P1D 在 C128 兑现不了复用？**因为队列太长。**
这个 trace 的复用是**同一会话相邻轮次之间**的，属于时间局部性：
一个请求要命中，它依赖的前缀必须在它被服务时还留在缓存里。
1P1D C128 的 prefill 队列堆到 95–120，一个请求从入队到被服务，
中间隔着上百个其他请求的写入，前缀早被挤掉了。
2P1D 把队列压回 35（与 1P1D 峰值点 C80 相同），前缀还在，命中率就回到 0.94。

**一个被排除的解释**：不是 prefill 侧缓存容量不够。
运行期采样里 prefill 的 KV 占用峰值只有 0.15–0.28，
四个点（1P1D C80/C96、2P1D C64/C128）全都远未占满。
容量从来不是约束，**驻留时间**才是。

**因此两段式模型应改写为**：

- 吞吐的上限由 **prefill 有效算力**决定，而"有效"取决于缓存命中率；
- 命中率由**队列驻留时间**决定，队列由到达率与 prefill 服务能力之差决定；
- 于是存在正反馈：队列变长 → 命中率下降 → 单请求 prefill 成本上升 →
  服务能力下降 → 队列更长。这就是坠崖，是一个**正反馈失稳**，
  不是撞到某个容量天花板。
- decode KV 打满是这个过程的**伴随现象**（在途请求多了），不是原因。

这个改写有一个直接的实践含义：**坠崖点不是硬上限，加 prefill 容量就能推走。**
R1 之所以看不出效果，是因为 C64 根本没进入正反馈区间——那里队列只有 20–25，
命中率 0.98，加 prefill 只是让请求更快通过一个本来就不拥堵的段。
**干预必须打在失稳区才看得到效果。**

### R4（3P1D C128）：第三个 prefill 节点基本没用了

| | 2P1D C128 | 3P1D C128 | 变化 |
|---|---|---|---|
| 绝对吞吐 tok/s | 348,884 | 363,019 | **+4.1%** |
| GPU 数 | 24 | 32 | +33% |
| tok/s/GPU | 14,537 | 11,344 | −22% |
| prefill 队列峰 | 35 | 22 | 队列进一步缓解 |
| decode 并发中位 | 65 | 74 | +14% |
| decode KV 峰 | 0.82 | 0.74 | |
| 实测命中率 | 0.987 | 0.989 | 已到顶 |

第三个 prefill 节点**确实**继续缓解了 prefill（队列 35 → 22），
但吞吐只涨 4.1%，却要多付 33% 的卡。

**这说明 C128 上 prefill 已经不再是约束。** 命中率 0.987 已经贴着理论值 0.957
（注：实测口径与理论口径不同，前者含 decode 侧，不必强求相等），
正反馈已经被 2P1D 完全按住，再加 prefill 只是让一个已经不排队的段更不排队。

**约束转移到了 decode**：decode 并发中位从 65 升到 74，仍远低于 128 的并发上限，
说明请求在等 decode 的位置。因此 C256 的杠杆是 **decode 容量**，不是 prefill。

**结论：C128 这一档，2P1D 是最优配比。** 1P1D 坠崖，3P1D 边际收益极低。

### R5（2P2D C256）：prefill OOR，但不是 KV 不够

按上面的推论，C256 走 2P2D（四节点里唯一能加 decode 的形态）。
**结果 BENCH_FAILED，`prefill-OOR`。**

```
rocdevice.cpp:3582: Callback: Queue 0x73d603000000 Aborting with error :
HSA_STATUS_ERROR_OUT_OF_RESOURCES ... Code: 0x1008  Available Free mem : 0 MB
```

关键在于**崩的时候 prefill 的 KV 池几乎是空的**——运行期采样显示
`p0 kv=0.081`、`p1 kv=0.101`，即 8%–10%，而 HSA 报告 **0 MB 可用**。
`max_total_num_tokens=3143744`，KV 池本身绰绰有余。

**所以耗尽的是非 KV 显存，不是缓存。** `mem_fraction_static=0.85` 把 85% 的 HBM
划给权重 + KV 池，剩下的 15% 要装下 CUDA graph、激活、scratch 和通信缓冲。
`PREFILL_GRAPH_MAX_BS=256` 让 graph 捕获吃掉了这 15%，运行期 HSA 要 scratch 时
一分不剩。

**而这些 graph 本来就是浪费的。** prefill 的 `num_running_reqs` 在本 campaign
**每一个点**上都被钉在 DP 宽度 8（见上表 `D_run` 对照，prefill 侧恒为 8）。
为 batch 256 捕获的 graph，prefill 永远不会用到。

**处理**：C256 重测时把 prefill 限到 128（该 shape 上已验证能起来的最大值），
decode 保持 256。这个放宽**显式声明给 live gate**（新增 `--prefill-conc`），
gate 仍然 fail-closed 地按声明值校验，并把它写进 `live-gate.json`——
而不是悄悄跳过检查。

### R9（2P1D C192）：峰值就在 C128 附近，且到 C192 仍未坠崖

节点 141 掉线后 2P2D 做不了，C256 只能落到 2P1D。C192 是在冲 C256 之前
先把曲线在高并发一侧夹住。

| | 2P1D C128 | 2P1D C192 | 变化 |
|---|---|---|---|
| 绝对吞吐 tok/s | 348,884 | 340,765 | **−2.3%** |
| tok/s/GPU | 14,537 | 14,199 | −2.3% |
| prefill 队列峰 | 35 | **65** | 接近翻倍 |
| **decode KV 峰** | 0.82 | **0.98** | **逼近饱和** |
| **decode 传输队列中位** | 18 | **67** | **3.7 倍** |
| decode 并发中位 | 65 | 62 | 基本持平 |
| 实测命中率 | 0.987 | 0.985 | 仍然健康 |

两点读法：

1. **2P1D 的峰值在 C128 附近**，C192 已经在下坡，但只掉 2.3%，
   远不是 1P1D 从 C96 到 C128 那种断崖。曲线到 C192 依然是平的。
2. **约束已经明确换到 decode**：decode KV 从 0.82 顶到 **0.98**，
   传输队列中位数从 18 涨到 **67**——六十多个请求做完 prefill、
   排队等 decode 侧腾出 KV 空间。而命中率仍有 0.985，
   说明 prefill 侧的正反馈没有被触发，**这一次瓶颈是真的在 decode 容量上**。

这与 R4（第三个 prefill 节点只换来 +4%）指向同一个结论：
**再往上走需要的是 decode 节点，而不是 prefill 节点。**
C256 在 2P1D 上按这个趋势应当撞上 decode KV 墙——这正是 R8 要验证的。

## 问题与解决方案

### 1. 3P1D 的 bootstrap 端口与 engine 端口相撞，两秒即挂

第一次运行里 R3/R4 在 2 秒内 `LAUNCH_FAILED`，`launch.log` 是空文件。
原因在 `lib/common.sh:188` 的 `configured service/worker ports overlap`——
它拦对了。

各类端口按**基址 + 实例序号**分配，而 `config.sh` 里
`BOOTSTRAP_PORT_BASE=18998` 与 `ENGINE_PORT_BASE=19001` **只差 3**。
1P1D/2P1D 最多 3 个实例，bootstrap 用到 18998–19000，正好差一格没撞上；
一旦上到 **4 个实例**（3P1D，或 2P2D），第四个实例的 bootstrap 端口
= 18998 + 3 = **19001** = engine-0 的端口。

这是个只在实例数 ≥ 4 时才出现的配置缺陷，前面所有 campaign 都没触发过。

**处理**：本 campaign 统一传 `BOOTSTRAP_PORT_BASE=18900`，留出 16 个实例的余量。
统一传（而不是只给 4 实例拓扑传）是为了让 campaign 内各点配置保持一致——
端口号不是性能参数。三个拓扑的 `validate_topology` 均已逐一验过通过。

### 2. `/home` 写满，R2 跑了 33 分钟后无声死亡

R2（2P1D C128）第一次尝试在 warmup 阶段的 `runner.log` **直接截断**：
没有超时消息、没有错误、`errors=0`，最后一行停在
`returned=140/270 | sent=142 | in_flight=2 | elapsed=720.1s`。
紧接着 `sweep.log` 出现 `printf: write error: Disk quota exceeded`，
这也是 R2 既没有 `VERDICT` 也没有 index 行的原因——**写不进去**。

`/home` 是 10T 共享 NFS，当时 100% 满、仅剩 30G。我这边占 96G，
其中 **41.8 GB 是 60 个 `aiperf_artifacts` 目录**，单个
`server_metrics_export.json` 就有 3.7 GB。

**一个被排除的解释**：warmup 期间 decode 侧连续 46 个采样点全是
`run=0 q=0 prealloc=0 xfer=0 kv=0.000`，看着像"请求没进 decode"。
**这是常态，不是故障**——已 PASS 的 R1 在 warmup 期同样是 42 个采样点全 0。
该 trace 约 99% 的 token 是 prefill 输入，warmup 阶段 decode 占用接近零。
（与上一轮报告问题 9 里记下的同一条教训；我差点第二次栽在上面。）

**处理**：

1. 删除四个已提交 campaign 的 `aiperf_artifacts`，释放 40.5 GB。
   这些正是提交时明确排除的部分——重算报告结论所需的数字
   全在 `agentx_conc<C>.json`、`metrics_sample.log` 与 gate 证据里，
   而这些已经在 git 中（commit `713e4a2`）。
2. `sweep.sh` 在每个点 **PASS 后**自动删除该点的 `aiperf_artifacts`。
   失败的点保留——那正是需要它们的时候。
3. `sweep.sh` 在开跑前检查剩余空间，低于 20G 直接 `ABORTED_DISK` 跳过。
   花一小时占着机器最后什么都没拿到，比不开始更糟。

第一次尝试的产物保留在 `p8x2d8/c128.attempt1-disk-full/`。

### 3. 节点 141 的 docker daemon 停了，3P1D 与 2P2D 就此中断

21:46 起，凡是用到 `crsuse2-m2m-141` 的点都在 8 秒内 `LAUNCH_FAILED`：

```
[launch] checking decode-1 on crsuse2-m2m-141 (GPUs 0,1,2,3,4,5,6,7)
Cannot connect to the Docker daemon at unix:///var/run/docker.sock.
```

`systemctl is-active docker` 在该节点返回 `inactive`，重启需要 sudo，
当前账号没有该权限（`sudo: a password is required`），
`journalctl` 也因权限不足读不到。**需要管理员介入。**

这同时解释了 R3 更早那次"四个节点同时 `docker inspect` 超时"——
141 的 daemon 当时已经在恶化了。

**影响**：3P1D（141 作 prefill-2）与 2P2D（141 作 decode-1）都无法组网。
R3、R6 记为 `BLOCKED`。剩下 137 + 140 作 prefill、138 作 decode，
即 2P1D，因此 C256 改在 2P1D 上做。

**顺带修掉的一个脆弱点**：`sweep.sh` 开头的镜像门禁原先硬编码了四个节点，
于是一个**本轮根本用不到**的节点把整个 sweep 卡在启动阶段
（`FATAL: crsuse2-m2m-141 image is MISSING`）。
改为从 plan 里推导——只检查"还没有 VERDICT 的点会用到的节点"的并集。
门禁的范围应当等于本轮的实际触及面，不多不少。
