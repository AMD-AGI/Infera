## 2026-09-08 后续调查与修复

### 根因定位

SGLang `send_kvcache` 的实际数据方向是 prefill producer-push：

`batch_transfer_sync[_write](local_src, remote_dst)`

旧 preflight 测试的是相反的 receiver-pull：

`batch_transfer_sync_read(remote_src, local_dst)`

四向隔离在无 `iommu=pt` 的 140/142 上得到：

- GPU→CPU READ：双向 `verified=true`，约 49.94–50.49 GB/s。
- CPU→GPU READ：双向 `verified=false`；256 MiB 的 8 个 chunk、268,435,456 字节全部仍为 sentinel `0`。
- GPU→GPU production WRITE，256 MiB：双向 `verified=true`，约 42.73–43.31 GB/s。
- GPU→GPU production WRITE，1 GiB：双向 `verified=true`，约 45.72–45.96 GB/s；32/32 chunk、全部字节一致。

因此，历史 `verified=false` 不是“生产 KV WRITE 已损坏”的证据。它证明的是 ionic/Mooncake receiver-pull READ 写入本地 GPU 的独立路径仍有问题；当前 SGLang 1P1D 不使用该路径。

诊断证据：

- `results/diag_gpu_to_cpu/`
- `results/diag_cpu_to_gpu/`
- `results/diag_production_write/`
- `results/diag_production_write_1g/`

### 当时调查中实施的诊断改动与当前边界

- Mooncake preflight 增加显式 producer-push RDMA WRITE，与 SGLang `send_kvcache` 一致；公共默认仍为 READ，本 benchmark 配置默认 WRITE。
- 当时排障曾保存额外 TRACE/detail 并强制 `opcode=write`；这些临时诊断扩展和 preflight gate 已在清理中退出。
- build/correctness/AgentX 保留 pair+image+source+config gate；preflight 仅记录日志和原始退出码，不再参与 resume 或最终成功判定。
- inventory 记录 IOMMU 模式，并排除 `iommu=pt`、`iommu.passthrough=1`、`iommu=off`、`amd_iommu=off/pt` 节点。
- 当时聚焦单测 47 项通过（不含当前 `test_preflight_kv.py` 完整回归）；当时 matched-only 诊断在 8 GPU×双向共 16 条 WRITE 路径上全部 `verified=true`。

## 执行中发现并修复的问题

- inventory 现在直接生成 `selected.env`，并优先保留仍健康的请求节点；节点失效时从候选池自动补位。
- 主工作流在加载 `config.sh` 前先 inventory，避免配置阶段绑定已占用节点。
- 节点对改变且从运行阶段 resume 时，自动回到 build，保证镜像和节点证据一致。
- 修复 ready timeout 环境变量名：`INFERA_SGLANG_READY_TIMEOUT` 改为实际被 worker 读取的 `INFERA_ENGINE_READY_TIMEOUT`。
- 冷启动预算和外层健康检查统一为约 3600 秒，避免 AITER 首次 JIT 在 1800 秒时被误杀。
- engine、router、etcd 增加 `--init`。
- 生命周期从直接 `docker rm -f` 改为先 `docker stop --time 120`，再普通删除，失败才降级强制删除。
- stop 对删除失败增加重试。
- 当前工作流把 preflight 降为诊断阶段：失败会记录原始退出码并继续，不再创建或消费失败门禁。

## 剩余风险与建议

1. 该历史 run 仍不能批准生产上线：它使用错误方向的门禁、`continue` 策略，且 correctness 与 AgentX 不在同一节点对/镜像证据链。
2. 生产 WRITE 已在两个方向、8 个 GPU 上通过；ionic receiver-pull READ→本地 GPU 的 silent no-write 仍需由 Mooncake/ionic 团队定位，但不得与当前 SGLang WRITE 路径混为一谈。
3. 最终验收必须恢复原 KV-aware 配置，并以新 RUN_ID、同一 pair+digest 完成 correctness/AgentX；preflight 结果作为独立诊断证据审阅。
4. prefill 容器退出后 HBM 可能延迟释放数十分钟。inventory 能绕开节点，但驱动级资源回收仍需修复。
5. 只有最终 KV-aware workflow 退出 0，且 report 内能关联 build/correctness/AgentX gate，才可作为生产验收；preflight 不再是硬门禁。
