===================== HOW IT IS COUNTED =====================

Each decode worker logs a "Decode batch" line while it is generating. Counting
them per worker is the distribution measurement — the router's own log does not
record per-request placement, so the workers' own logs are the evidence.

Total, over the whole session:

  $ grep -ac 'Decode batch' pd_decodeA.log
  23
  $ grep -ac 'Decode batch' pd_decodeB.log
  8

23 = 17 (kv-aware arm) + 6 (round-robin arm). 8 = 0 + 8. The published numbers
are the per-arm DELTAS of these counters, which is why they are quoted as
"17 / 0" and then "+6 / +8".

===================== WHAT THIS RE-DERIVATION DOES *NOT* SETTLE ==============

- **Which arm is which is inferred from the timestamps**, not from a marker in
  the decode logs. The workers do not log the router's policy. The mapping
  (12:17-12:18 = kv-aware, 12:19-12:20 = round-robin) comes from the run
  transcript and from the router log line quoted in
  results/step4_role_weights_routing.txt, and the router log itself is gone.
  The split is unambiguous in shape — one arm is 17/0, the other 6/8 — but the
  LABELS rest on the in-session record.

- **"Decode batch" lines are not requests.** A long generation logs several. The
  counts are a proxy for where decode work landed, not an exact request tally.
  For the differential that is sufficient: the same workload ran twice, so the
  proxy is comparable across arms. It is not a throughput measurement.

- Each arm ran the same 32-request workload (4 sessions x 4 turns x 2 phases).
  The prefill leg's log confirms 64 completions across the two arms
  (12:17-12:20), i.e. 32 each.
