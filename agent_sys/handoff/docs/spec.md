## 1. Purpose

A handoff is a module's input or output. It is the only thing that crosses
between tasks, which makes it the only place where quality can be enforced
system-wide.

**This document specifies the content and lifecycle layer.** The runtime slot —
identity, versions, the `CREATED → GENERATING → VALID | INVALID` machine, who may
write it — is already specified in `task_graph` spec §3.1 and is **not** restated
here. The two layers meet at one point: a `Handoff.type` names a handoff *kind*,
and a kind is what this document specifies.

```
task_graph spec §3.1        this document
─────────────────────       ──────────────────────────────
Handoff       the slot      HandoffSpec    the kind
  .id                         name
  .versions[]                 content shape
  .type ─────────────────────►schema
  .open_next() / .seal()      validators
                              scope tag
```

### 1.1 In scope

- What a handoff's content is: a README plus a typed dictionary.
- The digest that makes a version tamper-evident.
- The scope and lifecycle vocabulary: `fixed` versus `addons`.
- Storage: a filesystem tree, keyed and versioned, with tree-shaped permission.
- The validator binding, which is many-to-many.
- Locality independence — what makes a handoff replayable elsewhere.

### 1.2 Out of scope

- **The versioned slot** — `task_graph` spec §3.1.
- **How a validator works** — [`../../validator/docs/spec.md`](../../validator/docs/spec.md).
- **How a validation verdict is recorded** — the validator calls
  `update_validation_status` (§5.2); what it decides is the validator's business.

## 2. Design principles

| # | Principle | Consequence |
|---|---|---|
| 1 | **A handoff is standardised, or it is not a handoff** | What it contains and where each thing sits is fixed by the kind and by the content type. §3 |
| 2 | **A human can read it** | Every handoff opens with a README. An artefact only a program can open is a blob, and blobs do not get reviewed |
| 3 | **Checkable by construction** | A kind with no validator cannot be admitted. §5 |
| 4 | **Local-independent** | It names its dependencies and contains no local paths, so any suitable machine can consume it. §7 |
| 5 | **Tamper-evident** | Content carries a digest. §3.3 |
| 6 | **Storage is a tree, and so is permission** | §6 |

## 3. Content

### 3.1 A README plus a dictionary

Every handoff version's content is:

```
content
  ├─ README.md      required. Human-first. Must carry a fixed set of sections
  └─ items          a dict: key → typed value
```

**The README is required and is not decoration.** It is what a reviewer opens
first, and its required sections are fixed by the content type (§3.2). A handoff
whose README is absent or missing a required section is malformed.

**Keys of `items`** come from one of two places:

| Source | When |
|---|---|
| Declared in the handoff kind's schema | The normal case. The kind knows what it carries |
| Generated by the agent at runtime | When the number or names of items are not knowable in advance — several extracted operators, one per key |

Runtime keys are why `items` is a dict rather than a fixed record. A kind may
declare some keys and leave room for others.

### 3.2 Four content types

A handoff kind declares its content type, and the type fixes what `items` must
carry and what the README's sections are.

| Type | `items` carries |
|---|---|
| **`reproducible`** | `script` or `command` · `result` · `code` (a list of repos, own code, patches to concatenate or merge — the *materials*, well structured; the assembly lives in the script) · `env` (hardware, software, repos) · `logs` · `watchout` |
| **`code`** | `codes`. Skills keep the boundary and interface clear; validators keep it testable somewhere |
| **`structured_text`** | One or more of `text.json` / `.yaml` / `.xml`, plus `schema` if there is one |
| **`text`** | `content`, possibly several files |

`reproducible` is the richest and is the one the reference workflow mostly
produces: a thing that ran, the way to run it again, what came out, and what to
watch for. Its `env` entry is what makes it re-runnable elsewhere (§7), and it is
**required** whenever `script` or `command` is present — an executable with no
declared environment is not reproducible, whatever it claims.

**Each content type needs its own agent skill / rule / hook set** so an agent
produces it correctly. Four sets, not one generic one; recorded in
[`../../docs/TODO.md`](../../docs/TODO.md).

### 3.3 The digest is `sha256`

The task definition asks for md5, a hash, or any one tamper-evidence mechanism.
This spec picks one, because a field whose algorithm varies per producer is not a
mechanism — a consumer would have to be told which one applies, and that
negotiation costs more than the choice.

`sha256`: in the standard library, not collision-broken, and what a
content-addressed store would use if §6's open question is ever closed that way.

**The digest covers the content.** Two things are deliberately excluded:

- **Metadata** — a consumer holding a copy does not hold the producer's
  timestamp, and recomputation must be possible from what a consumer has.
- **Validation status** — a verdict recorded against a version must not change
  that version's identity. §5.2.

**What it is and is not for.** It detects accidental corruption and casual
tampering, and answers "is this the same artefact I validated?". It is not a
security boundary: an agent that can write a handoff can write its digest. The
boundary that matters is the producer/validator context separation (main spec
§5.2), and no hash substitutes for it.

Canonicalisation — key order, float formatting, line endings — is a design-stage
decision recorded in [`../../docs/TODO.md`](../../docs/TODO.md), because getting
it wrong makes the field useless and it should not be decided by accident.

## 4. Scope and lifecycle tags

A closed vocabulary. A handoff carries exactly one tag.

```
fixed                          declared by the recorded task graph
  ├─ required                  the task cannot run without it
  └─ optional                  the task runs; behaviour may differ

addons                         injected, outside the declared interface
  ├─ temp                      run-local: scratch, intermediate, this-run-only
  └─ knowledge                 long-lived accumulated experience
```

| Tag | Storage | Permission | Retention |
|---|---|---|---|
| `fixed.required` | Handoff storage | Covered by the consuming task's permissions (`task_graph` spec §3.2.2) | Kept for the life of the graph run, archived with it |
| `fixed.optional` | Handoff storage | Same | Same |
| `addons.temp` | Playground | The injecting and receiving task only | Discardable when the run ends |
| `addons.knowledge` | **Knowledge-handoff storage** — a separate instance (§6.2) | Broadly readable, narrowly writable | Outlives every run |

### 4.1 Knowledge handoffs borrow the word, not the machinery

A knowledge handoff is how expert experience enters an agent's context —
deployment guides, cluster conventions, pitfalls, few-shot examples. It is called
a handoff because it is versioned, digested, and stored like one.

**It is not forced through the whole task–agent–handoff system.** It has no
producing task in the ordinary sense, it is not an input any scheduler waits on,
and it does not participate in dispatch. Consequently:

**Its checking is loose.** A knowledge handoff's validators are limited to
**schema conformance and internal consistency**. Nothing asks whether accumulated
experience is `strong` — the taxonomy does not apply, and pretending it does
would produce a `weak` label on every piece of knowledge in the system, which
carries no information.

### 4.2 `addons` cannot satisfy a required input

A recorded graph declares its interface, and a fixed interface is the point of
the system. `addons` is the escape valve: a user or another agent injects
something that helps without amending the recording.

The constraint that keeps it honest: **an `addons` handoff cannot satisfy a
`fixed.required` input.** If it could, the declared interface would be advisory.
A task blocked on a missing required input stays blocked.

## 5. Validators

### 5.1 The binding is many-to-many

**A validator may need more than one handoff, and a handoff may have several
validators.** Both directions are genuinely many, and neither side may assume
otherwise:

```
        handoff kind A ──┐        ┌── validator X   (checks A alone)
                         ├────────┤
        handoff kind B ──┘        └── validator Y   (checks A and B together)
```

A validator taking several handoffs is how a cross-handoff check is expressed
(validator spec §3). A handoff with several validators is the normal case — one
checking its shape, another its usability, another its trustworthiness.

**Lookup is by handoff uuid**, with an **RFC 6901 JSON Pointer** into the content
where a validator needs one specific value rather than the whole artefact. Not by
kind: a task with two inputs of the same kind would be ambiguous.

**A Pointer rather than a jsonpath, and the reason is a property of the
standard.** RFC 9535 §2.5.1.2 forbids a syntactically valid JSONPath query from
erroring — *"some operations that might be considered erroneous, such as using an
index lying outside the range of an array, simply result in fewer nodes being
selected"* — so **no** JSONPath implementation can distinguish "the path is
wrong" from "the value is absent". The caller gets an empty result either way,
which is the silent pass this system exists to prevent. A Pointer separates the
three outcomes: malformed, missing, and a value that is genuinely `null`.

**The binding is recorded on both sides, and a conflict is fatal.** A handoff
kind names its validators; a leaf validator names the kinds it binds to. The
double link is for convenience — each direction is needed at a different moment —
and if the two disagree the system **crashes at load** rather than picking a
winner. A silently-resolved conflict means one of the two records is lying, and
nobody finds out which.

### 5.2 Recording a verdict

A validation phase produces **no output handoff**. It calls

```
handoff.update_validation_status(versioned_handoff, ...)
```

which is persisted — a YAML record maintained alongside the artefact — and is
**excluded from the digest** (§3.3).

**Every versioned handoff carries a validation history**: for each validator, the
result of each execution, plus enough context to interpret it — which task and
which versioned agent ran the validation, and the environment it ran in (readable
from that agent). "Has this been checked, by what, when, and did it pass" is
answerable from the handoff alone.

### 5.3 Every kind carries at least one validator

A kind with no validator cannot be admitted to the registry. A command-line flag
permits it for bring-up and debugging:

- **off by default**;
- every kind it lets through is **reported** by name at startup and in the run
  record;
- it does not disable existing validators, only permits absent ones.

### 5.4 Admitting a kind is a review of coverage

When a new handoff kind is submitted, the reviewable artefact is not "does it
have a validator" — that is checked mechanically. It is **how much of the kind
the validators actually cover**: which `items` keys nothing reads, which failure
modes would pass, whether each validator's strength label is honest, and whether
any validator depends on the producer.

## 6. Storage

### 6.1 v1 is a filesystem tree

There is not much choice here — an object store or a SQL database would serve,
and neither is better for an artefact a human must be able to open — so the
interface is clear and v1 is a filesystem.

| Property | |
|---|---|
| **Key–value** | A handoff is looked up by uuid |
| **Versioned** | Each version is its own directory |
| **Tree-shaped permission** | Reach is decided by containment: a task reaches its own subtree and its subtasks' (`task_graph` spec §3.2.2) |
| **Structured folder names** | Prefix, substring, and suffix conventions carry the information a permission hook needs, so a decision is a string match rather than a lookup. [`../../env_mgr/docs/spec.md`](../../env_mgr/docs/spec.md) §4 specifies the scheme |

The tree is what makes the permission model cheap: because a subtask's storage
sits inside its parent's, "may this task reach that path" is containment, and a
hook answers it without consulting a registry.

### 6.2 Knowledge handoffs get their own storage

A **separate handoff storage instance** for knowledge handoffs. The same
implementation, instantiated against a filesystem — or another storage backend —
of its own.

Separate because its lifecycle is different in every respect: it outlives every
run, it is not scoped to a task's subtree, and its permission shape is
broadly-readable rather than tree-confined. Sharing one instance would mean the
run-scoped rules could not be simple.

### 6.3 The consumption protocol

An agent **copies a handoff from storage into its playground and works on the
copy.** It never edits the stored artefact, and never depends on the storage
path.

This is what makes a re-run comparable to the run before it: the input is the
same bytes both times, because nobody edited it in place.

### 6.4 Records are detailed, and not yet movable

A stored handoff record carries **enough detail to be trackable** — provenance,
validation history, environment. Making storage *movable* between locations is
deferred; recorded in [`../../docs/ROADMAP.md`](../../docs/ROADMAP.md).

## 7. Locality independence

**A handoff contains no local information.** It declares hardware and software
dependencies, its container image if it needs one, and nothing about the machine
that produced it. Any machine satisfying the declaration can consume it.

For a `reproducible` handoff this is the `env` item (§3.2) and it is required.
For the others the kind's schema declares what applies.

A handoff carrying `/home/someone/run3/` is a record of one machine's afternoon,
not a transferable artefact — and the system's first principle is that a result
that cannot be re-obtained is not a result.

## 8. The spec file and the registry

A handoff kind is declared in a **task package** (main spec §4.3) as a jsonnet
source, rendered to YAML and validated against the handoff JSON Schema — which
this repository owns and the package does not:

| Key | Meaning |
|---|---|
| `name` | The kind name. Unique; this is what `Handoff.type` holds |
| `version` | The spec's own revision. **Maintenance metadata only** — nothing at runtime reads it (closure spec §1.2) |
| `description` | What this kind of artefact is, for a human |
| `content_type` | One of the four in §3.2 |
| `scope` | One of the four §4 tags |
| `items_schema` | The declared keys of `items` and their shapes. Runtime-generated keys are permitted where the schema says so |
| `readme_sections` | The sections the README must carry, beyond the content type's defaults |
| `validators` | Validator spec names. At least one, unless the §5.3 flag is set |
| `dependencies` | §7 |

The registry is one of the four independent registries (main spec §4.1). It
answers which kinds exist, which validators a kind is bound to, and — through a
reverse index — which kinds a given validator covers.

**Load-time checks**, each failing loudly with the file path:

1. The YAML validates against the schema; the name is unique.
2. Every named validator resolves in the validator registry.
3. At least one validator is named, unless the flag is set — in which case the
   kind is admitted and reported.
4. The two-way binding agrees with the validator registry's side. **A mismatch
   crashes** (§5.1).
5. A `reproducible` kind whose `items_schema` permits `script` or `command`
   without `env` is rejected.

## 9. Acceptance criteria

1. A handoff spec that omits a required key, or whose `items_schema` is not a
   valid schema, is rejected at load with the file path and the offending key.
2. A handoff version with no README, or missing a section its content type
   requires, is malformed and is rejected.
3. Each of the four content types accepts its declared `items` and rejects an
   item the type does not define.
4. A `reproducible` handoff carrying a `script` with no `env` is rejected.
5. `items` accepts a runtime-generated key where the schema permits one, and
   rejects it where the schema does not.
6. Recomputing `sha256` over a consumed handoff's content reproduces its digest,
   after a round trip through storage and a copy into a playground.
7. **Recording a validation verdict does not change the digest.**
   `update_validation_status` is persisted, is readable, and the version's
   identity is unchanged.
8. A versioned handoff's validation history names, per validator, each execution
   result plus the task, the versioned agent, and the environment.
9. **A validator taking two handoffs, and a handoff with three validators, both
   resolve** — the binding is exercised in both directions.
10. **A binding conflict between the two registries crashes at load**, naming
    both sides. Nothing is silently resolved.
11. Lookup by handoff uuid resolves; lookup with a JSON Pointer returns the
    addressed value, and **a malformed pointer, a pointer addressing nothing, and
    a value that is `null` are three distinguishable outcomes**; a task with two
    inputs of the same kind is unambiguous.
12. A handoff kind naming no validator is rejected unless the flag is set — in
    which case it loads **and** its name appears in the startup report and the
    run record.
13. Knowledge handoffs land in the separate knowledge storage, and their
    validators are limited to schema and internal consistency.
14. Each of the four scope tags produces the storage, permission, and retention
    behaviour §4 tabulates — verified by asserting where the artefact lands and
    who can read it, not by reading the tag back.
15. An `addons` handoff does not satisfy a `fixed.required` input: the consuming
    task stays in `WAITING_HANDOFF`.
16. **Permission is containment.** A task reaches its own subtree and its
    subtasks'; a sibling's subtree is denied. Asserted against the real layout.
17. A handoff whose content declares an absolute local path fails its
    locality-independence check. **NOT ENFORCED as of 2026-08-31** — user-ruled
    after the check refused a correct artefact, and every correct one it would
    have been given: measured 97% false positive on a real kit, because it reads
    a path's *shape* and `locality.py`'s own docstring records that Debian
    #1002451 refused that on the record. `handoff/store.py` no longer calls it;
    the module and its tests are kept intact, so re-wiring is one line. The
    rebuild — wire the oracles, split the certain verdict from the best-effort
    one, and choose where a declared image's prefixes live inside
    `dependencies` — is `ROADMAP.md` §6.4 at P2. Stated here rather than left to
    the roadmap because a criterion a reader believes is enforced, and is not, is
    worse than one that says so.

## 10. Open questions

| Item | Status |
|---|---|
| **Digest canonicalisation** | §3.3. The algorithm and scope are fixed; the serialisation is not. In [`../../docs/TODO.md`](../../docs/TODO.md) |
| **`addons.temp` retention** | "Discardable when the run ends" is not "discarded", and nothing sweeps a playground. The playground is also part of what makes an agent resumable (`env_mgr` spec §6), so the sweep cannot be unconditional |
| **Knowledge handoff provenance** | It outlives every run, so a `producer_task_id` may point at a task no live graph contains. Whether that reference must stay resolvable is unspecified |
