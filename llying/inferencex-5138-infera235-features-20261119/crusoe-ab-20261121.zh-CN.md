# InferenceX#5138：Infera#235 的四项 feature 在 crusoe 上的 A/B 实测（11-20 – 11-21）

对象是同目录 [`README.zh-CN.md`](README.zh-CN.md)（11-19）里"不打补丁就能开"的四项：MTP K5 → K3、decode mem 0.95、router
`decode-request-weight: 400000`、`stream-interval 30` + `SGLANG_CLIP_MAX_NEW_TOKENS_ESTIMATION=8`。在 crusoe（spur）MI355X 上，
用 [#5138](https://github.com/SemiAnalysisAI/InferenceX/pull/5138) 的 stock 镜像和 recipe 一次改一项，判断哪几项值得加进 #5138。
为了在本集群跑起来做的修正（GEM KV 分配、换 libionic、Mooncake [#4540](https://github.com/kvcache-ai/Mooncake/pull/4540) /
[#4541](https://github.com/kvcache-ai/Mooncake/pull/4541)）只用于本地 A/B，不进 PR（第 1.2 节）。

## 0. 结论

| # | 原报告的建议 | crusoe 实测 | 对 #5138 |
|---|---|---|---|
| 1 | d4 C80 用 K3；2P1D 用 K3 | d4：C64 +1.2%（同机），C80 −0.1%（不同机）；C96 K3 37,504，只比 C80 K5 高 0.4%，TTFT p90 23 s。2P1D K3 预热时两次卡死，被取消，没有数据 | 保持 K5，不拆 K3 条目；d4 的并发列表不扩到 C88 / C104 |
| 2 | 2P1D decode mem 0.92 → 0.95 | 没测。0.92 下 d4 C80 K5 跑满 3600 s，decode 最紧的卡只剩 2.8 GiB；2P1D decode 剩 7.9 GiB；0.95 要再占约 8.6 GiB | 所有形状保持 0.92 |
| 3 | d4 router `decode-request-weight: 400000` | C64：+2.2%，interactivity p50 / p90 55.2 / 50.8 → 57.7 / 53.5，TTFT p90 4.50 → 4.52 s；和基线不在同一台机器上 | 四项里唯一看到收益的；证据偏弱，要加先在 InferenceX sweep 上确认 C64 / C80 |
| 4 | base 加 stream-interval 30 + CLIP 8 | 没测：预期 +1% 左右，小于单次 ±0.9% 的波动；原计划并进最终合并复测，复测没有跑 | 没有本集群证据 |

另外两条和 recipe 直接相关：

- **`MC_RDMA_NOTIFY_ENABLED=0`：** 镜像里的 Mooncake `748af1a5` 默认开原生通知，本集群上 2P1D 和 1P1D 按 #5138 原样都起不来；
  两侧加上这个变量后起栈，Mooncake 报错为 0（第 3.1 节）。#5138 已在 11-20 拿掉 2P1D，说明里写了后续 PR 带这个设置加回来。
  建议 1P1D 也加：CI 上 1P1D 原样能过，但在本集群原样起不来，说明余量很小；关掉对 SGLang 没有功能影响。
- **2P1D C176 K5（带 #4540 / #4541 和 notify0）：** 36,417 tok/s/GPU，比 #5138 的参考前沿 38,392 低 5.1%，interactivity p90 43.2
  和参考相同。prefill 节点网卡在这一个点上仍有 133.8 亿个重传包、351 万次 ACK 超时，差距大概率来自本集群的跨机网络，
  这个数字不能用来评价 recipe。

### 1.2 起栈方式与对齐

spur 的 `srun` 没有 pyxis 的 `--container-writable`，而且作业里任何一个步骤非零退出，整个作业就结束，所以 srtctl 不能直接跑。
`crusoe-ab-20261121/harness/plan.py` 按 srtctl 的规则（参数顺序、环境变量合并顺序、端口分配、不占整机的 worker 用
`ROCR_VISIBLE_DEVICES`）把渲染出的配置拼成 docker 命令：etcd、worker（`python3 -m infera.engine.sglang`）、router
（`python3 -m infera.server --router-backend rust`）。

对齐结果：d4 C80 K5 本集群 37,353，PR 的 sweep（[run 44484159596](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/44484159596)，
`mi355x-amds`）同一点 37,645（−0.8%），PR 的参考前沿 37,310（+0.1%）；d4 C64 K5 32,672，参考前沿 32,532（+0.4%）。两边客户端
最后打印的统计（成功 / 预热 / 出错请求 9,289 / 884 / 4 对 9,333 / 884 / 8，rps 2.6，前缀命中 64.1%，KV 用量 99%）几乎相同。

本集群专用的偏差，只为在这里跑起来，不进 PR：

| 偏差 | 原因 |
|---|---|
| KV 用 GEM 分配：`LD_PRELOAD` [`hip_gem_alloc.c`](../pd-repro-crusoe-20261116/patches/hip_gem_alloc.c)（含设备号修正，同 11-16 的复现），覆盖 SGLang 的 `disaggregation/mooncake/utils.py`（[`patches/sglang-703e763d-mooncake-utils-amd-gem.diff`](crusoe-ab-20261121/patches/sglang-703e763d-mooncake-utils-amd-gem.diff)），加 `SGLANG_MOONCAKE_CUSTOM_MEM_POOL=AMD_GEM`、`MOONCAKE_DISABLE_HIP_DMABUF=0`、`MC_HIP_KFD_PIN_FIX=0`、`MC_DISABLE_HIP=1` | 本集群没有 peer memory，只能走 dma-buf 注册，驱动对 dma-buf 注册的显存计两次 |
| 把 libionic 54.0-187（repo.radeon.com）挂到镜像的 `libionic.so.1.0.54.0-149.g3304be71` 上 | 镜像自带的 54.0-149 与宿主机 ionic 驱动 ABI 不匹配；recipe 挂的宿主机 libionic 又要 GLIBC 2.38。两种情况 Mooncake 都会悄悄退回 TCP |
| `--disaggregation-ib-device` 的 `rdma0..7` 换成 `ionic_0..7` | 网卡名不同，数量相同 |
| 同机第 k 个容器启动前先空转 30,000 × k 个进程号，代替 `--pid=host` | 同机容器共用 `--ipc host`，RCCL 按进程号给共享内存命名，各容器的进程号都从小数开始；docker-authz 不允许 `--pid=host` |
| 模型先拷到本地 NVMe，HF cache 用本地目录 | 读模型快，不依赖 `/var/lib/hf-hub-cache` |
| 仅 2P1D：带 #4540 + #4541 的 Mooncake（[`patches/mooncake-748af1a5-4540-4541.patch`](crusoe-ab-20261121/patches/mooncake-748af1a5-4540-4541.patch)，在 `748af1a5` 上 cherry-pick，按 stock 镜像的编译参数重编，起容器时解包覆盖），两侧加 `MC_RDMA_WRITE_PREFER_DEST_NIC=1`、`MC_IB_TIMEOUT=18` | crsuse2 跨机写入时接收端丢帧（[`../mooncake-4540-4541-review-20261111/`](../mooncake-4540-4541-review-20261111/README.zh-CN.md)）。#4540 已于 11-19 合入 Mooncake 主线，变量名是 `MC_RDMA_WRITE_PREFER_DEST_NIC`；#4541 仍 OPEN。补丁是否生效按容器里 `engine.so` 有没有新变量名判断（打补丁后 md5 `2887e0b5`，stock `e3dc7093`），Mooncake 不会把配置行打到容器输出 |

## 2. d4（PP4 prefill + TP4/DP4 decode，8 卡，单机）

| 点 | 机器 | tok/s/GPU | 对照 | interactivity p50 / p90 | TTFT p50 / p90（s） | 出错 / 计分请求 | decode 最少剩余显存 |
|---|---|---|---|---|---|---|---|
| C64 K5 | v3-178 | 32,672 | — | 55.2 / 50.8 | 2.09 / 4.50 | 3 / 7,415 | 6.4 GiB |
| C64 K3 | v3-178 | 33,048 | +1.2% | 57.5 / 48.6 | 2.05 / 4.36 | 3 / 7,497 | 12.0 GiB |
| C64 K5 + 400k | v3-072 | 33,379 | +2.2% | 57.7 / 53.5 | 2.18 / 4.52 | 2 / 7,563 | 7.0 GiB |
| C80 K5 | v3-085 | 37,353 | — | 49.2 / 43.5 | 3.56 / 9.04 | 4 / 9,289 | 2.8 GiB |
| C80 K3 | v3-240 | 37,303 | −0.1% | 48.0 / 43.8 | 3.53 / 9.18 | 5 / 9,271 | 11.5 GiB |
| C96 K3 | v3-085 | 37,504 | 对 C80 K5 +0.4% | 46.7 / 43.0 | 7.34 / 22.96 | 5 / 9,439 | 11.2 GiB |

- 每个点 3600 s 计分，单次运行波动约 ±0.9%。出错请求都是 `InvalidInferenceResultError`（响应只有 usage、没有内容），占比 < 0.06%。
- d4 每个点的网卡重传和 ACK 超时都是 0。Mooncake 日志里的 "transfer failed" 都是客户端主动取消（AbortReq），不是 RDMA 失败。
- 只有 C64 K5 / K3 是同机对比。C80 K3 和 400k C64 第一次都排在基线的同一台机器上，被我的看门狗误杀（解析进度时没处理千分位逗号）；
  重跑时原机器已被别人占用，换了机器。
- 吞吐到 C80 就饱和：C96 只多 0.4%，TTFT p90 从 9 s 涨到 23 s，进不了 Pareto 前沿。

K3 在 stock d4 上没有收益，可能的原因（都没有单独验证）：

1. C64 起 KV 用量就有 99–100%，每个 decode rank 的 KV 在 0.92 下固定约 300 万 token，吞吐卡在能同时容纳多少请求上；K3 单步变快，
   但每个请求占的 KV 不变。原报告里 C96 +4.8% 是在 Infera 完整栈（KF kernel、custom AR、FP8 draft）上测的。
2. stock 镜像的 Triton DSA sparse MLA decode kernel 在一个 rank 验证超过 64 行时换成更慢的 split-dim kernel。C64 每个 rank 约 16 个请求：
   K3 验证 16 × 4 = 64 行，刚好不换；K5 是 16 × 6 = 96 行，要换。C80 每个 rank 约 20 个请求，K3 也有 80 行，两者都换。
   这和 C64 有 +1.2%、C80 没有的现象一致。

## 3. 2P1D 与 1P1D

### 3.1 起栈诊断（只起栈加 smoke，不计分）

| 配置 | 机器 | 结果 | decode0 的 Mooncake 报错：Notification QP 初始化失败 / `-302 ERR_MEMORY` / modify QP to RTR·RTS `Invalid argument` |
|---|---|---|---|
| 2P1D 原样 | v3-238 + v3-252 | prefill1 没起来（`ibv_reg_mr` 失败 67 次）；prefill0 也有 744 / 1,930 / 604 | 618 / 626 / 606 |
| 2P1D + `MC_RDMA_NOTIFY_ENABLED=0` | 同上 | 正常 | 0 / 0 / 0 |
| 1P1D 原样 | v3-238 + v3-252 | 900 s 内 worker 没注册到 router | 968 / 976 / 956 |
| 1P1D + `MC_RDMA_NOTIFY_ENABLED=0` | v3-027 + v3-238 | 正常 | 0 / 0 / 0 |

- `748af1a5` 的 `MC_RDMA_NOTIFY_ENABLED` 默认 true：每张网卡建通知 CQ，每个连接多建 1 个 QP 和 2 × 16 MiB MR，decode 网卡的资源被耗尽。
  缓冲区大小是写死的常量（`kNotifySlots = 256` × `kNotifySlotBytes = 64 KiB`），`MC_RDMA_NOTIFY_RECV_COUNT` /
  `MC_RDMA_NOTIFY_BUFFER_SIZE` 管的是另一条通道，调不小，只能整个关掉。
- SGLang 的 PD 通知走 ZMQ，`transfer_engine.py` 不调用 Mooncake 的通知接口，关掉没有功能影响。和 #5138 说明里在 AUS 上查到的根因一致
  （AUS 上加这个设置后 2P1D fast 33,554 tok/s/GPU、0 出错）。
- PR 的 sweep 里，1P1D 原样在 `mi355x-amds` 上 C32 / C48 / C88 都过了，2P1D C176 和它的 eval 都失败。

### 3.2 不带补丁的 2P1D C176 K5（notify0），不算结果

v3-240（prefill）+ v3-193（decode）。计分到第 23 分钟时，4,218 个完成的请求里有 64 个出错（1.5%），TTFT p95 138 s、p99 324 s；
prefill 节点网卡 93.8 亿个重传包、201 万次 ACK 超时；09:20 prefill1 因 PP 级间 NCCL RECV 超时被 SGLang watchdog 中止。
prefill0 的日志被网卡报错（`ionic_comp_msn: wqe is not posted`、`Failed to poll CQ`）刷到 11.4 GB。
crsuse2 的跨机丢帧之前已知，#4540 / #4541 就是为它做的，这个点本不该跑。

| interactivity p50 / p90 | 47.9 / 43.2 | | — / 43.2 |
| TTFT p50 / p90 | 4.35 / 19.49 s | | |
| 出错 / 计分请求 | 7 / 16,187 | | |
| prefill 节点网卡：发送 / 重传包 / ACK 超时 | 174 TB / 133.8 亿 / 351 万 | | |
| Mooncake 报错 | 0 | | |
| decode 最少剩余显存 | 7.9 GiB | | |
| 预热（1,953 个请求） | 1,371 s 完成 | 两次卡死，没完成 | |

K3 的预热进度见 [`results/2p1d-mc-k3-c176-warmup.txt`](crusoe-ab-20261121/results/2p1d-mc-k3-c176-warmup.txt)：

- 16:27 开始，到 1,200 s 时返回 1,023 个（K5 在 1,371 s 已全部完成）。
- 16:47 – 17:09 返回数停在 1,023，164 个请求在途；17:14 起又停在 1,250–1,252，88 个在途。
- 17:29 被 GPU 利用率看门狗（连续 40 分钟低于 50%）取消。我自己的看门狗 17:08 想停掉客户端，但没进得了节点（第 5 节）。

原因没有确认：作业被取消时 worker 容器被删，日志没有保存下来。推测是 KV 传输卡在重传里，而 recipe 的
`SGLANG_DISAGGREGATION_WAITING_TIMEOUT=1800` 让请求最多等 30 分钟才判超时，期间 GPU 空转。同一对机器上 K5 预热没有卡住，
所以也不能排除和 K3 有关。

结论：本集群上 2P1D 只拿到 K5 一个点，K3 对比放弃。如果还要做，应放到 AUS 上（没有跨机丢帧问题）。

## 4. decode 显存与 mem 0.95

| 形状 | K | verify graph（每 rank） | 跑满 3600 s 时 decode 最少剩余 |
|---|---|---|---|
| d4（TP4/DP4） | K5 | 10.55 GB | C64 6.4 GiB，C80 2.8 GiB |
| d4 | K3 | 7.02 GB | C64 12.0 GiB，C80 11.5 GiB，C96 11.2 GiB |
| 2P1D decode（TP8/DP8） | K5 | 6.89 GB | C176 7.9 GiB |
| 2P1D decode | K3 | 5.77 GB | 没跑完 |

- 剩余显存随运行时间下降：d4 C80 K5 在 fast 模式（1200 s）时剩 5.8 GiB，3600 s 时剩 2.8 GiB。
- 0.92 → 0.95 要多占 0.03 × 288 GiB ≈ 8.6 GiB：
  - K5：d4 只剩 2.8 GiB，连 0.93 都开不了；2P1D 剩 7.9 GiB，开不到 0.95；
  - d4 K3 开到 0.95 后约剩 3 GiB，和 K5 在 0.92 下一样紧，换来每 rank KV 约 +7%（135 → 144 GB；Infera 栈上 0.93 → 0.95 实测 +1.1%），
    不值得冒 CI 上 OOM 的风险；
  - 2P1D K3 的 graph 只比 K5 省 1.1 GB，开到 0.95 只剩约 0.4 GiB，同样不够。
- 这也回答了原报告为什么只在 override 里给 2P1D 写 0.95、而不放进 base：AUS 上 K5 0.95 在 graph capture 后只剩 2.1 GB（K3 6.0 GB），
  KV 用满后还会再涨 3.6–4.9 GB，#235 的 K5 C88 3/3 中止。stock 镜像上 0.92 的余量本来就薄，0.95 在哪个形状上都不合适。

## 5. 过程记录与教训

本次共用约 25 个 8 卡节点小时（约 200 GPU 小时）。主要浪费：

- 看门狗没处理千分位逗号，误杀两个有效点（d4-k3 C80、d4-w400k C64），重跑多用约 3 个节点小时，而且重跑没能排在同一台机器上。
- 不带补丁的 2P1D（3.2 节）：2 台 × 1.6 h。
- 补丁生效检查最初查的是日志里的配置行，而 Mooncake 不把配置打到容器输出，两个带补丁的点起栈后被误判失败（2 台 × 20 分钟）；
  当时没挂监控，3 个多小时后才发现。改为检查 `engine.so` 里的变量名。
- K3 2P1D 卡死（3.3 节）：2 台约 1 小时低利用率。

spur 上要注意的：

- 同一作业在每台机器上只能有一个 overlap 交互会话。作业里挂了常驻的清理守护步骤后，登录节点上的看门狗再也进不了这台机器，
  停不了卡住的客户端。卡死检测（应短于 40 分钟）和清理要写在作业脚本自己里面。
- 任何一个作业步骤非零退出，整个作业就结束；远程执行要把退出码包在输出里，步骤本身总是返回 0。
- docker 容器比作业活得久，被抢占或取消都不会删，要自己清；多节点清理作业可能报 `dispatch confirmation failed`，拆成单机作业即可。
- bash 边执行边读脚本，正在跑的脚本不能原地改；新功能另起文件（`point.sh` → `point3.sh`）。
- 容器日志要限长：网卡报错能在 1 小时内刷出 11 GB。`point3.sh` 每个容器只存开头 20 MB 和最后 30 万行。
