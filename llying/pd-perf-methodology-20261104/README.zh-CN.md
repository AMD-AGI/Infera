# PD 推理性能优化的方法论（以 GLM-5.2 AgentX PD 为例，11-04 起草）

从 `../dp-graph-variant-fix-aus-20261103/`（AUS 验证与优化）以及更早的 `../prefill-opt-20261027/`、`../best-4p4-51k-20261103/`、
`../2p1d-aus-v0521-20261019/` 中提炼。目的是让同一套做法能迁移到其他模型，每一条都附上这次的实例。后续会按这个主题继续深入。

## 1. 原则

1. **开跑前写下预测和判据**，跑完照判据判定，不事后改口径。例子：E10 同对基线上，修法预测至少 +1%，实测 +1.3%；E11 + 修法预测至少 +2%，实测 +5.5%；
   DP 均衡预测吞吐 +1–3%，实测 −0.9%，判"不成立"并找出原因。
2. **一次只改一个变量**，对照放在**同一对节点**上测。节点之间差约 3%，单次测量本身有约 ±1% 的波动。例子：AUS 上的 E10 基线 50,797，crusoe 上是 51,374。
3. **对照组必须先能复现问题**，否则修法组的 0 说明不了什么。例子：A 组限池门禁 2 次共 26 条开头坏或乱码，B 组 600 题 0 条。
4. **判据来自计数，并逐条人读被标记的样本**。计数会误判，比如 `#### 20.00` 被当成答错、第 213 题被误标为乱码。
5. **结论要能复现**：每次部署记录镜像、文件 md5、环境变量和启动日志里的关键行，确认"跑的到底是哪一版"。

## 2. 正确性

| 层次 | 做法 | 能抓到什么 | 实例 |
|---|---|---|---|
| 单元 | 镜像内挂修复文件跑，逐条行为断言 | 逻辑错 | `test_fix.py` 26 项；上游版 11 项 |
| 短 prompt 探测 | GSM8K 200 / 400 / 1,319 题，temperature 0，并发 64；统计正确率、乱码（重复、模板标签）、**开头坏**（首 token 对、紧接乱码） | graph 内 collective 读旧缓冲、开头坏 | `gsm8k_probe.py`、`probe_stats.py` |
| 长上下文 | 16k / 100k 随机填充，捞针 + 长前缀 GSM8K，每条不共享前缀 | 稀疏注意力路径、PP 分块 KV 发送 | `longctx_probe.py` |
| 限池门禁 | prefill 设备池压到 30 万 token / 级，两遍 16k × 128，让驱逐和回载持续发生 | HiCache 写回 / 回载路径 | `recipe-gate.env` |
| 审计 | 调试版 runner 每次回放读一次设备，验证机制的前提（这次是上界不小于真实值、各 rank 选择一致） | 机制本身的假设 | N1a：21,504 次回放 0 违例 |
| 官方 eval | InferenceX lm-eval GSM8K | 提交门槛 | ≥ 0.96 |
| **参照组** | 同一批题跑**去掉全部优化的原版框架**，再加官方另一种精度的权重，**原版再重跑一次量噪声** | 错题到底是模型本身还是栈造成的 | 原版重跑一次 0.973 → 0.966；我们的栈与原版 + 官方 FP8 互有对错各 12 题，分不出差别 |
| **真实接受长度** | decode 日志 `accept len`，在**真实接受率**下读 | 草稿路径的 bug：计分用模拟接受率，这类问题完全看不出来 | PTPC bug：1.2，修好后 3.6 |

要点：temperature 0 也不是确定性的。batch 组成不同会改变归约顺序，临界题就会翻转。所以"错题集合不同"要用"同一配置重跑一次"的差异来衡量，不能当成 bug。

## 3. 性能：三层 roofline

### 3.1 周期结构（基准本身的天花板）

闭环回放下：每卡吞吐 ∝ 并发 lane 数 /（卡数 × lane 周期），lane 周期 = trace 自带的间隔 + TTFT + decode。先拆出这三者的占比。
GLM-5.2 AgentX 上约为 50% / 16% / 34%，所以服务端时间全部归零也只有约 2 倍，各部分的弹性是 decode −10% ≈ +3.4%、TTFT −14% ≈ +0.7%（受限一侧不同，弹性就不同）。
另外，约 2/3 的请求是并行的子 agent，不在关键路径上。

### 3.2 容量（决定能加多少并发）

- decode KV 池：使用率均值、≥ 0.97 的时间占比、预分配等待数。4+4 下平均 0.82、等待 2.6–3.7；TP8 下 KV 多 32%，等待降到 0.2。
- prefill：有排队的时间占比、排队长度、未命中 token 的吞吐。4+4 是 66%，2P1D 是 92%，后者就是 prefill 受限。
- 前缀缓存命中率：多个实例之间会重复缓存。2P1D 两个实例合计多算约 8.5%。
- 判断瓶颈在哪一侧：一侧排队、另一侧有余量。`analyze_pd_logs.py` 一次给出两侧的指标。

### 3.3 每步硬件效率

1. **步长线性拟合**（`decode_step_fit.py`，DP 锁步下由最忙的 rank 决定）：`步长 = a + b·最忙 rank 请求数 + c·最忙 rank 上下文 + …`。
   - 截距 a 是固定开销；b / c 是"1 个请求相当于多少 token"，也就是 DP 均衡权重的理论值，这次是 42 万。
2. **带宽下限**：每步要读的字节数（主模型 1 次 + 草稿每步 1 次）÷ 可达带宽，和截距比较。
   - TP4：140 GB → 21.6 ms，截距 21.3 ms，已经在 roofline 上。
   - TP8：88 GB → 13.6 ms，截距 17.8 ms，还有约 4 ms 的 kernel / 通信空间。
3. **kernel 拆解**：trace 要加 `DEBUG_CLR_GRAPH_PACKET_CAPTURE=0`，否则 graph 内的 kernel 看不到；用 `dtrace_cat.py` 按类别、再按 kernel 名统计。
   每一类都和自己的 roofline 比：MoE 按字节算带宽，MLA 按 FLOPs 算，通信按延迟算。
4. **GPU 空闲**：`dgaps.py`（按下一个 kernel 的归属统计）、`dgap_stacks.py`（空闲期间的阻塞调用和 Python 栈）。
   **注意 profile 启动后的第一步有几十 ms 的采集开销**，要去掉 trace 开头约 60 ms 再统计（这次因此误判过一次，已更正）。
5. **逐请求延迟**：`ttft_by_len.py` 按未命中 token 分档看 TTFT 的 p50 / p99 / 最大值，用来发现调度饿死。这次 SPF 下超过 128K 的请求最长等了 1,524 s。

## 4. 优化项的排序方法

- 每一项先给出"每步省多少 → 端到端多少"（用 3.1 的弹性），再看前提和代价。小于 1% 的放后面，小于 0.5% 的不做（例：graph 间空闲只剩 0.5 ms）。
- decode 变快后，瓶颈会转到 prefill（4+4 → 2P1D 就是这样），所以各项收益不能直接相加。
- 不改精度的先做；改精度的要过 eval，并且要事先核对规则（见第 6 节）。
- kernel 优化要确认在**目标并行形状**下真的生效：KF 的 MoE 只为 TP4 的 i512 调过，到 TP8 的 i256 就回退了。看日志里的决策行和 trace 里的 kernel 名。

## 5. 实验流程（工程）

- 节点用 holder 作业持有，实验写成队列项（`holder_item.sh`、`opt_item*.sh`）。分配剩余时间不够的不启动，换节点后自动探测 IP、检查镜像（缺了就从 tar 加载）。
- 先门禁、后计分：门禁不干净，计分项自动跳过（队列项里写死判据）。
- 巡检：每 10 分钟查作业状态、日志新行、失败关键字和"无进展"，有事就唤醒；每小时自动提交一次结果。
- 计分期间节点上不跑任何别的东西。只有正确性门禁时，才在空闲的 GPU 上做参照实验或单元测试。
- 记录：README（方法与事先预测）、RESULT（结果与分析，错了就写"更正"）、STATUS（时间线）、`results/`（原始数据）。节点本地盘上的日志要及时同步到共享盘。

## 6. 提交合规（InferenceX）

逐项核对，再分成"提交线"和"探索线"两套配置：

| 规则 | 这次碰到的 |
|---|---|
| 镜像原样运行，不打引擎补丁（含 monkey-patching、覆盖容器文件） | KF overlay（`sitecustomize` 运行时替换）、挂载的修复文件、prefill 补丁、GEMM CSV |
| **草稿按发布精度运行**（Check 13，对草稿做在线或离线量化一律 FAIL） | PTPC（FP8 草稿 MoE）不能用 |
| 不减少模型 FLOPs | `index_share_for_mtp_iteration` 要先查 checkpoint 默认值（本模型默认就是 true） |
| 推测解码用 golden AL 的模拟接受率 | 计分看不到草稿质量，所以要另外测真实接受率 |
| 配置先进 SGLang cookbook，组件先合入上游 | 7 个 OPEN 的 SGLang PR、Infera 发版 |

## 7. 迁移到新模型的清单

1. 原版框架 + 官方权重的正确性和吞吐基线，再重跑一次量噪声。
2. 拆 lane 周期；读出两侧的容量指标（KV 池、prefill 排队、命中率）。
3. 步长拟合 + 带宽下限，判断 decode 的固定开销离 roofline 还有多远。
4. 带 packet capture 关的 trace：按类别拆解，每一类对照自己的 roofline。
5. 真实接受率（如有 MTP / 草稿）。
6. 对照组先复现问题，再验证修法；先门禁、后计分；开跑前写预测。
7. 每个优化项先核对规则和上游状态，再决定放在提交线还是探索线。

## 8. 这次的教训

- 计分用模拟接受率，草稿路径坏了也看不出来（PTPC 的 bug 存在了一周以上）。**每个配置都要读一次真实接受长度**。
- 参数不要照搬别的配置上的经验值：DP 均衡的 100 万权重来自 1P1D C88，在本配置上应该是 42 万。
- 采集方法本身有开销：profile 起始的那一步。
- 不要只盯着一个结果文件：巡检只看 `verify.out`，就会在计分期间每小时误报一次"无进展"。
- 引用别人的结论之前先回到原文：ATOM recipe 并没有点名排除 MTP 层；"低精度允许"这条对草稿不成立。
