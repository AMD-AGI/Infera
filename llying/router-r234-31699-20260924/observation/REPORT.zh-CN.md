# R2/R3 旁路正确性观察结果

本轮只作为正确性观察，不作为 4K 性能基线，也不推导吞吐收益。实际 P/D chunk 为 8192/4096，后续性能目标已更正为 4096/4096，须用户确认配置后才能运行。

## 结果

9 项检查通过，详见 [correctness.json](correctness.json)。

| 项目 | 结果 |
|---|---|
| R2 决策 | 1,139 次，824 次建议不同于原策略（72.34%） |
| R3 决策 | 1,139 次，0 次建议不同于原策略 |
| Shadow 是否改变实际派单 | 0 次；实际选择全部等于原策略选择 |
| R2 输入及 rank 对账 | 1,139 次 Router 决策与 1,139 条引擎记录的 rank＋input length 多重集合一致 |
| R2 候选及建议 | 每次 8 个候选，输入需求已知；建议均为记录成本的最小值 |
| R2 并发记账 | 128、1,118、3,318、6,618 tokens 四条请求依次加入对应 rank，下一次派单看到前面的记账 |
| R2 完成清理 | 补充探针前后八个 D rank 均无残留输入账本 |
| R3 GPU 命中 | 重复请求预测与实际均为 6,592 tokens，P rank 5 一致 |
| R3 host 前缀 | 3 次候选有仅 host 命中，最大 197 blocks＝12,608 tokens；没有改变最终建议 |
| R3 事件和公式 | 已收到真实 GPU/CPU_PINNED 事件；观察到的 unknown/rejected store 为 0；所选候选评分公式核对通过 |

输入长度的全量核对是 rank＋长度的集合对账，不冒充每个请求都有独立的 Router request-ID 关联。7 条受控请求则按请求 ID、时间窗口和长度进行了关联。四条并发请求全部选 rank 后，距最早客户端完成仍有约 1.09 秒，账本累加检查不混入完成扣减。

## 七条受控请求是什么

在原有服务上发普通 API 请求，没有重启、没有修改策略：两条空账本探针，四条不同长度的并发请求，一条重复请求。P/D scheduler PID 与 startup_time 始终不变，证据见 [engine-identity.json](engine-identity.json)。

## 能得出与不能得出的结论

R2 的输入需求、记账生命周期和旁路建议在本轮检查中符合实现预期，且对本次工作负载有明显的选 rank 差异。差异比例不是收益比例。

R3 的事件接入、GPU 命中、分层查询和评分检查通过，但本轮真实引擎请求的 cached_host 均为 0。仅 host 候选没有胜过原选择，故不能声称已验证主动选用 host 后的回读路径，更不能声称有性能提升。

本轮包括基础 smoke、884 条预热、随后被用户限缩范围而终止的短段发压，以及7条受控请求。完整3600秒窗口没有完成，已有阶段吞吐不用于性能结论。

## 当前状态

长发压、采样和自动后续阶段均已停止，模型服务保持空闲，未重启。用户的 allocation 保留，原有抢占清理 watchdog 仍在。后续性能必须先确认完整配置；入口已加批准配置与二进制哈希检查，旧8K自动任务禁止直接恢复。

## R3 为什么改了公式却没有改选择

R3 on 时，原负载项 L 不变，仅替换缓存项。本轮文本请求的权重为 GPU 20、host 10（20×0.5），分数越低越优先：

```text
原策略：L - 20 × 原单层目录命中 blocks
R3：   L - 20 × GPU 命中 blocks - 10 × host 延伸 blocks
```

同一前缀同时在 GPU/host 时不重复加分。只有超出 GPU 连续命中的 host 前缀才算 host 延伸。

实际 decision 2205：

| 候选 | GPU hits | host 延伸 hits | 原分数 | R3 分数 |
|---|---:|---:|---:|---:|
| P rank 4 | 0 | 197 | 0.0245 | -1969.9755 |
| P rank 5 | 420 | 0 | -5903.8104 | -5903.8104 |

R3 明确改善了 rank 4 的分数，但 rank 5 仍更低，所以两者都选 rank 5。这是正常的策略行为，不能为展示新功能而强行选 host。对性能价值而言，本轮没有改变派单，尚无 R3 增益的证据；也不能把这个短的8K样本外推成所有4K工作负载都无收益。
