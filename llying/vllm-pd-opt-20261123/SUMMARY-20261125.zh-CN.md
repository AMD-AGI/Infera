分支 `dev/pd_opt/vllm_glm52_agentx`，MI355X 单节点 8 卡（prefill PP4 × TP1 在 GPU 0–3，decode DP4 在 GPU 4–7），AgentX C104、3600 s。

## 1. 结论

- **推荐配置（a25 配置）**：a8 配置 + Triton decode top-k 第三版 + prefill `--max-num-batched-tokens 4096 --long-prefill-token-threshold 2048`。
- **成对结果**：v3-037 上两次 56,342 / 56,448（平均 **56,395**），比同节点 a8 配置 53,610 **+5.2%**；第二台正常节点 v3-239 上 56,280 对 53,629 **+4.9%**。
- **对 sglang P4D4（53,351）**：吞吐 **+5.7%**，交互 p50 持平、p90 更好，ITL p90 更好，TTFT 均值约为其一半：

  | | a25 配置（a28 A，v3-037） | a8 配置（a19 A，v3-037） | sglang P4D4 C104 |
  |---|---|---|---|
  | tok/s/GPU | **56,448** | 53,610 | 53,351 |
  | req/s | 3.662 | 3.542 | 3.469 |
  | 交互 p50 / p90 | **70.0 / 64.9** | 65.0 / 60.7 | 69.9 / 60.8 |
  | ITL p50 / p90（ms） | **14.3 / 15.4** | 15.4 / 16.5 | 14.3 / 16.4 |
  | TTFT p50 / p90 / 均值（s） | **2.01 / 5.22 / 2.81** | 2.50 / 6.85 / 3.87 | 4.20 / 9.23 / 5.65 |

- 同节点、无 prefill 停顿时轮间波动约 0.2%（a25 配置、a27 配置各两次）。
- Triton top-k 的正确性问题已关闭：门禁真实接受"低 1.2%"是统计假象；生产 logits 上逐行影子比对 716 万行，**0 个不精确的行**。

## 3. 各项改动的贡献（成对比较，各单次）

| 改动 | 比较 | 结果 | 机制 |
|---|---|---|---|
| Triton decode top-k 第三版（替换 aiter 每行一个 block 的 top-k） | a18，v3-231，对 vLLM 自带 top-k | +1.4% | decode 步中位 46 → 42 ms、ITL −1.0 ms；单独用时 prefill 排队 +0.12 s，抵掉一半 |
| prefill `--long-prefill-token-threshold 4096` | a19，v3-037，对 a8 配置 | +1.6% | prefill 准入排队 1.15 → 0.70 s；超长 prefill 不再饿死其他请求 |

| **阈值 4096 + Triton top-k** | a22，v3-037 | **+4.5%** | 两者叠加多于各自之和：阈值吃掉 decode 变快带来的 prefill 排队，KV 周转更快（KV 满的时间 30% → 24%） |

## 4. 主要发现

1. **门禁的真实接受不能直接比**。即使 temperature 0，门禁也不逐位可复现：每次有 1–4 个回答随机失控到 16k 上限，草稿在这些回答上接受约 3.97，一个就占约 10% 的 token。
   之前"Triton top-k 低 1.2%"就是不开时每次 2 个、开时每次 1 个造成的。去掉失控回答后每 token 接受：不开 3.366，Triton 3.358（15 次门禁）。
   生产 logits 上逐行影子比对（`VPD_TOPK_SHADOW`，录进 CUDA graph）：Triton 0 个不精确的行；三种实现只在并列元素的取舍上不同，aiter 与 vLLM 自带之间的差别最多。
2. **TTFT 拆解更正**：之前把 decode 的 Deferred 当成了 prefill 的。prefill 段的大头是等准入（约 0.79 s），CPU 层读回只有约 0.21 s；阈值类改动有效与此一致。
3. **负载里固定的超长未命中 prefill**（第 8 / 21 / 42 min：66 万 / 54 万 / 95 万 token）：不开阈值时 prefill 停 20–90 s，小请求等约 65 s，所在 300 s 窗口吞吐低 20–25%，
   约占全程 1%。阈值 4096 / 2048 基本消掉；a22 / a25 / a27 / a28 全程 0 次停顿。
4. **节点差异**：v3-071 decode 慢约 30%（读 KV 的 kernel 慢一倍，频率 / 功率正常），在那里 Triton top-k 比 aiter 还慢，成对 −1.7%，已排除；
   v3-111 正常，但 a24 的 B 侧碰到一次偶发的 91 s prefill 停顿，成对只 +0.1%（停顿前 +3.2%），不作结论。成对比较只在正常节点、无停顿时才可信。

## 6. 现在的瓶颈（推荐配置，a28 A）

- **周期**：吞吐 ∝ 104 条通道 / 通道周期。req/s 3.542 → 3.662（+3.4%），TTFT 均值 −1.06 s，交互 p50 65 → 70。剩下的周期里 decode 约占一半多，客户端间隔（改不了）约占三分之一，TTFT 约 10%。
- **TTFT 2.81 s**（10 s 计数 + Little 定律）：

  | 段 | 均值 |
  |---|---|
  | prefill 引擎（排队 0.65 + 计算 / PP4 流水线 0.69 + 其他） | 1.58 s |
  | decode：KV 拉取中（Mooncake） | 约 0.48 s |
  | decode：等开始拉取（等 KV 空间） | 约 0.17 s |
  | 其余（路由、首步、网络） | 约 0.3–0.5 s |

- **KV 拉取为什么慢**：每个请求 4 段 × 1.44 GB（每个 PP 级一段），都在 decode GPU 那块网卡上 RDMA 回环（crusoe 上 ionic_k 只通 ionic_k）；
  每段约 3.3 万个描述符（一个 64 token 的块 × 一层约 44 KB），约 8.3 GB/s、平均 203 ms、p90 462 ms。4 段合起来约 33 GB/s，接近单网卡回环的上限，所以调 Mooncake 的线程 / QP 意义不大。
- **decode 步 42 ms**（a8 trace 拆解当时是 48 ms：MoE 17、dense 11、通信 6.7、top-k 3.2、稀疏 MLA 2.9、indexer 1.7、norm 1.3）：top-k 已降到约 1.5 ms；MoE 在带宽上限；
  DP 不均约 1.2 ms / 步（现在主要是请求数不均，调均衡权重估计只能省约 0.2 ms）。

## 7. 后续需要改代码的方向（估计收益，按"TTFT 每秒约 3%"、"步长变化 × 0.3–0.6"）

1. **KV 传输路径（约 +1%）**：(a) 查清 HIP IPC 路径的 HIP 错误 209（预热时、还没到传输），容器只看见 4 块 GPU 时的 peer access 也要验证；
   (b) decode / prefill 分配连续块、让 Mooncake 合并描述符；(c) prefill 按分块边算边推 KV，把传输藏到计算后面。
2. **prefill 调度（约 0.5–1%）**：超长 prefill 只用剩下的预算（按上下文长度限分块），让带着它的步不拖慢其他请求；小请求优先（SPF）；PP4 流水线延迟。
3. **decode 侧**：按会话把下一轮路由到持有上一轮 KV 的 rank（decode 前缀命中现在约 10%，能减小拉取量，要和 DP 均衡权衡）；
   Triton top-k 在异常节点上会比 aiter 慢，可以加运行时回退。
4. **上游**：Triton top-k（精确性证据已有）、阈值 / 分块的结论、门禁接受的拟合方法，先写草稿，不对外发。
