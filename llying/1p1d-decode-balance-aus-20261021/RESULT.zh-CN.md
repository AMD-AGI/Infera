# 1P1D C88 decode 按请求数均衡：结果与分析

> 部署与方法见 `README.zh-CN.md`，时间线见 `operations/STATUS.zh-CN.md`。吞吐按 12 张 GPU 计（AgentX 自己算的 per_gpu）。

## 0. 摘要（持续更新）

- **A/B 结论（a9，同一部署 n04-25 + n06-33，prefill 带 EAGLE 参数，1P1D C88，1800 s，AgentX 正式汇总）**：decode 按请求数均衡
  （`--decode-request-weight 1000000`）对比现有 R2（权重 0）：**interactivity p90 55.7 → 79.6（+43%）**、p50 75.8 → 86.5（+14%）、
  吞吐 26,462 → 27,186 tok/s/GPU（+2.7%）；代价是 TTFT 均值 8.3 → 9.6 s（p50 5.5 → 5.6）。机制：最忙 rank 在跑中位 / p90 8 / 11 → 6 / 8，
  步长尾部（最忙 ≥ 10 时 52–69 ms 的步）消失。
- 叠加 prefill MTP 后，相对 PR 210 的 C88（crsuse2，27,453 @ p90 42.8）为 27,186 @ 79.6。AUS 上 PR 210 原样配置的严格复现还没跑成
  （四次分配都被抢占打断），排在下一次分配第一位，之后按相反顺序重复 A/B。
- **第一个结果（`ka8-pmtp-w180k`：prefill 带 EAGLE 参数 + router 权重 180,000，1P1D C88，1800 s）：27,577 tok/s/GPU，interactivity
  p50 / p90 = 85.0 / 74.4**；PR 210 的 1P1D C88（crsuse2，prefill 无 MTP，router 无权重）为 27,453 @ 49.1 / 42.8。吞吐相同（prefill 是瓶颈），
  p90 交互 +74%。这一轮在测量窗口结束 2 秒后被抢占，结果由 AIPerf 的逐请求记录算出（§2）。
- **对照 `ka9-pmtp-w0`（prefill 带 MTP，router 权重 0 = PR 210 的 R2）：26,462 @ 75.8 / 55.7**。所以相对 PR 210 的 42.8：
  **prefill 带 MTP 贡献 p90 42.8 → 55.7（+30%），decode 按请求数均衡（权重 180,000）再贡献 55.7 → 74.4（+34%）**，吞吐不降。
  均衡的机制：最忙 rank 在跑数中位 / p90 从 8 / 11 降到 6 / 8，而两对节点同等最忙负载下每步耗时逐档相同。
- **同部署严格 A/B（`ka9-pmtp-w0` 对 `ka9-pmtp-w1m`，权重 1,000,000）：p90 交互 55.7 → 79.6（+43%），吞吐 26,462 → 27,186（+2.7%），
  TTFT 均值 +15%、p90 +8%**（代价，原因待查）。相对 PR 210 的 1P1D C88（27,453 @ 42.8）：同等吞吐下 p90 交互 +86%。
- v0.5.22 C88 上最忙 rank 多 1 个请求 ≈ 多 105 万 token（v0.5.21 C176 为 17–19 万），180,000 低估了请求数；B 组请求数最忙 / 均值仍为
  1.47 / 1.82。下一组用 1,000,000。
- PR 210 的 kit 从分支本身以 `PREFILL_WORKERS=1` 在 AUS 上起栈成功（11 分钟，router 列出 1 prefill + 1 decode），只需站点环境变量；
  镜像在 AUS 上原样构建成功（约 7 分钟）。分配极短（51 / 31 / 62 分钟，两天内 9 次抢占），A/B 改为每组 1800 s。

## 1. 为什么 R2 下 decode 仍不均衡（实验前的分析）

DP attention 下 8 个 decode rank 每步同步，所有请求在同一步里经历同一个步长，所以**交互速度的 p90 对应的是负载高峰时刻的步长**，
即最忙 rank 处在高位的时刻。AUS 2P1D C176 两轮 decode 日志（v0.5.21，R2 开，每 rank 每 40 步一行 `#running-req` / `#token`，按 3 s 分箱）
拟合（`scripts/decode_step_fit.py`）：

| 轮次 | 每步 ms = | R² | 最忙 rank 1 个请求 ≈ token |
|---|---|---|---|
| a5-pmtp C176 | 23.2 + 0.83·最忙请求 + 4.85·最忙上下文(M) + 0.169·总请求 + 0.238·总上下文(M) | 0.934 | 170,743 |
| a4-spf2 C176 | 22.9 + 0.80·最忙请求 + 4.19·最忙上下文(M) + 0.192·总请求 + 0.250·总上下文(M) | 0.941 | 192,255 |

同一窗口里每 rank 的均衡情况（a5-pmtp）：

| | 均值 | 最忙 / 均值 中位 | 最忙 / 均值 p90 |
|---|---|---|---|
| 在跑请求 / rank | 10.27（最忙中位 15、p90 19） | 1.42 | 1.67 |
| 上下文 token / rank | — | 1.08 | 1.17 |

- **R2 把 token 均衡得很好，请求数没有**：R2 的代价只有"已预约输入 token + 本请求 token"，一个 rank 可以用几个短请求填满别人一个长请求的量。
- 步长对最忙 rank 的请求数和上下文都敏感：多 1 个请求 ≈ 多 17–19 万 token。所以按"token + 权重 × 请求数"打分、权重 ≈ 18 万，
  就是让最忙 rank 的预测耗时最小的线性代价；Dynamo 的 `decode_blocks + w × active_requests` 是同一形式，GB300 的 w = 8192 块
  （请求数主导）。
- 这一组系数下，C176 若请求数完全均衡（最忙 15 → 10）约省 4 ms / 步（−6%）；C88 的相对不均衡更大（crsuse2 v0.5.22：均值 6.7、
  最忙中位 11 / p90 16），收益取决于 v0.5.22 上的系数，在复现轮日志上重拟。

**同部署 A/B：w1m 对 w0**（同一对节点、同一组引擎，只换 router 权重，每轮前 flush，两轮 flush 核对都通过）：p90 交互 55.7 → 79.6（**+43%**），
p50 75.8 → 86.5（+14%），ITL p90 18.0 → 12.6 ms（−30%），吞吐 +2.7%；**TTFT 变差**：p50 +3%、p90 +8%、均值 8.29 → 9.50 s（+15%）。
最忙 rank 在跑数中位 / p90 8 / 11 → 6 / 8，w1m 的最忙 rank 再没超过 9（w0 常到 10–14）；代价是上下文均衡变差（最忙 / 均值 1.23 / 1.44 →
1.52 / 1.84）。TTFT 变差的可能原因：KV 更多地堆在少数 rank 上，按目的 rank 走的 KV 传输与 decode 侧预分配排队（待查）。
两轮共 24 次 "Decode transfer failed" 全是测量阶段结束时 AIPerf 取消在途请求（`Aborted by AbortReq`）。

`ka9-pmtp-w0` 有 AgentX 官方汇总；同一份逐请求记录用 `records_summary.py` 算出 26,620 / 75.6 / 55.7 / 5.44 / 11.11，吞吐差 0.6%、
p90 交互完全一致——`ka8-pmtp-w180k` 由记录算出的数字可信（官方口径下吞吐约低 0.6%）。

**w180k 对 w0**（不同节点对；两对节点"按最忙 rank 在跑数分组的每步耗时"逐档相同：@6 40.9 / 40.5、@7 42.1 / 42.2、@8 43.4 / 43.6、
@9 49.2 / 49.5 ms，栈的快慢一致，差别只在负载分布）：p90 交互 74.4 对 55.7（**+34%**），p50 85.0 对 75.6（+12%），ITL p90 13.4 对 18.0 ms
（−26%），TTFT 不变，吞吐 +3.6%（含节点差异）。w0 的最忙 rank 常到 9–14（@9 1,079、@10 847、@11 499、@12 222 个分箱），w180k 几乎不超过 9
（@9 453、@10 137）。

`ka8-pmtp-w180k` 的 AgentX 在测量窗口结束（00:36:13）后 2 秒被抢占，AIPerf 没写汇总；数字由 `scripts/records_summary.py` 从
`profile_export.jsonl`（随请求完成追加，5,234 个测量期请求）按 InferenceX 的定义算出（interactivity = 1 / 逐请求 full-response ITL 的
分位数；吞吐 = 窗口内完成请求的输入 + 输出 token ÷ 1800 s ÷ 12 卡），与 AIPerf 被杀前最后一次实时统计一致（TTFT p50 5.446 s、rps 2.9）。
prefill flush 核对通过（4 / 4 rank 的第一个 batch `cached=0`）。

**窗口长度（1800 s 对 3600 s）的影响**：AgentX 的每条 lane 顺序回放一个会话，越往后的轮次上下文越长；1800 s 窗口只走到前半段。
同一轮 3600 s 的逐请求记录里（AUS 2P1D C176）：

| 同一轮 | tok/s/GPU | rps | 每请求 token | intvty p90 |

2.867 req/s 反而比 PR 210 的 2.769 高 3.5%，每请求 token 110,770 比 118,953 少 6.9%；按 6.6% 换算到 3600 s 约 28,200。
