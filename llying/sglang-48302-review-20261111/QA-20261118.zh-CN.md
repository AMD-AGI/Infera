## 1. verify 为什么只抓一张图

**结论**：在 verify 模式下，"dense"和"sparse"两张图执行的 kernel 完全相同，抓两张没有任何计算上的收益，反而带来三个问题。PR 让 verify 只抓 sparse 这一张。

**拆开看**：

1. **两张图各是什么。** 启动时，对每个 batch size，runner 先设好标签"dense"录一遍图，再设"sparse"录一遍。录图时 indexer 调 `_should_skip_logits_computation()` 决定这张图里要不要算 logits（`dsa/dsa_indexer.py` 第 1003–1038 行）：
   - **decode / idle 模式**：标签是 dense 就返回 True，这张图里只写 K、跳过 logits 和 top-k（`_forward_cuda_k_only`）；标签是 sparse 就走完整的 indexer。两张图确实不同。
   - **TARGET_VERIFY 模式**：这个函数**不看标签，直接返回 False**（verify 既不算 `is_extend_without_speculative`，也不算 `is_decode_or_idle`，最后一行 `return False`）。所以 verify 的 dense 图和 sparse 图都走完整的 indexer，kernel 序列一模一样。
2. **main 为什么会抓两张。** `create_attention_graph_variants()` 原来不区分录图模式，只要是 HIP 上的 DSA 模型就返回 `DsaGraphVariants`，verify runner 也就跟着录了两张。
3. **抓两张带来的三个问题**：
   - **白白多一倍**的录图时间和图显存。
   - **每步多一次同步。** replay 前要 `select()`，但 verify 路径上没有 host 端的长度镜像（`seq_lens_cpu`），只能走 `forward_batch.seq_lens.max().item()`（`graph_variants.py` 第 58–60 行），每个 verify 步都做一次 GPU→CPU 同步。PD 计分时测到 verify 前的 GPU 空闲从 0.59 ms 降到 0.03 ms，主要就是去掉了这一次。
   - **乱码。** 这是最关键的一点：两张图虽然计算相同，但**用的 buffer 地址不同**。图里的 custom all-reduce、aiter all-gather / reduce-scatter 在录图时登记的是"这张图的输入 buffer 地址"。DP attention 下，如果 rank0 回放 dense 图、rank1 回放 sparse 图，rank0 会去 rank1 的"dense 图 buffer"里读数据，而 rank1 这一步写的是它的 sparse 图 buffer，于是读到的是旧数据。也就是说，**问题出在地址不一致，而不是计算不同**。
4. **PR 的做法**：给 `create_attention_graph_variants()` 加一个 `capture_forward_mode` 参数，非 decode 的录图直接返回 `None`（`graph_variants.py` 第 112–115 行），verify 只录一张图。三个问题一起消失。A/B 里也能看到：main 的每个服务启动时有 4 行 `DSA dual-graph enabled`（每个 rank 的 verify 都录了两张），PR 是 0 行。

## 2. 原来空闲 rank 为什么选 sparse？现在让它也能选 dense，有没有问题

**结论**：原来选 sparse，是因为"没有长度信息时选一定正确的那张"。现在按全局上界选：所有 rank 都不超过 2048 时，空闲 rank 也选 dense，正确性和性能都没有问题，而且这正是修 bug 所必需的。

- **原来的逻辑**（`graph_variants.py` 第 54–63 行）：空闲 rank 没有请求，`seq_lens_cpu` 和 `seq_lens` 都是空的，走到 "No length info: be safe and use the correct-for-all sparse graph"。sparse 对任何长度都正确，所以没有信息时它是保守的选择。
- **这恰恰是 bug 的来源之一**：其他 rank 的序列都短、选了 dense 时，空闲 rank 固定选 sparse，两边回放的图就不一致。
- **正确性**：
  - 空闲 rank 跑的是填充的假数据，输出会被丢弃，它选哪张图都不影响自己的结果。它参与图里的集合通信，只是为了和其他 rank 配对。
  - 只有当全局上界 ≤ 2048，也就是所有 rank 的所有序列都 ≤ 2048 时才会选 dense。这时 dense 对每个 rank 都正确。
  - 所有 rank 都空闲时上界是 0，大家都选 dense，同样一致。
- **性能**：
  - 空闲 rank 选 dense 只会更快（dense 跳过了 logits 计算）。
  - 反过来，有一个 rank 超过 2048 时，原本能用 dense 的短 rank 也要跟着用 sparse，这些 rank 会稍微慢一点。但 DP attention 下所有 rank 每步同步前进，一步的耗时由最慢的 rank 决定，而最慢的正是那个用 sparse 的长序列 rank，所以整步几乎不受影响。
  - 实测：审计中 dense 的占比随负载变化，混入长上下文时只有 0.04%，纯 GSM8K 时是 3.5%–3.7%。A/B 中 PR 的吞吐反而高 1.9%。

## 3. "上界偏小可能悄悄出错"是什么意思？是不是录图时就按长度定好了，设计有缺陷

**结论**：不是。录图时**两张图都录**，并不按长度选；**每一步 replay 之前都会重新选一次**，用的是这一步的长度。"上界偏小会出错"是在说：每步选图时用的长度必须不小于真实的最大长度。PR 保证了这一点，所以这不是设计缺陷，而是一个必须满足、并且已经满足的前提。

- **录图**（启动时一次）：对每个 batch size，dense 图和 sparse 图都录下来。dense 图里固化的是"跳过 logits，直接认为前 2048 个位置全选"的路径；sparse 图里固化的是完整的 indexer。录图时的序列长度不参与选择（见上面引用的代码注释："Graph replay freezes this branch; use the capture variant, not capture-time sequence lengths"）。
- **回放**（每一步）：`replay_prepare()` 每步都调 `_resolve_attention_variant()`，也就是 `select()`，按这一步的最大长度选一张图回放。
- **为什么上界偏小会悄悄出错**：如果这一步实际有一条序列长 3000，但选图时用的长度以为最长只有 1900，就会选到 dense。dense 图不算 logits，那条序列就不会按打分选 top-2048，而是看到一个错误的 KV 子集。不会报错，只是输出质量变差。所以选图用的长度必须是上界：偏大最多慢一点，偏小会出错。
- **PR 怎么保证上界不偏小**（`dp_attn.py` 第 532–552 行）：
  - 有 host 镜像（`seq_lens_cpu`）时，取它的最大值，是精确值；
  - 没有镜像时（开 spec 时 acceptance 还在路上），用"已提交长度 + 2 × 每步最大 token 数"：最多落后一个未处理的步，再加上这一步要写的 token。
  - 各 rank 的上界取最大值后再选图。所以对每个 rank 来说，这个值都不小于 main 原来按本 rank 长度算出的值，**比 main 更保守**。
- **实测**：两次审计共 37,632 次 replay，上界一次都没有小于设备上的真实最大值。
- **残余风险**：如果以后调度器改得让 host 长度落后超过两步，这个假设就会失效。之前的 review 建议过加一个默认关闭的调试断言来兜底，为了保持 PR 小没有加；如果 reviewer 提出来，可以补。

## 4. all-gather 里写死的 13 是做什么的

**结论**：是的，第 13 列（从 0 开始数）就是 PR 新加的那一列：**本 rank 这一步最长 decode 序列的上界**（不完全是 max_seq_len，而是它的上界）。

- 每步开始前的 MLP sync 里，每个 rank 填一行 14 个 int64：
  - 0：token 数；
  - 1：算 logprob 的 token 数；
  - 2：能否用 decode 图；
  - 3：是否有 extend；
  - 4：能否 TBO；
  - 5：forward mode；
  - 6：能否用 prefill 图；
  - 7：prefill 图的最大前缀长度；
  - 8：能否用 draft 图；
  - 9：健康检查；
  - 10：attention pairs；
  - 11：是否在关闭；
  - 12：drain 状态；
  - **13：本 PR 的上界**。
- all-gather 之后，每个 rank 都拿到一张"rank 数 × 14"的表 `tp0_info_cpu`（每个 DP rank 取其 TP0 的那一行）。`tp0_info_cpu[:, 13].max()` 就是所有 rank 上界的最大值，即全局上界（`dp_attn.py` 第 325 行）。它被放到 `ScheduleBatch` / `ForwardBatch` 的 `dp_decode_graph_max_seq_len` 上，交给 `select()` 用。
- "写死"的意思是：列号是字面量 13，和周围代码风格一样（第 0–12 列也都是字面量）。风险在于以后 main 如果在它前面插列，就要跟着改。单测 `test_sync_row_carries_the_bound` 断言新列在最后一列，可以兜住这个问题。这次合并 main 后核对过，仍是 14 列。

## 5. ragged 指什么

**结论**：ragged 是"每行长度不一样"（锯齿状数组）的意思。这里指 **verify 时每个请求的 verify token 数可以不同**，所有 token 紧挨着打包，不再补齐成"batch × 固定宽度"。

- 普通 verify：每个请求固定 `num_draft_tokens` 个 token（GLM-5.2 的 EAGLE 3/1/4 就是每个请求 4 个），形状规整。
- ragged verify：每个请求的长度不同（`RaggedVerifyLayout.verify_lens`），用 `qo_indptr` 这种偏移数组标出每个请求的起止位置（`speculative/ragged_verify.py`），按 token 总数分档录图。
- 只有 DFlash 系列（包括 DSpark）在 `SGLANG_RAGGED_VERIFY_MODE=compact` 时启用（`spec_info.py` 的 `supports_ragged_verify()`）。**GLM-5.2 用的 EAGLE 不涉及。**
- review 里提到它，是因为 DSpark 走 ragged 路径时，空闲 rank 会把 forward mode 改成 `TARGET_VERIFY`，并把长度全设为 1，按本地规则会选上限最小的 variant，是 DSV4.1 那段改动没覆盖到的另一个不一致来源。这部分已经从本 PR 删掉，留给后续 PR。

## 6. aiter 分区桶也必须生效吗？GLM-5.2 是不是只用了 DsaGraphVariants

**结论**：GLM-5.2 只用到了 `DsaGraphVariants`。aiter 分区桶（`SeqLenBucketGraphVariants`）属于 aiter attention 后端，GLM-5.2 用的是 `attention_backend='dsa'`，根本不会创建分区桶。这次 A/B 的 12 个服务日志里都没有分区桶的启动行。

- **分区桶什么时候生效**（`aiter_backend.py` 第 2626–2646 行）：
  - 模型走 aiter attention 后端；
  - 用的是 paged ragged decode；
  - 最大上下文长到分区数 ≥ 128；
  - `SGLANG_AITER_DECODE_PARTITION_BUCKETS`（默认开）。
  
  满足这些条件时，同一个 batch size 会按最长序列落在哪个长度桶，录多张图（分区数不同）。所以它主要影响 ROCm 上走 aiter 后端的非 DSA 长上下文模型。
- **为什么 PR 也改了它**：它和 DSA 的 dense/sparse 是同一类问题。每个 rank 按自己的长度选桶，DP attention 下也会回放不同的图，图里登记了 buffer 的集合通信同样会读到旧数据。顺手按全局上界选，就补上了同一个洞。
- **需要说清楚的一点**：这部分**只有单测，没有端到端测过**（GLM-5.2 跑不到它）。如果 reviewer 要求缩小范围，也可以把它拆到单独的 PR。我倾向于保留：改动只有几行，规则和 DSA 完全相同，而且"上界偏大"对分区桶也只是稍慢、一定正确。

## 8. 是不是只有图里用了 aiter 通信算子才会出问题？要不要加依赖判断或环境变量

**结论**：

- 不是只有 aiter 算子。**ROCm 默认就开着的 custom all-reduce 也会触发。** 这次 A/B 的 P 配置就是镜像默认设置，没有 E11，main 照样乱码 153 条。所以这是 ROCm 上 DSA 模型开 DP attention 时开箱即用就会遇到的问题，不是小众场景。
- 建议**不加**环境变量，也不做"按算子判断"的依赖。

**什么条件下会出问题**（三条同时满足）：

1. 开了 DP attention：各 rank 同步前进，图里有跨 rank 的集合通信。
2. 同一个 batch size 有多张图，而且各 rank 可能选得不一样：HIP 上 DSA 的 dense/sparse，aiter 分区桶，DSV4.1 的 candidate。
3. 图里的集合通信会绑定"这张图自己的 buffer 地址"：至少包括 custom all-reduce（录图结束时 `register_graph_buffers()`，见 `custom_all_reduce.py` 第 183–241 行）和 aiter 的 all-gather / reduce-scatter（E11）。

如果图里只有 RCCL 这类按通信序列配对、不按图登记 buffer 的集合通信，而且两张图的通信序列相同（dense/sparse 只差 indexer 的本地计算），按机理推断不会出错。这个组合（关 custom AR、不用 E11）我们**没有在 main 上做过对照**，属于推断，没有实测。

**为什么不加开关或依赖判断**：

- **代价几乎为零**：已有的 all-gather 里多一个 int64，不加集合通信，不读设备，还顺带去掉了一次 `.item()` 同步，实测是净收益。
- **本来就有天然的范围限制**：只在有 MLP sync（DP attention）时启用，只对有多张图的 variant 起作用；不开 DP attention 时选图规则完全不变。
- **按算子判断很脆弱**：一个 op 最后走 custom AR、quick reduce、aiter 还是 RCCL，取决于 tensor 大小阈值、环境变量和后端选择，而且会随版本变化。判断错了就是悄无声息的乱码，比现在"所有 rank 永远选同一张图"这个简单的不变式风险大得多。
- **默认关闭等于默认带 bug**：用户得先知道有这个开关，才能避开乱码。

如果 reviewer 坚持要一个开关，可以加一个默认开启的总开关，方便排查问题；但不建议默认关闭，也不建议按算子判断。

## 9. E 配置、E11 对 E10 的提升是什么？PR 对性能有没有作用？这次的配置和当时有什么不同

**名词**：

- **E10**：我们 GLM-5.2 AgentX PD 4+4 生产配方的第 10 个实验版本。它是 yihou 的 llr35 栈，加上 prefill 补丁 v3、E1（驱逐余量）、E10（HiCache 备份配额）；decode 端开 custom all-reduce。当时最高 51,374 tok/s/GPU。
- **E11**：在 E10 基础上 decode 端设 `SGLANG_USE_ROCM700A=0`，MoE 的 gather/combine 改走图内的 aiter all-gather / reduce-scatter。每步 decode 快约 3 ms（17 个请求时 45 → 42 ms），但没有本 PR 时乱码严重（200 题 53 条），不能用。
- **这次的 E 配置**：就是"单机版的 E11 设置"，只设了 `SGLANG_USE_ROCM700A=0`，没有 E10 的其他私有组件。P 配置是镜像默认（`=1`）。

**PR 对性能有作用**，分直接和间接两部分：

| 来源 | 当时 PD 计分（AgentX C104，1 小时） | 这次单机 A/B |
|---|---|---|
| 直接：verify 只录一张图，去掉每步一次 `.item()` | E10 → E10 + PR：50,797 → 51,477（+1.3%） | 8 组对比平均 +1.9%，TPOT 一般低 1.8% |
| 间接：让 E11 变得可用 | E10 + PR → E11 + PR：51,477 → 53,609（+4.1%），合计相对 E10 +5.5% | 没有在同一台机器上对比 P 和 E（见下） |

这次 E 固定在 n06-25、P 固定在 n04-33。粗看 PR 的 E 比 P 快约 2%（p1k 3,303 对 3,232，p8k 986 对 963），方向和 E11 的收益一致，但混杂了机器差异，不能当结论。

**这次配置和当时有提升的配置有什么不同**：

| 项 | 当时（PD 计分） | 这次（单机 A/B） |
|---|---|---|
| 部署 | PD 分离：1 个 prefill 节点（TP1 × PP4）+ 1 个 decode 节点（TP4 / DP4 attention），两台机器之间走 RDMA | 单机聚合：prefill 和 decode 在同一组 4 张卡上交替跑 |
| 代码 | v0.5.22 的 Infera 构建，带 KF kernel、调优 GEMM 表、FP8 草稿 MoE、HiCache、prefill 补丁 | 最新 nightly 镜像 + main / PR 的 Python，无任何私有改动；DSA 用 Triton 后端 |
| 负载 | AgentX trace 回放，多轮 agent 对话，长上下文，前缀缓存命中 96%，104 并发，1 小时 | ShareGPT 真实文本截成随机长度：1k/1k @64、8k/1k @32，每组约 3.5 分钟 |
| MTP 接受率 | 模拟接受长度 2.99 | 真实接受，约 3.8–4.0 |
| 指标 | 每卡 tok/s（含输入） | 单服务输出 tok/s 和 TPOT |
| 其他 | `mem-fraction-static 0.95`、`stream-interval 30` | `mem-fraction-static 0.88`，默认 stream interval |

**和上下文的关系**：PR 省下的是每个 verify 步的一次同步和一点调度开销，属于每步固定的时间。

- PD 的 decode 节点上，几乎全是 decode 步，这部分省下的时间占比更直接。
- 单机聚合时，prefill 会穿插在 decode 中间，冲淡一部分收益；但这次请求更短、每步更快，固定开销的占比反而更大。

两边都落在 +1% 到 +2% 左右，方向一致。E11 那 +4.1% 是 PD decode 节点上通信路径换掉带来的，需要在同一台机器上对比 P 和 E 才能复现，这次没有做。
