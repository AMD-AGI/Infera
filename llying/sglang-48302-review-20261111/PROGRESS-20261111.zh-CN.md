### 2.1 单元测试（CPU，v0.5.23 ROCm 镜像 + PR 工作区）

在 holder 35609 上排队执行（`/perf_apps/liyingli/sgl48302-validate-20261111/unit_item.sh`）。跑 PR 改过或新增的 3 个测试文件，以及两个相关的现有文件（`test_tbo_filter_batch_marker.py`、`test_schedule_batch_out_of_place.py`）。

- 第一次（17:21）：脚本把 `CUDA_VISIBLE_DEVICES` 设成了空串，`sglang/test/test_utils.py` 取它的第一个字符时报 `IndexError`，4 个文件收集失败（与 PR 无关）。去掉后重排。
- 第二次（17:35）：PR 测试文件 12 过 1 败。失败的是我新写的 `test_forward_batch_takes_the_bound`：decode 模式的 `init_new` 调 `clamp_position`，这个 fused op 优先走 JIT（要求 CUDA/HIP 设备），容器里能看到 GPU，于是对 CPU 张量走了 ROCm kernel 而报错。CI 的纯 CPU 机器会退回 torch 实现，但为了两种环境一致，测试里把 `clamp_position` 换成它的原生语义 `clamp(seq_lens - 1, min=0)`。其余 4 个文件全过。
- 第三次（17:41）：**全部通过**。PR 测试文件 13/13；`test_tbo_filter_batch_marker.py` 11、`test_schedule_batch_out_of_place.py` 6、`test_dp_spec_prefill_coordination.py` 12、`test_aiter_megamoe_rank_sync.py` 1。
- 补丁合进测试提交后推送：PR head `7f393397` → `4dae7a44`（18:43）。

### 2.2 main 上的审计（R1）

在 holder 35609 的一台机器上排队执行（`audit_item.sh`），源码是 PR 合并 main 后的提交 `c7b9aa66`，加一个只在验证副本里的审计钩子（每次 replay 读一次设备上的真实最大长度）：

- N 组（GPU 0–3）：GLM-5.2-MXFP4，TP4 / DP4 attention，不开 MTP，检查 decode 的 DSA dense/sparse：各 rank 是否每步都选同一个 variant、上界是否从不小于真实最大值、dense 时有没有超过 `index_topk` 的序列。
- S 组（GPU 4–7）：同上加 EAGLE 3/1/4，检查 verify 只抓一张图（启动日志没有 DSA dual-graph）、没有 host mirror 时的上界、MTP 下的输出质量。
- 负载：每组同时跑 GSM8K 探测 400 题（64 并发）和 16k token 长上下文探测 64 条（32 并发），让各 DP rank 的序列落在 `index_topk`（2048）两侧。

- 第一次（17:51）：两个服务都在加载权重时 OOM。原因在我的脚本：参数串里有换行，传进 `bash -c` 后内层 shell 在第一个换行处结束了命令，实际只生效了第一行参数（`tp_size=1`），整个模型挤在一张卡上。改成单行后重排。之后 holder 在 17:50 收到抢占通知、17:55 被抢占，18:39 换到 n01-29 / n10-29 重启。
- 第二次（18:54–19:10，holder 重启后的 n01-29）：**通过**。两个服务都正常起来（N 组启动日志有 4 行 "DSA dual-graph enabled"，即每个 rank 的 decode 都抓了 dense/sparse 两套；S 组 0 行，即开 MTP 时 verify 只抓一套）。

| 组 | GSM8K 400 题 | 开头坏 / 乱码 | 长上下文（约 14k token）捞针 / 长前缀 GSM8K |
|---|---|---|---|
| N：不开 MTP | 392（0.980） | 0 / 0 | 32/32、31/32 |
| S：EAGLE 3/1/4 | 393（0.983） | 0 / 0 | 32/32、31/32 |

N 组审计（`audit_stats.py`）：4 个 rank 对齐 70 个块、17,920 次 replay：
- `new_mismatch=0`：各 rank 每次 replay 选的 variant 都相同；
- `old_mismatch=468`（2.6%）：如果按原来"每个 rank 按自己的真实长度选"的规则，会有 468 次不一致，说明触发条件确实存在（各 rank 的 `old_dense` 分别是 6、6、358、123）；
- `bound_viol=0`：上界从没小于设备上的真实最大长度；`viol=0`：dense 时没有超过 2048 的序列；`nobound=0`：每次 replay 都有上界；
- 空闲 rank 也被覆盖：DP0 有 11,481 次 IDLE replay；
- dense 只用了 7 次：这次负载里长序列很多。不变量都成立，但 dense 的覆盖较少。

S 组没有审计记录，这是预期：开 MTP 时 target 用 verify graph（PR 让它只有一套），没有可选的 variant。

- 第三次（19:19–19:32，`audit2_item.sh`）：为了让 dense 被充分覆盖，只起 N 组服务，只跑 GSM8K 600 题（64 并发），不加长上下文。**通过**：

这一轮也修掉了脚本退出时服务进程没被清理的问题（之前 `kill` 只杀了包着 srun 的子 shell，两个 GLM 服务在审计结束后还占着 8 张 GPU 约 20 分钟，发现后手动取消了这两个 step）。两次审计的结果都补进了 PR 描述（19:35）。
