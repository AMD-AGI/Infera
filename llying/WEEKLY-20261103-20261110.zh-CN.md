## 一、本周结论

1. **最高吞吐 51,374 → 56,593（+10.2%）**：周初 E10（4+4 C104）→ 1P(PP8) + 1D(TP8) C208（16 卡）；对 AUS 上的 E10（50,797）是 +11.4%。
2. **第二版 Pareto（kit v2，单节点 4+4）全线高于第一版（PR #210）**：同交互 +17% ~ +70%，并且整体高于 ATOM 4P4D（PR #209）。
3. **E11 乱码根因找到并给出通用修法**（sglang#48302），跨机验证 judge 0 FAIL；剩余错题证明是模型本身。
4. **定位清楚的三个问题**：单节点慢 23%（同机 Mooncake HIP 传输）、MTP 真实接受长度只有 1.2（草稿 MoE 量化 bug）、K5 C88 崩溃（decode 显存余量不足）。
5. **PP8 的瓶颈是 prefill 在长上下文上的计算**；decode 内核变快只提高交互，不提高吞吐。

### 3. 分析结论（都已实测）

| 问题 | 结论 |
|---|---|
| DP 均衡 | C32 / C48 / C64 / C88 / C104 吞吐 +0.7% ~ +2.3%、交互 +5% ~ +10%；代价 TTFT p90 最多 +29% |
| MTP K 选择 | K5 / K3 步长比在最忙 rank 14-16 个请求处越过 1.21：C64 及以下用 K5，C88 以上用 K3 |
| K5 C88 崩溃（3 / 3） | K5 graph 捕获后每卡只剩 2.1 GB，运行中多占 3.6-4.9 GB；mem-fraction 0.93 可跑通 |
| dense 层在线 FP8 | 吞吐持平（-0.1%）：小 M FP8 GEMM 只到 1.8 TB/s、激活量化 +1.08 ms、indexer 回退 +0.67 ms |
| 1P2D（12 卡） | 被单个 PP4 prefill 限住，同交互比 4+4 低 5-16% |
| PP8 瓶颈 | prefill 流水线是满的；上下文到每批约 25 万 token 时单级耗时 140 → 310 ms；排队请求占住 decode 九成时间满载的 KV |

### 4. 内核（11-09 起，另一会话）

- MLA absorb BMM 配置：TP4 每步 3.09 → 2.14 ms（-0.95 ms），门禁通过。
- PP8 上 MoE 调优行 + absorb：吞吐持平（56,595 对 56,593），交互 +6.5% / +10%；早先 -5.7% 是 decode KV 上限造成的，已不用。
- aiter MegaMoeTP 接入 SGLang：单层 TP8 快 34-50 µs，TP4 / TP8 门禁都通过；TP4 端到端没有变快（49,016 对 49,242），原因在查。
