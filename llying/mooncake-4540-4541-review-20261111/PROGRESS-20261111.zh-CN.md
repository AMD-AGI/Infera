### 2.2 双机测试的环境问题（与 PR 无关，但影响结论）

1. **镜像里的 ionic 用户态驱动和宿主机内核不匹配**：两个 sglang-rocm 镜像（v0.5.22、v0.5.23）都装的是 `libionic1 54.0`（kernel ABI 4），而这些机器的 ionic 内核驱动是 ABI 1（宿主机装 `libionic1 39.0.26.07.10`）。容器里 libibverbs 报 "Driver ionic does not support the kernel ABI of 1"，**一张 RDMA 网卡都找不到**。把宿主机的 `/usr/lib/x86_64-linux-gnu/libionic.so.1.1.39` 挂到容器里那个实体文件的位置后，8 张网卡都可见，端口 ACTIVE。
2. **由此发现 srt-slurm#630 冒烟测试里 Mooncake 实际走的是 TCP**：那次 prefill / decode 日志都是 "Found 0 HCAs"，只有 `TcpTransport`，没有 `installTransport, type=rdma`。我在 #630 总评论里写的 "Mooncake over the ionic rails" 不准确（不影响 #630 要验证的注册、路由、就绪、KV 事件）。更正文字见文末，等你决定要不要改那条评论。
3. 脚本自身的几个问题（已修）：n02-29 的主机名解析到 `127.0.1.1`，改用 `ip route get` 求本机地址；P2P handshake 会自己选端口并把段名改成"IP:实际端口"，改为从目的端日志读段名；目的端第一次加载镜像要一分多钟，改为等它打出"Allocating memory on GPU"后再等 20 秒。

### 2.4 #4540：实际走哪张网卡

- 关闭（`MC_ENABLE_DEST_LOCAL_RAIL=0`，目的端亲和开）：发起端 GPU 0 写目的端 GPU 3，两端都走 `ionic_0`（发送端按源 GPU 选本地网卡，接收端按同名选），37.05 GB/s。
- 开启：第一次被 holder 的抢占通知打断（目的端 step 在 17:50:49 收到 SIGTERM，发起端随后连不上而崩溃），**不是 PR 的问题**。

holder 被抢占后在新节点（n01-29 → n10-29）上整套重跑（18:43–18:55），编译、单测全部通过，#4541 的结果复现（38.21 / 37.75 GB/s，timeout 14 / 18，数据 QP 和通知 QP 都一样），#4540：

| `MC_ENABLE_DEST_LOCAL_RAIL` | 发起端网卡（GPU 0 在 `ionic_3` 的 PCIe 根下） | 接收端网卡（GPU 3 在 `ionic_1` 的根下） | 吞吐 |
|---|---|---|---|
| 0 | `ionic_3`，源 GPU 本地 | `ionic_3`，和 GPU 3 跨 PCIe 根 | 38.59 GB/s |
| 1 | `ionic_1`，和 GPU 0 跨根 | `ionic_1`，GPU 3 本地 | 28.25 GB/s |

GPU 和网卡的对应关系是从 sysfs 的 PCI 路径读出来的（GPU 0 = render128 在根 `0000:70`，和 `ionic_3` 同根；GPU 3 = render152 在根 `0000:10`，和 `ionic_1` 同根）。

结论：
- **功能正确**：开启后两端都换成了目的 GPU 被固定的那张网卡，和设计一致。
- **吞吐下降约 27%**：AUS 每块 GPU 都有专属网卡，单条流下发送端跨根读的代价比接收端跨根写更大。这就是文档里写的取舍，也印证了 10-29 的判断"AUS 这类集群不需要它"。这个功能针对的是 crsuse2 那种"整组网卡共享、接收端扇入导致丢帧"的环境。这一条原样写进了 PR 描述。
