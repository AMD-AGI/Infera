口径：
- 引擎指标来自 AIPerf 的 `server_metrics_export.csv`。**直方图行比表头多一列**：依次为 count、count_rate、sum、sum_rate、mean、p1…p99，最后是分桶计数。本文的 p50/p90 由同一角色所有 rank 的分桶合并后线性插值得到，均值为 sum/count（`scripts/compare_runs.py`）。gauge 行与表头对齐。

## 6. 主要发现

1. **c768 已饱和，瓶颈是 prefill 排队。** P 每个 rank 同时只处理约 4 个请求，排队约 116 个；TTFT 均值有 83% 是 P 排队。单请求 P 处理时间只比 c384 多 0.3 s，排队时间却从 1.2 s 涨到 15.4 s。
2. **P 并没有在算很多新 token。** 96% 左右的 prompt token 命中缓存，真正重算的只有 4% 左右。限制 P 吞吐的是每个请求的固定开销：平均 12 万 token 的长上下文、以及从 UMBP 搬回的 KV。
3. **工作集超出了 P 的 GPU 缓存。** 从 c384 到 c768，GPU 命中从 77.6% 降到 59.1%，UMBP 命中从 18.8% 升到 36.7%，单请求 P 处理时间同步从 0.64 s 涨到 0.93 s（+46%）。与此同时 P 的 KV 使用率只有约 9%，说明正在处理的请求很少，GPU 上的空间大多用作前缀缓存。
4. **D 的 KV 也到了上限，但目前不是主要排队点。** D KV 使用率 p90 0.997，每步耗时从 62 ms 涨到 117 ms；但 D 的排队均值只有 1.75 s，约占 TTFT 的 11%。
5. **KV 传输和 router 都不是瓶颈。** Mooncake 传输 p90 40 ms；router 加两个引擎前端约 20 ms；客户端到 router 约 0.2 s。
6. **同等每卡负载下与 agg 对比**：1P1D c768 吞吐高 7–10%，单用户解码速度是 agg 的 1.6 倍，但 TTFT 中位数约是 agg 的 10 倍。

1. **c640 与 c768 在同一个平台上。** P 一小时完成的请求数几乎相同（54,553 与 54,056），两者都已顶到 prefill 的处理上限；c768 多出的 128 路会话只是在 P 前排队，TTFT 从 5 s 涨到 17 s，吞吐不增。c640 高 2.7% 来自更高的 P GPU 前缀命中（73% 对 59%）与略短的单请求处理时间，但该差距在单轮波动范围内（c768 按 10 分钟切片在 389k–504k 之间波动），宜视为吞吐相当、c640 延迟显著更好。
2. **c892 掉出平台。** 会话工作集远超 P 两卡约 6000 万 token 的 KV 容量，P 的 GPU 命中跌到 22%，73% 的前缀从 UMBP 搬回；P 内部并发略降、单请求略慢，P 完成数下降 13%，总吞吐同比下降 12.8%。decode 因 P 喂不饱反而更空闲（每 rank 151 个、每步 85 ms）。
3. **瓶颈与优化方向**：在 c640 以上，限制吞吐的是 prefill——计算能力与 GPU 前缀缓存容量；decode 有余量。调整 PD 配比时应优先给 prefill 加资源。
4. **平台左边界**：c512 时 λ 为 13.15 请求/s，低于 c640、c768 的约 15，吞吐低 12.3%，prefill 尚未饱和（判断方法见第 8 节）；左边界在 c512–c640 之间，c576 正在测试。

## 8. prefill 饱和的判断与 decode 有效批大小

### 8.1 λ 的定义

λ 为正式计分期间 prefill 引擎每秒完成的请求数：λ = N / Δt。

- **N**：P 端口（30000）两个 DP rank 上 `vllm:request_queue_time_seconds` 直方图在计分窗口内的计数增量之和——vLLM 每完成一个请求记一次观测。串行下发下 P 侧请求在生成首 token 后结束（P 端 `max_tokens=1`），因此 N 也是 P 交给 D 的请求数。P 的 `request_prefill_time` 计数、P 的 `vllm:request_success` 计数器、D 的 `request_decode_time` 计数与之一致（c892 时 D 少 48 个，为窗口结束时仍在 decode 的请求）。
- **Δt**：AIPerf 记录的正式计分阶段引擎指标窗口（`server_metrics_export.json` 的 `start_time`–`end_time`），四个点均为 3,640 s（3,600 s 计分加收尾）。

| | c512 | c640 | c768 | c892 |
|---|---|---|---|---|
| 指标窗口（UTC） | 10:42:47–11:43:27 | 08:12:42–09:13:22 | 18:51:04–19:51:44 | 06:08:40–07:09:20 |
| P 完成数 N | 47,878 | 54,553 | 54,056 | 47,111 |
| **λ（请求/s）** | **13.15** | **14.99** | **14.85** | **12.94** |

λ 是一小时平均值；窗口两端的边界效应（预热中开始、计分中完成的请求计入，计分中开始、窗口结束时未完成的不计入）不超过 1%。总吞吐约等于 λ × 平均输入长度，因此 c640 与 c768 的 λ 几乎相同，吞吐差 2.7% 来自平均输入长度（12.5 万与 12.4 万 token）。

### 8.2 利特尔定律

利特尔定律（Little's Law）：在一个长期稳定的系统中，**系统内平均的对象数 L = 平均到达率 λ × 每个对象在系统内的平均停留时间 W**。最早由 Philip M. Morse 在 1958 年作为经验规律提出，John D. C. Little 于 1961 年给出一般证明（"A Proof for the Queuing Formula: L = λW", *Operations Research* 9(3): 383–387）。它不依赖到达分布、服务时间分布和调度策略，只要求系统稳定（长期到达率等于离开率）且各均值存在，是排队论和性能分析中最常用的守恒关系。

用于本测试：把 D（或 P）看作系统，请求为对象，串行下发下 D 的到达率就是 P 的完成率 λ。

| | c512 | c640 | c768 | c892 |
|---|---|---|---|---|
| D 每 rank 正在处理 L（实测） | 162.4 | 201.7 | 210.5 | 151.3 |
| λ × D decode 时间均值 ÷ 2 | 161.8 | 201.0 | 209.7 | 150.8 |
| D 每 rank 正在处理 + 排队（实测） | 165.0 | 205.1 | 223.8 | 153.9 |
| λ × D 端到端时间均值 ÷ 2 | 165.3 | 205.6 | 224.3 | 154.3 |
| P 每 rank 正在处理 + 排队（实测） | 19.5 | 47.2 | 119.6 | 302.2 |
| λ × (P 排队 + 处理时间均值) ÷ 2 | 20.7 | 48.7 | 121.2 | 303.4 |

D 侧误差在 1% 以内，P 侧在 1–6%（排队计时与 gauge 采样口径略有差别）。

### 8.3 decode 有效批大小随并发的变化

| 每 rank | c512 | c640 | c768 | c892 |
|---|---|---|---|---|
| D 正在处理（均值，p50 / p90） | 162（173 / 200） | 202（216 / 246） | 210（220–225 / 257–264） | 151（158–160 / 221） |
| D 排队 | 2.6 | 3.5 | 13 | 2.6 |
| D KV 使用率均值 | 0.63 | 0.78 | 0.81 | 0.58 |
| D 每步耗时 p50（ms） | 89 | 107 | 117 | 85 |
| D decode 时间均值（s） | 24.6 | 26.8 | 28.2 | 23.3 |

由利特尔定律，D 的有效批大小 = λ × 每个请求在 D 上的时间。并发增加时：P 未饱和，λ 上升，D 批大小随之上升（c512→c640：162→202）；P 饱和后 λ 持平，D 批大小基本持平（c640→c768：202→210，增量来自批次变大后每步变慢、decode 时间变长，而非 λ），多出的会话堆在 P 前（P 排队 87→231）；P 能力下降时 D 批大小下降（c892：151）。

**因此"并发增加而 D 有效批大小不再增长"是 P 饱和的有效判据**，与"λ 不再增长"等价，且能在 decode 侧直接观察。前提是 D 自身没有先达到上限（KV 满或达到最大并发数）——那种情况下 D 批大小同样持平，需看排队堆在哪一侧：c768 时 D KV 使用率 p90 已达 99.7%、D 排队从 3.5 升到 13，两侧都已接近上限。

### 8.4 为什么 c512 已有排队，prefill 却未饱和

| | c512 | c640 | c768 | c892 |
|---|---|---|---|---|
| P 同时处理的请求数（两 rank 合计） | 5.8 | 7.6 | 7.9 | 7.3 |
| P 排队（两 rank 合计） | 33 | 87 | 231 | 597 |
| P 排队为空的时间占比 | 5.0% | 1.8% | 1.5% | 0.3% |
| P 排队时间 / 处理时间（均值，s） | 2.40 / 0.75（3.2×） | 5.62 / 0.88（6.4×） | 15.40 / 0.93（16.6×） | 45.92 / 0.97（47×） |
| P GPU 前缀命中 | 82.3% | 73.2% | 59.1% | 22.0% |
| 每秒到达数的变异系数 / 单秒最多到达 | 0.51 / 324 | 0.54 / 416 | 0.62 / 483 | 0.81 / 562 |

c512 时 P 有 95% 的时间队列不空，但 λ（13.15）尚未到平台（约 15）。原因：

1. **到达不均匀**：子 agent 一次分出多个请求、多个会话同时进入下一轮，平均每秒 13 个，单秒最多 324 个。
2. **单请求工作量方差大**：多数请求只需重算几百 token，少数冷启动长 prompt 需算十几万 token，连续占满多步。
3. **P 并行度低**：每 rank 同时只处理 3–4 个请求。

并行度低、服务时间方差大、到达集中时，平均利用率未到 100% 也会频繁排队（排队论中等待时间随 ρ/(1−ρ) 与服务时间变异系数一起增长）。因此"队列是否为空""P 是否空闲"在这里不能判断饱和。

**判断 prefill 是否饱和，按可靠程度：**

1. λ 随并发是否还在增长（需至少两个并发点）：c512→c640 增长，c640→c768 持平。
2. D 有效批大小随并发是否还在增长（8.3 节），前提是 D 未先到上限。
3. P 排队时间相对处理时间的增长速度：3.2× → 6.4× → 16.6× → 47×，c640 以后明显超线性。

### 8.5 吞吐峰值的位置

最高点更可能在 c640 附近（约 c600–c700），而不是靠近 c768：c640 与 c768 的 λ 同在约 15 的平台上，吞吐差在单轮波动范围内（c768 按 10 分钟切片在 389k–504k 之间）；继续加并发 λ 不再增长，而 P 的 GPU 前缀命中持续下降（82% → 73% → 59% → 22%），平台本身缓慢下沉，峰值应落在 λ 刚达到平台处。按 c512 时 λ 与并发近似成正比外推，λ 约在 c580 达到平台。c576 的结果用于验证；要把峰值定得更准，需要同一点重复测量。

## 9. 待讨论的问题

以下只列问题和可验证的方向，不代表结论：

- **P 每个 rank 为什么只同时处理约 4 个请求？** 排队原因是 `capacity`，`max-num-batched-tokens` 为 16384。需要查清容量被什么占满：长上下文 chunk、UMBP 加载、还是调度策略。
- **P 的 GPU 前缀缓存容量是否值得扩大**，例如提高 P 的显存比例、增加 P 的 rank 数，或调整 UMBP 加载方式（C 方案 embedded UMBP 还没测过性能）。
- **P:D 配比**（2P1D、1P2D、DP4 等），以及按每卡吞吐算是否划算。
- **c384 与 c768 配置不同**，需要在当前配置下重测 c384，才能单独看出并发的影响。
- **decode DP2 偶发死锁**（4 次正式测试出现 1 次），见 `DECODE_HANG.zh-CN.md`，根因尚未定位。
