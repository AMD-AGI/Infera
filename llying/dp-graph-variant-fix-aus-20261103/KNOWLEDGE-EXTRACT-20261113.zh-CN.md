## 1. 结论

1. **它改了我对 MoE 的两个判断。**
   - MI355X 上实测的顺序读上限是 6.70–6.74 TB/s，不是标称的 8。TP4 上 KF 的 gemm1 已经在这个上限的 100–101%，所以那次 campaign 总共只拿到 1.105 倍。按同样的算法，我们 TP8 每层 644 MB 的下限约 96 µs。
   - 他的基准里 MoE 的时间不随 token 数变（192–336 个 token 都是 0.234–0.237 ms），因为每次都读全部专家。我在 trace 里看到的"每多一个 token 多 0.12 µs"，更可能是合成负载里路由不均匀、专家没被读满造成的。**所以"跳过补齐行约省 1–1.5 ms"这个估计站不住**，要等拿到真实路由再定，很可能小得多。
2. **indexer 打分 kernel 已经是优化过的版本。** KF 的打分在 48–84 行、上下文 43 万–66 万时是 95–96 µs，而且不随 batch 变；aiter 原版是 273–311 µs。我们真实 trace 里的 105–117 µs 就是它。所以 indexer 剩下的空间不在打分本身，而在 top-k、十来个前处理小 kernel，以及按 4 行分组。
3. **我们生产 overlay 里的 top-k 有一个正确性隐患。** 它每行最多保留 8,192 个候选，超过的静默丢弃，没有溢出检测和回退。作者在真实输入上见过它溢出（上下文 67 万–70 万，24 次调用里 10 次结果不精确）。上游 PR #47872 已经补了精确回退，但我们跑的是旧版。**我们的上下文 p95 在 44 万–52 万，是否触发没有查过。**
4. **有一个现成的工具能补上我们最大的测量缺口。** "进程内单步基准"可以指定每卡 batch 和每个请求的上下文长度（TP8 + DP attention 下跑过 30 万和 50 万），热态每个点 200–390 秒。它需要移植（写死了 MTP 5 步，SGLang 接口是旧版），但移植后就能在 30 分钟的免抢占期内采到长上下文、指定 batch 的 trace，不用等 AgentX 预热 40 分钟。
5. **PR #237 的新入口现在不能直接用。** 它只在 MI300X 上、对一个玩具算子跑过 1 小时；它的测量脚本造不出 MXFP4 权重、FP8 的 KV 池、路由和页表。之前那六次 campaign 用的是手工搭的任务目录加旧的命令行，那套流程在这个集群上跑通过（每次 6–8 小时，被抢占后续跑）。
6. **作者自己记下的教训，和我们这次复盘发现的问题是同一类**：按假设的 batch 做优化，上线后形状对不上；只在合成数据上验证，真实输入上出错；eager 模式的计时和 graph 里差几倍。

## 2. 对我们各优化项有用的信息

### 2.1 MoE

| 信息 | 数字 / 内容 | 对我们意味着什么 |
|---|---|---|
| 实测的读带宽上限 | 6.70–6.74 TB/s（非临时性加载、4 组 1.29 GB 轮换），是标称 8 TB/s 的 85% | 我报告里按 6 TB/s 算的下限偏保守，按 8 算的都偏乐观。这个上限是在每卡中间维 512 的访问模式上量的，256 要重量 |
| TP4 的 gemm1 | 906.7 MB，6.80 TB/s，已到上限 | "TP4 KF 的 MoE 效率高"是因为它贴着上限，不是有余量 |
| TP8 的下限（按同样算法推） | 644 MB ÷ 6.74 TB/s ≈ 96 µs，加约 2.3 µs 启动 | 我们生产路径两个 GEMM 合计 130–153 µs（token 数 384–640），所以 GEMM 阶段还有 34–57 µs / 层，即 2.5–4.3 ms / 步。这是上界 |
| 有效的手段 | 调优表改用 16 行 tile 的那一行（+3.5–3.9%）；排序和清零并成一次启动（8.2–8.9 → 5.0–5.3 µs）；在前处理里先把激活量化好（gemm1 −3 µs）；shared expert 的 tile 分散到 8 个 XCD（−3 µs）；输出缓冲按 4 MiB 对齐（gemm2 有一个约 3.5 µs 的慢模式）；清零用不进缓存的写（gemm1 −1.08 µs） | 思路可搬。但每一项都是针对中间维 512 写的门槛，256 上要重新推 |
| 无效的手段 | 重调 tile 和配置（±1%）；加深 K 方向流水；提高占用率；专家权重不用"不进缓存"的加载（慢 12%）；寄存器级共享权重；gemm2 改成非原子的归约；按列优先切分 | 这些不用再试 |
| 作者列的剩余空间 | shared expert 权重重复读（≤ 7–8.7 µs）；gemm2 慢模式（约 4 µs）；前处理高出启动地板的部分（约 2.9 µs，"只有去掉这次启动才行"）；gemm2 原子写（≤ 3.5–4.2 µs）；每个 kernel 交界约 1.5 µs | 后几项正是"把通信和 MoE 并成一个 kernel"能解决的。知识库里完全没有 MegaMoeTP 的内容 |
| 一个没查的疑点 | v0.5.21 的 aiter MoE 每次约 235 µs，v0.5.19 镜像里是 179–203 µs，怀疑是 kernel 选择退化，没有核对 | 我们应先核对当前 aiter 对（6144、256、257）这个键在 token 数 448–640 上选了哪个 kernel。调优表按"向上取 2 的幂"查，448–640 正好跨 512 和 1024 两行 |
| 上游状态 | MoE 候选没有提 PR；它写死了 257 专家、每 token 9 个、中间维 512 | — |

### 2.2 indexer

| 路径 | 信息 | 对我们意味着什么 |
|---|---|---|
| 超过 48 行：打分 | KF 版 95–96 µs，aiter 原版 273–311 µs（48–84 行），上下文到 43 万–66 万都是平的。手段：按 XCD 分配、每个执行单元 4 个 wave、成对的行共用一遍 key、最长的组先派发 | 我们已经在用。成对共用写死了按 6 行分组（行数要是 6 的倍数且 ≤ 96），每请求 4 行时大多用不上 |
| 超过 48 行：top-k | SGLang 自带的两个版本在约 60 行以上都有台阶（一个 93.5 → 179.8 µs，另一个 48 → 96 µs）。KF 的选择器 47–48 µs 且是平的 | 见下一行 |
| KF top-k 的缺陷 | 每行候选超过 8,192 个时静默丢弃；并列时结果不确定。真实输入上溢出过。要 `SGLANG_OPT_USE_TOPK_V2=false` 才会走到它 | **我核对了我们的 overlay：`kf_indexer.py` 里上限是 8,192，写入用掩码截断，没有溢出回退。** 需要在真实的长上下文输入上回放检查 |
| ≤ 48 行：自带的 4-kernel 融合路径 | KF 改进版单算子 1.36 倍，结果完全一致，但端到端没有收益；它的逐行打分 kernel 在 30–48 行反而比原版慢（129.5 对 79.1 µs）；每请求 4 行时不分组；唯一一次 4 行的实测是 −1.5% | 不要直接启用。分组在长上下文下收益最大（40 万上下文、24 行：79.9 对 120.4 µs） |
| 作者的建议 | 由主机把"每请求几行"传进去，按这个数专门生成分组 kernel | 这就是我们要做的改动，起点是上游 #47276（仍未合入）和 #45307 |
| 放开 48 行 | 没有任何测量；上限没有环境变量可调 | 要自己做 |

### 2.3 sparse MLA

- KF 的 decode 版在服务镜像里是 3.13–3.48 倍，上游 PR #47278（未合入）在 TP8 + DP attention 的服务器上 ITL 中位 −11.8%。**但这些都是在 1.28 GB 的 KV 池上量的**，没有覆盖我们超过 2 GiB 的情况。
- 加速比随行数下降：48 行 3.15 倍，96 行 2.38 倍。
- 2 GiB 的台阶只在 prefill 的 kernel 上量过（+38%）。Triton 里试过三种绕法都失败（拆成多个 ≤ 2 GB 的视图 +17%；另两种一个结果错、一个没收益），和上一个会话试出来的结论一致。
- 没做的两条路：按 2 GiB 分段各启动一次再合并；或者不用 Triton，写成每页一个缓冲描述符的寻址方式（融合 indexer 的 HIP kernel 里就是这种写法，偏移始终是 32 位）。
- 作者的结构性想法：同一请求的几行共用 gather 出来的 KV。

### 2.4 每个 kernel 的固定开销

| 观察 | 数字 |
|---|---|
| 空 kernel 启动一次 | 约 2.3 µs |
| graph 里相邻 kernel 之间 | 约 1.5 µs |
| kernel 结束时有脏的缓存行要写回，会推迟下一个 kernel 的派发 | 中间结果改用"直写"的存储方式后，交界从 1.9 降到 1.0 µs；清零改用不进缓存的写，gemm1 快 1.08 µs |
| 合并启动 | MoE 从 6 个 kernel 并到 3 个；indexer 把一个单独的初始化 kernel（"一次 5 µs 的派发"）并掉 |
| 参数 | 标量参数做成编译期常数，kernel 开头就不用先加载参数 |

我量到的约 4 µs 和这里的 2.3 + 1.5 对得上。新的一点是：**除了合并 kernel，还可以在不合并的情况下改存储方式来缩短交界**，这比改模型代码便宜。

### 2.5 BF16 的 GEMM 和调优表

- 重调的完整流程是现成的：从 decode 日志里收集"没找到调优配置"的行 → 在同一镜像里离线调 → 检查 → 只读挂载 → 确认合并成功且不再有回退。65 个形状约 1 小时 20 分钟，要 4 张空闲的卡。
- 查表规则：先找精确的 M，没有就向上取到 16 或 32 的倍数，再没有就取下一个 2 的幂，最后退到默认实现。
- 已有的两张表里，o_proj 覆盖了 M = 1–384；另外三个小 GEMM 只调了 M = 264–384（那是 TP4、每请求 6 行的形状）。按规则推，我们 68–96 行时这几个 GEMM 会落到 M = 128 那一行。这是推断，用他的检查脚本在我们的日志上跑几分钟就能确认。上一个会话做的"调优表补行"已经覆盖了一部分。
- 效果有限：他那次重调端到端 +0.9%，在噪声内。这类 GEMM 的空间不在调参。
- 没有任何关于"FP8 的 GEMM 在小行数下为什么慢"的内容。

### 2.6 布局和 MTP 步数

- TP8 下 MoE 不按专家分片（EP1）比分片（EP8）快，10 个点里 9 个，行数越少差得越多。我们现在就是 EP1，不用改。
- 把上下文沿序列切到各卡的那种布局（DCP）在 PD 下被否了：同样负载每步慢约 30%。
- MTP 3 步对 5 步只有一对数据（TP4、C96）：3 步 +4.8%。他的规则是：3 步和 5 步的接受长度之比（0.828）高于两者的步长之比时，3 步赢；batch 小或 decode 不是瓶颈时，更深的更好。**TP8 上没有数据**，这个问题只能靠我们自己补一对测量。
- 只有 indexer 随上下文变长：全部请求 30 万上下文时每 token 时间 +6.6%，50 万时 +11.0%。

## 3. 能直接用的方法

### 3.1 进程内单步基准（补我们最大的测量缺口）

- 位置：快照里 `yihou/draft/handoffs/kbk-tool-inprocess-step-bench/content/items/codes/sglang_decode_internal_bench/`，代码是完整的。
- 它做什么：不起调度器和 HTTP 服务，直接驱动模型和 MTP 的 worker 跑整步。只捕获一个指定 batch 的图；每张卡的每个请求可以指定上下文长度；KV 和 indexer 的 key 用随机数填满，权重和 router 是真的，接受长度是模拟的。
- 校验：实际接受长度逐位核对；图的回放次数等于迭代次数；参数回读。
- 用时：TP8 下热态每个点 200–390 秒；新节点上冷启动最长约 14 分钟。
- 要改的地方：
  - 写死了 MTP 5 步（6 行），要改成可配。
  - 用的是旧版 SGLang 的接口，没在 v0.5.22 上跑过。
  - 所有卡的 batch 相同，量不到补齐行的影响。
  - KV 按"batch × 最长上下文"整块预留，每卡池约 347 万 token 时，batch 24 只能放约 14.4 万的上下文。
- 它没有和带 DP attention 的真实服务对过表。关掉 DP attention 时，并发 16–24 和服务差 1% 以内，并发 4–8 差 22–24%（原因没查清）。

### 3.2 算子工作集

- 格式和生成脚本都在：13 个算子定义、80 组输入，覆盖一步里 75.1% 的 kernel 时间，每组带"出现概率"和"每步调用次数"。
- 它现在的内容不能直接用：TP4、每请求 6 行、只有 batch 8–14；batch 分布是假设的，而且后来发现是错的（实际每卡 4.6–5.4 个请求，88–93% 的时间 batch ≤ 8）；MoE 的参考实现一度和生产差 13 dB；路由和 indexer 的输入是均匀随机的。
- 改成我们的：卡数 4 → 8，每请求行数 6 → 4，batch 分布换成我们日志里量出来的直方图（`BATCH-DIST.md` 里已有），indexer 的定义在 48 行处拆成两个，MoE 在 token 数 432 以上重新核对走哪个 kernel。

### 3.3 一次 campaign 是怎么跑的（旧流程，在这个集群上跑通过）

| 步骤 | 内容 |
|---|---|
| 任务目录 | 把生产 kernel 原样拷成一个文件（另留一份不动的）；受保护的驱动脚本（一种模式出精度，一种模式出时间）；graph 计时的框架；一份说明（目标、调用路径、形状、基线、哪些不做以及为什么） |
| 计时 | 在 CUDA graph 回放下计时；一次回放里连续调用多次，每次用不同的权重或 KV 池，总量大于 256 MB，避免缓存命中造成的假象 |
| 打分 | 各用例"原版 ÷ 候选"的平均，取 3 次测量里最小的；比当前最好的高 0.5% 才保留 |
| 预算 | 每次 6–8 小时，每轮 10–20 分钟，最好的结果出现在第 4–15 轮；一张卡；状态放共享存储，被抢占后续跑 |
| 做完之后 | 独立复测 → 在服务镜像里对同一入口做 A/B → 加门槛接进 overlay → 确认每个形状都真的走到了 → 只改一个变量的端到端 → 用真实输入回放 → 提上游 |

作者定的几条准入标准，我认为应当照搬：
- 动手前先算：这个算子占一步的比例 ×（1 − 1 ÷ 预期加速比），和端到端的噪声带比。低于约 3% 的不值得单独做端到端。
- 候选在服务镜像里、graph 模式下、**每一个实际会出现的形状档位**上都要复测，不只是概率最大的那档。
- 依赖数据的算子（top-k、路由、稀疏索引）必须用抓下来的真实输入回放。
- 精度门槛从现役 kernel 标定：先量现役 kernel 对 fp32 参考的精度，门槛设在它下面一点。他用的是 MoE ≥ 30 dB（现役 46–51）、sparse MLA ≥ 25 dB（现役 26.5–27）、indexer 的选择结果要求集合相等或 60 dB。

### 3.4 抓真实输入

- 知识库里没有抓好的真实路由。作者留的做法是：在 overlay 里加一个导出钩子，服务端关掉 CUDA graph 跑几步（graph 回放时 Python 钩子不触发），把 top-k 的专家 id 和 indexer 的选择结果存下来。后来那次 DCP 的 campaign 就是这么抓的，并因此发现了候选上限溢出。
- 已知的影响量级（二手）：路由塌缩时 MoE 读的显存少 2.3 倍；路由不固定种子时，最大的一行在两次运行间差 4.5%。

### 3.5 测量纪律（有数字支撑的规则）

- 开着 profiler 的运行不算成绩：线上 −6.6%。
- 时间只取 graph 模式下的；形状和 kernel 身份从同样 batch、同样上下文的 eager 运行里取。eager 下 verify 慢 1.56 倍，sparse MLA 的加速比在 eager 下只有 1.07–1.42 倍，graph 下是 3.1–3.6 倍。
- 读任何占比之前，先数每次图启动里有多少个 kernel。
- 同一对节点上端到端的波动是 ±0.1% ~ ±1%；换节点同样的命令差过 9.3%。对比要 ABBA、每臂至少 3 次。
- 模拟接受长度只能用来比速度，不能当正确性；要核对实际的接受长度。
- 每个 kernel 要证明两件事：开关真的传到了进程里；每个形状上真的走到了它（日志里要有逐形状的"走新的 / 走旧的"一行）。

关于我们自己的 trace：采集时都设了 `DEBUG_CLR_GRAPH_PACKET_CAPTURE=0`，知识库里说这个开关对步长的影响从没对比过。我们这边有间接的对比：trace 里的步周期和不开 profiler 的计分运行日志里的步长差 0–2%（graph batch 12：32.2 对 31.5 ms；16：35.5 对 35.5 ms），所以扰动不大。

### 3.6 作者踩过的坑（和我们相关的）

| 坑 | 例子 |
|---|---|
| 形状对不上 | 按"batch 8–14、每请求 6 行"调好的 kernel，上线后实际 batch ≤ 8 占 88–93%，后来又换成每请求 4 行 |
| kernel 上面还有一层分发 | ≤ 48 行根本走不到被优化的那个函数；模块在上游改了名，一次运行成了空操作而没人发现 |
| 只优化了驱动脚本计时的那部分 | 融合 indexer 的逐行 kernel 只测了 12 和 24 行，30–48 行反而比原版慢 |
| 合成数据掩盖了依赖数据的路径 | 合成输入上又快又精确，真实输入上又慢又不精确 |
| 前向模式 | 只为 verify 写的 kernel 被 prefill 阶段的一个 batch 走到，直接让 GPU 出错 |
| 参考实现本身不对 | 工作集里 MoE 的参考和生产差 13 dB；通用的 30 dB 门槛会放过召回率只有约 0.85 的 top-k |
| 按标称带宽算余量 | 按 8 TB/s 算"还有约 1.3 倍"，实测上限说最多 1.10 倍 |
| 编译器 | Triton 3.7 / ROCm 7.2 上有四处会算错的组合（明细在 `KF-CAMPAIGNS.md` 第 10 节）；手调的 absorb 配置在 M = 256 时让 LLVM 崩溃 |
| 第一次使用落在图捕获里 | KF 的 MoE 如果第一次调用发生在图捕获期间，会退回 aiter 的 kernel |
| 端到端的设计 | 几个 kernel 捆在一起比，分不出各自的贡献；全部用模拟接受长度，没有一次真实接受长度下的运行 |

## 4. PR #237：新的 Forge 入口

**它是什么**
- 一个技能目录（说明、参考页、检查脚本、启动脚本、模板），优化器本身是 Hyperloom 的 `forge-loop`。
- 工作集模式：改引擎源码的一份拷贝，按工作集里记录的基线，由受保护的测量脚本和独立验证器裁决。验证器的规则：基线要复现到 5% 以内否则中止；候选复测要在 15% 以内；收益要高过噪声。
- AKLR 原生模式：在 AKLR 的算子定义上从零做，只支持 FlyDSL / Triton / Gluon。
- 上游给的成本参考：GEMM 约 10 美元 / 小时，MoE 约 17 美元 / 小时，每轮 20–70 分钟。预算下限 1 小时，默认 3 小时。

**为什么现在不能直接用**

| 问题 | 说明 |
|---|---|
| 没在 gfx950 上跑过 | 证据是 543 个 CPU 测试（启动被桩掉）和一次 MI300X 上 1 小时、2 轮的玩具算子 |
| 造不出我们的输入 | 测量脚本只会生成普通类型的随机张量 |
| 没有我们的工作集 | 旧的 GLM-5.2 工作集是另一种格式，而且形状不对 |
| 抢占 | 每轮比免抢占期长；工作集模式的启动脚本没有续跑分支，续跑要手工 |
| 挂载和存储 | 容器不挂 `/perf_apps`；状态默认在本地盘 |
| 候选只能是单个 Python 文件 | 多文件或要编译的 HIP kernel 怎么放，PR 里没说 |
| 交付 | 产出是对镜像里那棵树的补丁，不是 aiter / SGLang 的 PR |

**对我们有用的**
- 上游 AKLR 知识库里，我们的算子族除了 absorb 都有对应页面。
- 上游已有一个 GLM-5.2、每卡中间维 256 的 MoE kernel，测的是 2 的幂的 token 数（含 256、512），不含 448–640。
- 这两条取自 PR 链接的上游文档当前版本。

## 5. 这些信息让我们的计划改什么

1. **先做一次真实输入的抓取。** 一次抓取同时回答三件事：MoE 的专家覆盖率（决定"跳过补齐行"值不值得做，也决定 MoE 的真实字节数）、top-k 候选是否溢出（正确性）、后续所有单算子基准的输入。
2. **移植进程内单步基准**，替代我之前建议的"长上下文合成负载"。它更快，而且能精确指定 batch。
3. **MoE 先查后做。** 先核对 aiter 在 token 数 448–640 上选了哪个 kernel；再在每卡中间维 256 的访问模式上重量读带宽上限；然后才决定在 MegaMoeTP 内部还是在单卡 GEMM 上投入。按上限推，GEMM 阶段最多还有 2.5–4.3 ms / 步。
4. **indexer 的目标改成三件事**：top-k 的正确性和台阶、按每请求行数分组、放开 48 行。打分 kernel 本身不用重做。
5. **kernel 个数那一项加一条便宜的路**：先试"直写"和"不进缓存的写"来缩短 kernel 交界，再考虑合并。
6. **campaign 用旧流程的做法手工搭任务目录**，不等 PR #237 的新入口成熟。准入标准照 3.3 的四条执行。
7. **"跳过补齐行"从第 3 位往后放**，等第 1 步的结果。

## 6. 没有覆盖的

- TP8、每请求 4 行、v0.5.22 上的任何测量。
- MegaMoeTP、补齐行的代价、FP8 的稠密 GEMM、KV 池超过 2 GiB 时的 decode sparse MLA。
- 抓好的真实路由和真实 indexer 输入。
- 任何离线工具对真实 PD decode 的校准，尤其是开着 DP attention 时。
- 真实接受长度下带这些 kernel 的端到端运行。
- 集群上现在有没有可用的 Forge / AKLR 检出和登录，我没找到本地的检出。
