**优化：GEMM2 列组宽度改成前粗后细**
- 前面的列组宽一些，后面的窄一些，这样快结束时的单元更小，CTA 之间更容易拉平。
- aiter 已经支持这种宽度：H 6144 有 12 个 512 列块，设 `AITER_MEGAMOE_TP_LB_Q=3` 时，aiter 会自动用 `[3,3,3,2,1]`。
  - 此前的参数扫描只测了 q = 1 / 2 / 4 / 8，漏了 q = 3。
- 我加了一个小补丁（`bench/megatp_cgw_patch.py`，环境变量 `AITER_MEGAMOE_TP_LB_CGW`），可以指定任意宽度，用来做对比。

## 2. sparse MLA > 2 GiB 寻址：原因已查清，修法已写好，待 microbench

**原因**
- Triton 3.7 的 HIP 后端只在张量底层的整块存储 ≤ 2³¹−1 字节时，给指针参数标记"32 位范围"；有这个标记才能用 buffer 访存。
- TP8 每层 KV 池 2.36 GB，超过了这个限制，所以 KV 的所有 gather 都退回普通的 64 位地址访存；kernel 同时还改用了 64 位行偏移。
- 11-09 试过的"无符号 32 位偏移"只改了偏移，没有恢复 buffer 访存，所以无效。

**修法**（`bench/make_kf_sparse_split2g.py` 生成 `bench/kf_sparse_mla_split2g.py`，只改 decode 用的 split-K kernel）
1. 启动器把 KV 池以约 2 GiB 为界拆成两段（行 [0, S) 和 [S, N)），每段用一个只带 `data_ptr()` / `ptr_range()` 的小对象传给 Triton。Triton 自带的 `MockTensor` 也是这么用的，所以每段都能拿到 32 位范围标记。
2. kernel 对每次 gather 从两段各发一次带掩码的 buffer 加载，掩码互补。被掩掉的加载不访问内存、返回 0，两者按位 OR 即为正确结果。
3. 加了开关：`KF_SPARSE_SPLIT_2G=0` 可以关闭这个修法。

目前进度：代码已生成，语法检查通过。

**下一步 microbench**（在计算节点上做）
- 正确性：与原 kernel 逐位比较，覆盖整个池、拆分边界附近、首尾 slot 和无效 slot（-1）。
