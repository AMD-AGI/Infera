# amdgpu 6.19 驱动上 GLM-5.2 PD 起栈崩溃：根因与解决方案（2026-11-13）

接 `REPORT-20261110.zh-CN.md` 第六节、`HANDOFF-20261112-REVIEW.zh-CN.md` 第 3a 节和第 4 节第 6 条。

## 一、结论

**根因是 amdgpu 驱动的一个已知回归，不是我们的代码，也不是 ROCm 用户态。** 从 amdgpu-dkms 6.18.4 开始，驱动内核里负责 GPU 计算显存的部分（KFD）
在每次分配显存前做限额检查时，把"已经分配、又被固定（pin）住的显存"算了两次。

- 第一次：分配时记进 `kfd.vram_used`。
- 第二次：网卡注册时固定住，记进 `vram_pin_size`，限额检查又减一次。

我们的 PD 起栈要把整个 KV 缓存（每卡 110–190 GB）注册给 ionic RDMA 网卡，网卡注册必须固定显存。注册完之后，驱动认为显存已经用光，之后任何新的显存申请都返回
ENOMEM（显存不足）。最先碰到的是 PyTorch 第一次真正创建 HIP stream（要给硬件队列分配显存）：ROCm 7.2 拿到空 stream 后段错误，ROCm 10 如实报
hipErrorOutOfMemory。

- 上游 Linux 已修：[`9131cc85d0de` drm/amdkfd: correct vram_available calculation](https://github.com/torvalds/linux/commit/9131cc85d0dedd8ba4cae60dbe5985d081551f30)
  （AMD 的 Zhen Han，2026-09-20，标了 `Cc: stable`）。提交说明原文："kfd.vram_used already includes BOs that are later pinned. Pinning does not
  consume extra VRAM. Subtracting vram_pin_size counts those bytes twice and causes fake-OOM while VRAM is still free."
- **AMD 已发布的 DKMS 都还没带这个修复**，包括最新的 7.1.9（31.60）。所以集群往任何已发布的新版本升级，问题都还在。
  Linux 主线从 v7.4-rc1 起包含这个修复，v7.3 不含。
- **独立的使用说明**（问题描述、怎么判断别的集群是不是同一个问题、原理、两种修法的用法和限制）：`driver619/README.zh-CN.md`。

## 二、"是不是因为别人没用 RDMA、我们用了"

方向对，但更准确的说法是：**我们把一大块显存注册给了 RDMA 网卡，别人注册的量小得多**。

- 别人在 6.19 节点上也跑跨节点 RDMA：11-13 03:20 kgoginen 的 4 节点 flux MLPerf 训练就在 n03-33、n04-25、n04-29 上，
  多节点训练靠 RCCL 走 RDMA。但 RCCL 只注册几百 MB 的通信缓冲，被多扣的这点显存不会把可用显存扣光。
- 我们每卡注册的是整个 KV 缓存，110–190 GB。多扣一份后，"权重 + 2 × KV"超过了 288 GB 显存。
- 同一台 6.19 节点上的对照（e1ab 会话，11-12，GLM-5.2 单节点 4+4 PD，`/perf_apps/liyingli/bench_agentx/e1ab/logs/e1ab.out`）：
  - 不启用 RDMA 时正常就绪：00:32 在 n04-29、07:45 在 n04-25；09:27 的消融 A 不挂宿主机的 ionic 网卡驱动，Mooncake 找到 0 张网卡；
  - 启用 ionic RDMA 后，08:34 起 5 次 prefill 全部段错误。

## 三、机制（源码证据）

源码来自 AMD 官方仓库的 DKMS 包（`/perf_apps/liyingli/bench_agentx/kfd619/src/`）。集群上的 6.19.14.31400100 就是
repo.radeon.com 上的 amdgpu 31.40.1，6.16.13 是 30.30.x。

### 3.1 限额检查（`amd/amdgpu/amdgpu_amdkfd_gpuvm.c` 的 `amdgpu_amdkfd_reserve_mem_limit`，约第 237 行）

| 驱动版本 | 可分配上限 | 结果 |
|---|---|---|
| 6.16.13（30.30 / 30.30.4） | `vram_size − 预留 − vram_pin_size + kfd.vram_pinned` | 用 KFD 记的固定量抵消 |
| 6.18.4、6.19.0、6.19.4、6.19.14（31.10–31.40.1）、7.1.3、7.1.9（31.50、31.60） | `vram_size − 预留 − vram_pin_size` | **抵消项被删，固定的 KFD 显存算两次** |
| 上游修复后 | 与报告可用显存用同一个函数，`kfd.vram_pinned` 只在 BO 第一次固定、最后一次释放时更新 | 正确 |

报告给用户态的可用显存（同一文件的 `amdgpu_amdkfd_get_available_memory`，`hipMemGetInfo` 读到的就是它）在所有版本里都保留了 `+ kfd.vram_pinned`。
所以在 6.19 上，**报告的可用显存和限额检查用的是两套算法**。

### 3.2 两种注册方式怎么记账

- **dma-buf 注册**（Mooncake `MOONCAKE_DISABLE_HIP_DMABUF=0`）：网卡驱动调 `amdgpu_dma_buf_pin` → `amdgpu_bo_pin`，BO 第一次被固定时
  `vram_pin_size` 加上 BO 大小，`kfd.vram_pinned` 不变。所以**在所有版本上都多扣一份**：报告的可用显存少了注册量，限额检查也一样。
- **peer memory 注册**（`MOONCAKE_DISABLE_HIP_DMABUF=1`，`ibv_reg_mr` → `kfd_peerdirect.c` 的 `amd_get_pages`）：每次注册（每张网卡、每个 1 GiB 分块）
  都调 `amdgpu_amdkfd_gpuvm_pin_bo`，`vram_pinned` 无条件加一整个 BO 的大小。`vram_pin_size` 只在第一次加。
  - 6.16：限额检查里有 `+ vram_pinned`，这份多出来的抵消让限额检查实际上失效，所以**生产一直正常**。
  - 6.19：限额检查不看 `vram_pinned`，KV 照样算两次。报告的可用显存则被抵消得远大于实际值。

用 11-10 的旧数据验算 peer memory 下的异常读数。小模型 5 层，每层一个 KV buffer，8 张网卡，每个 buffer 按 1 GiB 分块注册：

| 显存比例 | 每个 buffer | 预测多出的抵消 = 8 × 5 × 分块数 × buffer 大小 | 实测报告的可用显存 |
|---|---|---|---|
| 0.5 | 23.43 GiB，24 块 | 22,497 GiB | 22,538 GiB |
| 0.8 | 37.92 GiB，38 块 | 57,638 GiB | 57,523 GiB |

### 3.3 与所有已观测现象对账

| 现象 | 解释 |
|---|---|
| 生产配置在 6.16 上一直正常 | 生产用的是 peer memory（生产日志都有 `HIP dmabuf disabled via MOONCAKE_DISABLE_HIP_DMABUF`），6.16 的限额检查被抵消 |
| 生产配置在 6.19 上必崩 | 6.19 的限额检查不再抵消。例：e1ab prefill PP0 权重 93.6 GB、KV 124.4 GB，分完 KV 后剩 67.4 GB，注册后再扣 124.4 GB 就成了负数 |
| `MOONCAKE_DISABLE_HIP_DMABUF=1` 在 6.19 上也崩（11-10 门禁 61） | peer memory 在 6.19 上同样算两次 |
| 小模型测试 6.16 和 6.19 门槛相同（0.5 正常、0.65 崩） | 测试脚本 `pd_startup_test.sh` 默认走 dma-buf，dma-buf 在两个版本上都多扣，所以分不出驱动 |
| 小模型 0.5 能起、0.8 必崩，与网卡数量、CUDA graph 无关 | 条件是"权重 + 其他 + 2 × KV ≤ 显存"，与网卡数量、graph 无关 |
| ROCm 10 镜像也失败，报 hipErrorOutOfMemory | 限额在内核里，换用户态没用 |
| Mooncake 新的 KFD pin anchor（上游 PR #4657）在 6.19 上没用（e1ab 11-12 08:48） | anchor 靠 peer memory 抬高 `vram_pinned` 来抵消，6.19 的限额检查不看它 |
| 不分离 PD 的服务、单卡 torch、RCCL 训练都正常 | 不注册显存，或者注册量小 |
| 40 GiB / 1 GiB 的最小复现不崩 | 40 + 40 远小于 288 GB |

## 四、对之前记录的更正

1. **11-10 20:33 "根因 = 6.19 驱动重复记账"那条撤回本身是错的。** 那次对照在 6.16 上跑的是 dma-buf 路径，而生产走的是 peer memory。
   dma-buf 在两个版本上都多扣，peer memory 只在 6.19 上多扣，6.19 特有的就在这里。
2. REPORT-20261110 04:05 说"kit 默认 `MOONCAKE_DISABLE_HIP_DMABUF=0`"：kit 的 `env.sh` 默认确实是 0，但生产配置在
   `opt-aus-20261103/pkg/config/site.local.env` 第 18 行默认设成 1。所以 11-10 的门禁 61（`arm-C-prod-ptpcfix-nohip-dmabuf1.env`
   只把它再设成 1）与生产配置完全相同，"改成 1 就能绕过"从一开始就不成立。
3. HANDOFF-20261112 里的"ROCm 10 镜像加小模型在 6.19 上也崩"：那次也是 dma-buf 加 0.8，说明不了 ROCm 10 是否有用。
   不过按源码，限额在内核里，ROCm 10 确实修不了。
4. Mooncake 文档（`MC_HIP_KFD_PIN_FIX`，PR #4657）说"amdgpu-dkms 6.19.14 只计一次"，与 6.19.14.31400100 的源码和实测都不符：
   e1ab 在这版驱动上的探测打出了 "lowered KFD free VRAM by 64 MiB"。

## 五、解决方案

### 方案 A（根本修法）：驱动打上游补丁

- 上游补丁 `driver619/upstream-9131cc85d0de.patch`（5 个文件，+127 / −43）。
- 针对集群这版 DKMS 的回移补丁 `driver619/backport-9131cc85d0de-amdgpu-dkms-6.19.14.31400100.patch`：上游 11 处改动里 10 处直接打上，
  1 处只是缩进不同（DKMS 源码这里用空格），已手工处理。**还没编译验证。**
- 需要集群管理员用这个补丁重建 DKMS 并重载驱动，或者请 AMD 尽快发布带这个修复的 DKMS。在那之前，任何已发布的新驱动都有这个问题。

### 方案 B（不依赖驱动）：KV 缓存改用 GEM 分配

思路：KV 不经过 KFD 分配，就不会进 `kfd.vram_used`，被网卡固定时只在 `vram_pin_size` 里算一次。

1. 用 DRM render node（`/dev/dri/renderD*`）的 `DRM_IOCTL_AMDGPU_GEM_CREATE` 在显存里分配 KV，导出 dma-buf fd；
2. 用 `hipImportExternalMemory` 导入当前进程。KFD 导入 dma-buf（`import_obj_create`）**不调用**限额记账，已读源码确认；
3. 分配后立刻用一页的 dma-buf MR 把 BO 固定住，让报告的可用显存和限额检查马上反映这块 KV；
4. Mooncake 对这些 buffer 只走 dma-buf 注册。

按源码，这样做在 6.16、6.19 和打了上游补丁的驱动上都只计一次：上游补丁的 `amdgpu_amdkfd_account_vram_pin` 对非 KFD 分配的 BO 直接返回。

**风险：这些 buffer 绝不能走 peer memory 注册。** `amd_get_pages` 无条件读 `bo->kfd_bo->domain`，GEM 分配的 BO 这里是空指针，会在共享节点上触发
内核空指针错误。所以 Mooncake 对这些 buffer 必须关掉 `ibv_reg_mr` 回退和 KFD pin anchor（`MC_HIP_KFD_PIN_FIX=0`），最好在 Mooncake 里按指针类型
（ROCr 把导入的 buffer 报为 `HSA_EXT_POINTER_TYPE_GRAPHICS`）硬性拒绝。

改动范围：一个分配模块，SGLang 的 KV pool 分配处接入，Mooncake 加一个保护。要在 6.19 和 6.16 节点上分别验证记账、RDMA 传输正确性和速度。

### 现状（临时）

`opt_item5.sh` 的驱动检查继续自动排除 6.19 节点。不砍 KV 的话，6.19 上起 PD 必须满足"权重 + 2 × KV + 其他 ≤ 显存"：prefill PP0 的 KV 要从 124 GB
砍到约 90 GB，decode 从 142 GB 砍到约 79 GB。

## 六、实测（两节点作业 36242：n04-29 amdgpu 6.19.14.31400100，n04-33 6.16.13，11-13 07:00 起）

结果目录 `/perf_apps/liyingli/bench_agentx/kfd619/out/`，脚本在本目录 `driver619/`。

### 6.1 最小复现（`kfd_pin_repro.py`，单进程单卡，只用 HIP / HSA / libibverbs；`repro-1113T0700`）

"剩余可分配"是注册之后驱动还肯让这个进程再分配多少显存（以 256 MiB 为步长二分查找）。注册前两台节点都是 287.25 GiB。

| KV 大小与注册方式 | 6.19 剩余可分配 | 6.16 剩余可分配 | 6.19 / 6.16 注册后新建 stream |
|---|---|---|---|
| 40 GiB，dma-buf | 207.25 GiB（扣 2 × 40） | 207.25 GiB（扣 2 × 40） | 正常 / 正常 |
| 40 GiB，peer memory（生产用的方式） | 207.25 GiB（扣 2 × 40） | 247.5 GiB（扣 1 × 40） | 正常 / 正常 |
| 150 GiB，dma-buf | 0 | 0 | 段错误 / 段错误 |
| 150 GiB，peer memory | 0 | 137.5 GiB | **段错误 / 正常** |

- peer memory 注册后驱动报告的可用显存（`hipMemGetInfo`）：40 GiB 注册给 1 张网卡时是 1,807 GiB，注册给 8 张网卡时是 13,007 GiB，150 GiB 时是 22,487 GiB，
  两个驱动版本都一样。这正好等于"实际剩余 + 网卡数 × 分块数 × 分配大小"（207 + 40 × 40、207 + 8 × 40 × 40、137 + 150 × 150），与第三节读源码得出的结论一致。
- 用 torch + Mooncake 的缩小版（`mc_gem_test.py`，150 GiB KV 分成 25 个 6 GiB buffer，`batch_register_memory` 注册，生产设置
  `MOONCAKE_DISABLE_HIP_DMABUF=1`；`gem-1113T0703`）：6.19 上读新 `torch.cuda.Stream(priority=0).cuda_stream` 时段错误，**和生产崩在同一处**；
  6.16 上正常，RDMA 写入 26.4 GB/s，数据校验通过。
- 镜像 `infera-sglang:v0522-fdbafb60` 里的 Mooncake 没有 KFD pin anchor（`.so` 里没有相关字符串），`MC_HIP_KFD_PIN_FIX` 对它不起作用。

### 6.2 方案 B：KV 改用 GEM 分配

- 单进程测试（`repro-1113T0700`、`repro-gemfd-1113T0721`）：GEM 分配、`hipImportExternalMemory` 导入、GPU 读写都正常。
  分配 40 / 150 / 200 GiB 并固定后，剩余可分配分别是 247.25 / 137.25 / 87.25 GiB，即**只扣一次**，两个驱动版本相同。
  用 BO 自己的 dma-buf 句柄注册（8 张网卡共 1,200 个 MR 也可以）后，剩余可分配不变，新建 stream、再分配都正常。
- 两处用户态的坑，都已在分配器里处理：
  1. HIP 不记录导入显存的地址范围（`hipMemGetAddressRange` 返回空的起点），ROCr 的 `hsa_amd_portable_export_dmabuf` 碰到导入显存会段错误。
     这两个调用正是 Mooncake 注册 HIP 显存的方式。
  2. Mooncake 不管 `MC_DISABLE_HIP` 怎么设都会装节点内的 HIP 传输，注册时对每块显存调 `hipIpcGetMemHandle`。导入显存拿不到 IPC 句柄，
     整个 `batch_register_memory` 因此失败，还留下一个没清掉的 HIP 错误，紧接着 torch 下一次 kernel 启动报 invalid argument。
  验证阶段的处理：`libhip_gem_alloc.so` 用 `LD_PRELOAD` 加载，只对自己分配的地址接管这三个调用，并拒绝这些地址上的 `ibv_reg_mr`
  （防止走到会触发内核空指针错误的 peer memory 路径）；其余地址原样转给原函数。Mooncake 二进制不用改。
  正式交付要改成 Mooncake 的原生支持，不能靠预加载（InferenceX 不允许运行时替换函数）。
- torch + Mooncake（`gem-preload2-1113T0754`）：**6.19 上 150 GiB 和 198 GiB 的 GEM KV 都能注册**，注册后新建 stream、再分配 8 GiB 都正常，
  RDMA 写入跨过 1 GiB MR 边界的数据校验通过；同一轮里 KFD 分配、peer memory 注册的 150 GiB 对照照样段错误。
- GPU 读写带宽：GEM 显存与普通显存相同（拷贝 4,785–5,012 对比 4,645–5,031 GB/s，读 902–929 对比 927–931 GB/s）。
- RDMA 写入速度（`rdma-bw-ab-1113T0802`，同一对卡 GPU 1 ← GPU 5、同一张网卡 ionic_5，40 GiB，一次只跑一组，三轮）：同一台节点上三种方式**完全一样**。
  n04-29：生产路径 15.43–15.45、KFD 加 dma-buf 15.38–15.43、GEM 加 dma-buf 15.45–15.46 GB/s；n04-33：三种都是 27.9–28.3 GB/s。
  两台节点之间差近一倍，但三种方式在 n04-29 上同样慢，与注册方式无关（11-10 在 6.19 的 n03-33 上 GPU 0 ← GPU 4 测过 22.2 GB/s）。

## 七、验证计划（第 1、2 步已在第六节完成）

1. **最小复现**（不起 SGLang，单节点，每项几分钟）：`hipMalloc` A GiB → 分别用 dma-buf 和 peer memory 注册给 ionic → 再 `hipMalloc` B MiB、创建新 stream。
   预期：6.19 上两种注册方式都在"已用 + A + B > 显存 − 预留"时失败；6.16 上只有 dma-buf 失败。同时记录 `hipMemGetInfo`、
   `/sys/class/drm/card*/device/mem_info_vram_used`（实际显存占用）和 `/sys/class/kfd/kfd/proc/<pid>/vram_*`，与第三节的公式逐项对上。
2. **方案 B 原型**：同一个脚本里换成 GEM 分配 + 导入 + 固定，在 6.19 上注册 190 GB 后还能分配、建 stream，RDMA 写入的数据正确、速度不变。
3. **端到端**：GLM-5.2 PD 生产配置在 6.19 节点上起栈并计分，与 6.16 同配置对比。
