# 目标是 Pareto 曲线：TP8 decode 还能往哪里发力（2026-11-12 07:30）

## 0. 先修正复盘的前提

目标是 InferenceX 上的 Pareto 曲线（每 GPU 吞吐对交互度）尽量接近或超过 NV Dynamo + SGLang 的 GB300，而不只是最高吞吐。

- decode 变快会降低 ITL、提高交互度，让曲线上的点右移；同样的交互度下，还能多接并发，吞吐也会上去。所以 decode 侧的工作是有效的。
- `REVIEW-20261112` 里"decode 工作对计分没用"的说法只对"PP8 1P1D 的最高吞吐那一个点"成立，对整条曲线不成立。
- prefill 仍然决定曲线最右端那个点（最高吞吐）。所以两条线都要做：decode 管曲线的大部分，prefill 管最右端。

## 1. 回答：TP8 decode 是不是能发力的地方

**是，而且主要在 MoE。**

### 1.1 KF 在 TP4 做到了什么、TP8 差在哪

11-04 的交接分析（`TP8-KERNEL-HANDOFF`）：
- TP4 的 decode 固定开销正好压在带宽下限上（21.3 vs 21.6 ms），KF 的 MoE kernel 读权重达到 5.81 TB/s（峰值的 73%）。
- TP8 的固定开销比下限高约 4 ms（17.8 vs 13.6 ms），原因是 MoE 没用上 KF 的 kernel：
  - KF 的 gemm1（BM16、激活预量化）、atomic 版 gemm2、融合排序都只为 TP4 的每卡中间维 512 写过；
  - TP8 每卡中间维是 256，走的是 aiter 原版 kernel，只有 4.18 TB/s（52%），当时估计还有约 5.6 ms/步的空间。

之后做的两件事：
- **MoE 调优表补行：**M 704 时每次 −12%。
- **MegaMoeTP：**把 all-gather + MoE + reduce-scatter 合成一个 kernel，通信被完全藏住了，graph 内每步 −1 ~ −4 ms。
- **但它内部 GEMM 的效率和生产 GEMM 差不多，没有达到 KF 的水平。**

### 1.2 现在的差距

TP8 每卡每层 MoE 权重约 644 MB（MXFP4），75 层共 48.3 GB：

| 路径 | 每层 µs | 有效带宽 |
|---|---|---|
| MegaMoeTP，graph 内（c160，每卡约 20 个请求） | 196.7 | 3.28 TB/s |
| MegaMoeTP，microbench（640 token，q3） | 171.5 | 3.76 TB/s |
| MegaMoeTP，microbench（768 token，q3） | 178.1 | 3.62 TB/s |
| 生产路径只算 GEMM（384 / 768 token） | 132.7 / 184.9 | 4.85 / 3.48 TB/s |
| **TP4 上的 KF（参照）** | — | **5.81 TB/s** |

- 达到 5.0 TB/s：每层约 129 µs，每步省 3.2 ms（对比 microbench）到 5.1 ms（对比 graph 内）。
- 达到 5.8 TB/s：每层约 111 µs，每步省 4.5–6.4 ms。
- 繁忙时（每卡 batch 16–24）一步是 37–43 ms，**这相当于同并发下交互度提高约 10–17%**，是目前看得到的最大一块。

### 1.3 TP8 的 MoE 为什么更难

这几条是根据已有测量做的判断，还没逐一验证：
- **gemm2 的 K 只有 256：**每个输出要和 9 个专家的结果相加。生产路径是 bf16 atomic 写回，实测受 atomic 限制，没有受读权重限制。
- **token 越多效率越低：**生产路径在 384 token 时有 4.85 TB/s，768 token 时降到 3.48 TB/s。这和"受写回 / 归约限制、不受读权重限制"一致。
- **MegaMoeTP 的尾巴：**这两天的插桩显示，GEMM 后的尾巴来自 GEMM2 列组粗粒度和 CTA 间负载不均。q3 修掉了一部分；GEMM 阶段本身仍约 4 TB/s。

## 2. 对 Pareto 曲线有用的 TP8 decode 项目（按收益排）

| # | 项目 | 每步估计 | 作用在曲线的哪段 | 状态 |
|---|---|---|---|---|
| 1 | **TP8 MoE GEMM 效率提到 5 TB/s 以上**（改 MegaMoeTP 内部，或把 KF 的 gemm1 / atomic gemm2 / 融合排序移植到中间维 256） | **−3 ~ −6 ms** | 中高并发（batch ≥ 8） | 需要几天的 kernel 工作；第一步见第 3 节 |
| 2 | sparse MLA 超过 2 GiB：KV 上限，或拆两段 | −1.1 ms 或 −0.28 ms | 全段 | 实验配置已就绪 |
| 3 | 繁忙时的 indexer（> 48 行走标准路径，每层约 115 µs） | 约 −1 ms（待量） | batch ≥ 13 | 73j trace 分析在排队 |
| 4 | **MegaMoeTP 在小 batch 变慢**（batch 2–7 每步慢约 1 ms） | +1 ms 要修回来 | **低并发、高交互度一端** | 可以低于某个 token 数就切回生产路径；要先量清楚 |
| 5 | 窄 GEMM 合并 + 调优表 | −0.35 ms | batch ≥ 13 / 全段 | 原型和实验配置已就绪 |
| 6 | MegaMoeTP q3 | −0.3 ms | 中高并发 | 实验配置已就绪 |
| 7 | 小 kernel（norm 等每个约 4 µs，共约 1.1 ms）的融合 | 约 −0.5 ms | 低并发一端更明显 | 未开始 |

第 2、5、6 项加上第 1 项的下限，繁忙时每步合计约 −5 ~ −8 ms（约 −13% ~ −20%）。

## 3. 建议：下一阶段以 TP8 MoE 为主线

1. **先量清楚（约 1 天，只用 microbench 和插桩）：**
   - 用已有的逐 CTA 时间戳，把 MegaMoeTP 的 GEMM1 和 GEMM2 分开计时，在 128 / 256 / 384 / 640 / 768 token 下各看一遍；
   - 用 rocprof 硬件计数器看各阶段受什么限制：读权重带宽、atomic / 归约、占用率、负载不均；
   - 对照 KF 中间维 512 的 kernel 用了哪些手段，判断哪些能搬到 256。
2. **再决定路线：**
   - 改 MegaMoeTP 内部：它是 FlyDSL 写的，源码在手，插桩已经做过，能保住通信重叠；
   - 或者 KF 风格的 GEMM 加独立通信：KF 的 kernel 更高效，但会丢掉通信重叠。
   - 目标：640 token 时每层 ≤ 130 µs（≥ 5 TB/s），精度与生产相当。
3. **小 batch 的回退：**给 MegaMoeTP 加一个"低于 N 个 token 就走生产路径"的门槛，修掉曲线高交互度一端的约 1 ms 退步。
4. **交付形式：**InferenceX 不允许 overlay / 运行时替换函数（交接文档第 6 节），所以最终要以 aiter / SGLang PR 交付。现在的 overlay 和补丁只用于实验。

## 4. 怎样衡量曲线右移（不依赖长计分）

- **step 曲线：**用已有的固定并发合成 decode 负载，在每卡 batch 4 / 8 / 12 / 16 / 20 / 24 下测各实验配置的 graph 内步长，得到"步长–batch"曲线。交互度约等于接受长度 ÷ 步长，可以直接换算曲线右移多少。
- **端到端：**再挑 2–3 个 AgentX 并发点（例如低、中、高各一），在同一对节点上背靠背确认。
- **对标：**最好有 GB300 曲线上我们要追的那几个点（交互度、吞吐），用来把目标换算成每个并发下需要的步长。
