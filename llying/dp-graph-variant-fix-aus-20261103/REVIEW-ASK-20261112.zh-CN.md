## 3. 排除掉的方向（microbench 证明没有收益或不可行）

- **lm_head 换 kernel：**最快的 kernel 只比 `torch.matmul` 快 1–14%，每步约 20 µs。
- **窄 GEMM 换 aiter Triton kernel：**全部比生产慢。
- **MTP 层 MoE：**已在带宽上限（约 6.6 TB/s）。
- **draft 的 sparse kernel：**价值低（每步合计约 0.24 ms）。
- **MegaMoeTP 的其他参数：**在新宽度下重扫 mt / npp，最优组合不变；自定义列组宽度和 q=3 效果相同。
- **sparse MLA 的另外 4 种写法：**都不可行。
- **dense FP8：**11-06 试过，每步反而慢 0.4 ms。

## 4. 为什么建议现在复盘

1. **收益在递减。**单个 kernel 调参每项只剩 0.1–0.3 ms / 步。剩下的大头要么需要决策，要么需要更大的工程：
   - MegaMoeTP 占 46%，GEMM 已接近生产，剩下主要是各卡到达不齐，约 0.75 ms；
   - 繁忙时的 indexer 约 2.4 ms / 步，"分段调用融合 indexer"的收益还没量；
   - dense FP8 要动精度；KV 上限要牺牲容量。
2. **积压了 5 个没做端到端的实验配置**（q3、sparse2g、kvcap、gemmtab、gemmmerge）。microbench 的收益相加，不一定等于端到端的收益：graph 内的各卡不齐、调度、PD 交互都会吃掉一部分。继续堆 microbench 收益，风险越来越大。
3. **端到端的可比性问题还没解决：**不同节点对之间 prefill 差 10%，64c 和今天的基线差异没有查清，抢占又让 1 小时以上的计分经常失败。不先定好测量方法，后面的端到端结果也难以解读。
4. **我的执行问题：**
   - 几次测试因为我的错误要返工：编译缓存没清、列块数算错、TP4 的偶然快值当成了结论、测试写得太严、两个导入钩子互相递归；
   - 11-11 17:00 后我没挂定时心跳，机器夜里空闲了几段。
   这些值得在复盘里一起看。
