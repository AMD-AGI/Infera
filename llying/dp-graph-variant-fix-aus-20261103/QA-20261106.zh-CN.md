## 二、decode 在线 FP8 为什么没有收益——从零讲

### 1. decode 每一步在做什么

decode 每一步给每个正在生成的请求各产出几个 token（MTP K3 时每个请求验证 4 个 token）。这一步里，模型的每一层都要把"这一步所有
token 的向量"乘上这一层的权重矩阵：

    输出 [M × N] = 输入 [M × K] × 权重 [K × N]

- **M**：这一步、这张卡上的 token 数。C104 时每个 decode rank 大约 16 个请求，× 4 个 token = 约 64 行，范围约 16-128。
- **K、N**：权重矩阵的形状，是固定的，例如 `o_proj` 是 16384 × 6144。

### 2. 为什么 decode 的 GEMM 由"读权重"决定（访存受限）

一次 GEMM 的耗时取下面两者的较大者：
- **计算时间** = 2·M·K·N 次运算 ÷ 算力；
- **访存时间** = 权重字节数 ÷ 显存带宽。

M 很小时，权重矩阵很大、运算很少：以 M=64 为例，每读 1 字节 BF16 权重只做约 64 次运算，而 MI355X 要每字节约 300 次运算以上，
算力才会成为瓶颈。所以 decode 的 GEMM 基本是**在等权重从显存读进来**，时间 ≈ 权重字节数 ÷ 实际达到的带宽。

### 3. 为什么当初预期 FP8 有收益

BF16 每个权重 2 字节，FP8 每个权重 1 字节。dense 层权重从每卡 21.9 GB 变成 10.9 GB，要读的字节减半。如果带宽利用率不变，这部分
GEMM 时间应该减半：每步从约 6.6 ms 降到约 3.3 ms。另外每卡省出 10.9 GB 显存，KV cache 多了 7.7%，能多容纳一些请求。

### 4. 实际测到的（单节点 C104，decode rank 0 每步内核耗时，dense FP8 对基线）

| 项目 | 基线（BF16） | dense FP8 | 变化 |
|---|---|---|---|
| dense 层 GEMM | 6.6 ms（读 21.9 GB，等效 3.3 TB/s） | 6.06 ms（读 10.9 GB，等效 **1.8 TB/s**） | -0.54 ms |
| 激活量化（新增的内核） | 0 | 1.08 ms | +1.08 ms |
| indexer（DSA 稀疏注意力选 token） | 1.61 ms | 2.28 ms | +0.67 ms |
| 草稿模型 MoE（副作用，见下） | 1.84 ms | 1.05 ms | -0.8 ms |
| **合计** | | | **约 +0.4 ms，每步反而稍慢** |

每步耗时稍慢，但 KV 多了 7.7%，decode 能同时跑更多请求：最忙 rank 的在跑请求中位从 16 升到 17，decode 在跑总数从 50 升到 54。两者相抵，吞吐
基本不变（53,176 对 53,209）。每个请求分到的速度下降，交互 p90 降了 9%。

### 5. 第一个原因：小 M 下 FP8 GEMM 没有跑满带宽

权重少读了一半，时间只少了 8%，说明 FP8 内核只用到约 1.8 TB/s 带宽（BF16 内核有 3.3 TB/s，显存实际可达约 5-6 TB/s）。

每步有约 240 次 FP8 GEMM（78 层 × `fused_qkv_a` / `q_b_proj` / `o_proj` 3 个，加上 3 层 dense MLP 各 2 个），平均每次读约 45 MB、
用时约 25 µs。这么小的 GEMM，固定开销占比很大：
- **启动、收尾**：内核开始和结束时并不是所有计算单元都在读数据；
- **并行度**：M 很小时，输出矩阵按 M 方向切不出几块，只能靠 N 方向（或把 K 方向切开再合并，即 split-K）把工作分给 256 个计算单元；
  N 较小的层（如 `fused_qkv_a`）分不满；
- **内核选择**：aiter 按 M 查调优表，查不到精确 M 时向上取整到 128 的倍数或下一个 2 的幂，选到的内核未必最适合实际 M。

调优工具单独测 `o_proj` M=16 时能到 19.5 µs、5.2 TB/s，说明大矩阵能跑满；拉低平均值的是较小的矩阵和真实运行时的上述开销。
具体是哪几个形状慢，trace 里还没有按形状拆开（这是下面交接项 1 的第一步）。

### 6. 第二个原因：激活量化是额外的一步

FP8 GEMM 要求两个输入都是 FP8。权重在加载时量化一次就好；激活（每层的输入向量）每一步都不同，所以**每次 GEMM 之前**都要：
求每一行的最大绝对值 → 算缩放系数 → 把每个数除以系数转成 FP8。

这一步由一个单独的内核完成：SGLang 的 Triton 内核 `_per_token_group_quant_8bit`，每步 240 次、共 1.08 ms，平均每次约 4.5 µs。
它处理的数据很少（64 行 × 几千列），时间主要花在启动和一次额外的显存读写上。**它的开销（1.08 ms）比 FP8 GEMM 省下的时间
（0.54 ms）还多。**

### 7. 第三个原因：indexer 换到了慢路径（与 FP8 本身无关）

GLM-5.2 用 DSA 稀疏注意力：每一层先由一个小模块"indexer"给历史 token 打分，挑出最相关的一部分再做注意力。yihou 的 KF overlay
有一个更快的融合版 indexer 内核（`fused2`），但它的工作划分是"每 6 行一组、最多 16 组"，所以只支持行数是 6 的倍数且 ≤ 96 的
batch，其他情况回退到较慢的 `preshuffle` 内核。

dense FP8 下 KV 更多、每 rank 同时跑的请求更多，batch 更常超出这个范围：fused2 的使用比例从基线的 38% 掉到 0%，每步多 0.67 ms。
这个限制在基线里同样存在（基线也有 62% 的调用走慢路径），所以修好它对所有配置都有收益。

### 8. 一个意外的收益

dense FP8 的配置同时打开了 `SGLANG_USE_AITER_FP8_PER_TOKEN=1`，副作用是草稿模型的 MoE 换成了 aiter 的 per-token FP8 内核，每步快
0.8 ms。后来单独测这个开关（条目 21，n10-29）：C104 53,129，基线 53,209（n02-33）/ 53,057（n04-33），**端到端看不出收益**。
trace 里省的 0.8 ms 为什么没有体现在吞吐上，还没有查。

### 9. +8%-12% 是怎么推算的

假设三项都修好：
- FP8 GEMM 达到约 3.3 TB/s → 约 3.3 ms，比 BF16 基线省约 3.3 ms；
- 激活量化融合掉约 2/3 → 剩约 0.4 ms；
- indexer 全走 fused2 → 省 0.5-0.7 ms。

合计每步比基线快约 3-4 ms。C104 下每步约 40 ms，即快 7%-9%；再加上 KV 多 7.7% 能多容纳请求，同交互下吞吐约 +8%-12%。

这是按内核耗时推算的，没有实测。实际收益会打折：每步变快后，瓶颈可能转到 prefill。

## 三、内核交接项（what / why / how）

### 交接项 1：小 M 的 FP8 GEMM（a8w8 bpreshuffle，per-token 激活 × per-channel 权重）

- **What**：aiter `gemm_a8w8_bpreshuffle` 在 decode 形状上的内核。trace 里实际跑的是 FlyDSL `kernel_gemm_0`（每步约 219 次）和
  CK-tile `FlatmmKernel`；SGLang 在条件满足时还会选 `smallm_fp8_gemm`。
  - 形状：M 4-256；N×K 为 `q_b_proj` 16384×2048、`o_proj` 6144×16384、`fused_qkv_a`、dense `gate_up` 24576×6144、dense `down`。
- **Why**：decode 的 dense 层 GEMM 是访存受限的，FP8 应该接近减半，实际只达到约 1.8 TB/s。如果能达到约 3.3-4 TB/s，每步约省
  2.5-3 ms（约 6%-7%），dense FP8 才会有收益。
- **How**：
  1. 用 rocprof 按形状拆开 trace，找出带宽最低的形状（预计是 N 或 K 较小的 `fused_qkv_a`、`q_b_proj`）；
  2. 对这些形状在实际 M（16、32、64、128）下做单算子测试，与 BF16 hipBLASLt 同形状对比；
  3. 针对小 M 选或写内核：M 方向用小 tile（16 / 32）、对 N 小的层用 split-K 或 stream-K 把 256 个计算单元填满、宽向量加载
     preshuffle 权重、把缩放系数乘法放进收尾；
  4. 检查查表逻辑：实际 M 都应命中精确调优行，避免取整后选错内核；
  5. 在 CUDA graph 回放下测，把内核之间的间隙算进去。
  - 基础：aiter 2bb549102（v0.5.22 镜像）；调优表放在 `dense-fp8/tune/`。

### 交接项 2：激活量化融合

- **What**：每个 FP8 GEMM 前的 per-token 激活量化，每步 240 次、1.08 ms（Triton `_per_token_group_quant_8bit`）。
- **Why**：单独一个内核，启动开销加一次额外的显存读写，开销比 FP8 GEMM 省下的还多。融合后约省 0.7 ms / 步。
- **How**：把量化合进"产生这个激活的上一个内核"，让它直接输出 FP8 和缩放系数。SGLang 的 aiter 线性层已经支持直接接收预量化的
  `(fp8, scale)` 输入（`apply_fp8_linear` 的 tuple 分支，原本给"融合 RMSNorm + 量化"用），所以主要工作在模型侧接线：
  - `fused_qkv_a` 的输入来自 `input_layernorm`，dense `gate_up` 来自 `post_attention_layernorm`：用 RMSNorm + per-token 量化
    融合内核（aiter 有 `rmsnorm2d_fwd_with_dynamicquant` 等）；
  - `q_b_proj` 的输入来自 `q_a_layernorm`：同上；
  - dense `down` 的输入来自 SiLU×mul：用 aiter 的 `silu_and_mul_quant`；
  - `o_proj` 的输入来自注意力输出，没有现成的融合点（78 次 / 步），暂时保留单独量化。

  这样 240 次中约 162 次可以融合掉。另一条路是改用 block-scale FP8（每 128 列一个缩放系数），SGLang ROCm 的 DeepSeek FP8 路径
  已经有融合的 RMSNorm + 分组量化，但权重量化方式和 GEMM 内核都要换，改动更大。

### 交接项 3：KF 融合 indexer（`fused2`）扩展

- **What**：yihou KF overlay 的 `kf_indexer.py` 中的 `_gluon_paged_mqa_logits_fused2`。限制来自 `_LPT_GROUP_ROWS=6`、
  `_LPT_NG2=16`：只支持行数是 6 的倍数且 ≤ 96。
- **Why**：超出范围就回退 `preshuffle`。基线只有 38% 的调用用上 fused2，dense FP8 下是 0%。全部走 fused2 约省 0.5-0.7 ms / 步，
  对所有配置都有效（不依赖 FP8）。
- **How**：
  - 行数不是 6 的倍数：补齐到 6 的倍数，补出的行做掩码；
  - 行数 > 96：增加组数（放大 `_LPT_NG2` 或拆成多个 CTA / 多次调用）；
  - 与 preshuffle 路径逐元素对比结果；
  - 检查 CUDA graph 各批大小的补齐是否一致。

  交给 yihou 或 KF 维护者，配合 yihou 的上游 PR。

### 交接项 4：TP8 的 MoE（2P1D 的 TP8 decode，11-04 trace）

- **What**：TP8 decode 下，MoE 的三个部件都没用上 KF 内核，回退 aiter 原版。MoE 每步 12.5 ms，按读权重字节数估算应为约 8.3 ms。
- **Why**：约 5.6 ms / 步的空间，决定 2P1D / TP8 配置能否超过 4+4。
- **How**：以 v0.5.22 镜像的 aiter MXFP4 fused MoE 为基础，让 KF MoE 内核支持 TP8 的形状（每 rank 的 intermediate 维度是 TP4 的
  一半），或为 TP8 形状单独调优 aiter MXFP4 MoE；用 TP8 trace 逐部件对比。与交接项 1-3 独立。

- QA-20261105 第二节（2）的表里写"运行时激活量化：`aiter.per_token_quant_hip`"，不准确。dense FP8 的线性层走 SGLang 通用的

## 五、K5 C88 为什么会崩溃？能否讲清楚？是否重测？（15:18 的问题）

**能讲清的部分：什么时候、在哪里崩。讲不清的部分：是哪个内核、为什么。后者还需要一次专门的复现实验。**

### 1. 现象（3 次都一样）

| 运行 | 节点 | 起栈后多久崩溃 | 崩溃前最忙 rank 的在跑请求 |
|---|---|---|---|
| 24（09:21） | n06-33 | 27 min | 22 |
| 24r（10:25） | n06-33 | 26 min | 24 |
| 24s（10:57） | n10-29 | 29 min | 25 |

崩溃全过程最忙 rank 达到过 24-28 个在跑请求。三次都是 decode 进程打印
`rocdevice.cpp:3582 ... Queue 0x7fbb04800000 Aborting with error : HSA_STATUS_ERROR_OUT_OF_RESOURCES`，随后
`Fatal Python error: Aborted`，整个 decode 退出。日志在 `/perf_apps/liyingli/vfix-logs/v2/crash-k5-c88/`。

### 2. 这个错误是什么意思

这一行是 ROCm 运行时在 **GPU 硬件队列报错时** 打印的：某个提交到这条队列的内核在启动或运行时出错（拿不到所需的资源，如寄存器、
LDS、scratch 私有内存，或运行中访问越界），运行时随即中止整个进程。它**不是**显存不够：
- 崩溃时 KV 用量 0.62-0.90；
- KV 池在启动时就预分配好了；
- 显存真正不足时报的是 PyTorch 的 OOM，不是这一行。

### 3. 已经排除的

- **节点问题**：两台不同的机器都崩了。
- **退出 CUDA graph 走 eager 路径**：三次崩溃前所有 decode batch 都在用 CUDA graph（1,182 / 1,026 / 1,388 行全部 `cuda graph: True`）。
- **偶发**：3 次全崩，时间点接近。

### 4. 触发条件（推断）

只有"K5 + 高负载"会崩：
- K5 C64 跑了三轮（pkg kit、v2 kit、DP 均衡各一轮），最忙 rank 约 14-18 个请求，没有崩；
- K3 在 C104 / C112 下最忙 rank 也有 24 个左右请求，但每个请求只验证 4 个 token，也没有崩；
- K5 C88 在 26-29 min 时，KV 填满、最忙 rank 涨到 24-28 个请求。K5 每个请求验证 6 个 token，所以 target verify 一次要算
  144-168 行，比此前任何稳定配置都多（K3 约 96 行，K5 C64 约 84-108 行）。

推测：负载第一次涨到这么高时，decode 用到了 K5 下最大的那几个 CUDA graph 批，其中某个内核在 144-168 行这个形状下出错。可能的
内核：KF 的 MoE / indexer / 稀疏注意力内核，或 aiter 的内核。**这一点没有证实。**

### 5. 怎么定位（交给下一个 agent / 内核同事）

1. **缩短复现时间**：起 K5 部署后直接施加让单个 rank 跑 24-28 个请求的负载，或用 SGLang 的单批测试在 bs 24-28、K5 下跑
   target verify，不必等 26 min。
2. **关掉 KF 内核对照**（`KF_KERNELS=0`）：如果不再崩，问题在 KF 内核；否则在 aiter / SGLang 原版。
3. **在复现里打开 `AMD_LOG_LEVEL=1`、`HIP_LAUNCH_BLOCKING=1`**，找出是哪个内核出错；这两个开关会拖慢速度，只在复现时用。
4. **临时规避**：K5 下把 CUDA graph 最大批或每 rank 最大在跑请求数限制在约 20。

### 6. 是否重测

- **为 Pareto 出数：不需要。** 按 K3 / K5 交叉点的实测（最忙 rank 超过约 14-16 个请求后 K3 更划算），C88 时最忙 rank 经常在 20 以上，
  本来就该用 K3。补测的"DP 均衡 + K3 C88"就是这个点。
- **为查清崩溃：需要**，但按上面的方法做专门的复现，而不是再跑一次 3600 s 的 sweep。

### 7. 补充（11-06 15:50，日志复查）：K5 的显存余量只有 K3 的三分之一，崩溃都在 KV 接近满载之后

**更正第 1 小节的表**：表中"崩溃前最忙 rank 的在跑请求 22 / 24 / 25"是**整次运行的峰值**（逐行统计为 28 / 24 / 25），不是崩溃那一刻。
崩溃前最后一行各 rank 的在跑请求是：24（09:21）8 / 22 / 8 / 15，24r 13 / 8 / 12 / 24，24s 9 / 17 / 8 / 10。所以崩溃并不是发生在
batch 最大的那一步，第 4 小节"某个内核在 144-168 行时出错"的推测证据不足。

**新发现 1：K5 捕获完 CUDA graph 后，每个 decode rank 只剩 2.1 GB 空闲显存，K3 有 6.0 GB。** 来自 decode 日志启动段
（`Capture ... CUDA graph end` 与 `available_gpu_mem`），v2 的全部 15 次运行都一致：

| 配置 | target verify graph 占用 | 捕获完后空闲（每 rank） | 结果 |
|---|---|---|---|
| K3（C88 / C104 / C112，含 DP 均衡） | 7.63 GB | 6.03 GB | 全部正常 |
| K5 C32 / C48 / C64（含 DP 均衡 C64） | 10.52-10.54 GB | 2.09-2.10 GB | 正常 |
| K5 C88（3 次） | 10.52 GB | 2.10 GB | 3 次崩溃 |

原因：K5 每个请求验证 6 个 token（K3 是 4 个），target verify 的 graph 内存池大了约 2.9 GB；draft decode / draft extend 的 graph 也更大。
KV 池按 `mem-fraction-static 0.95` 预先划走，剩下的就只有这 2.1 GB。

**新发现 2：三次崩溃都发生在某个 rank 的 KV 用量第一次达到 ≥ 0.98 之后 1-4 分钟。**

| 运行 | 起栈 | 第一次 KV ≥ 0.98 | 崩溃 | 间隔 |
|---|---|---|---|---|
| 24（n06-33） | 08:53:57 | 09:18:32（DP2） | 09:21:01 | 2.5 min |
| 24r（n06-33） | 09:58:40 | 10:23:25（DP3） | 10:24:21 | 56 s |
| 24s（n10-29） | 10:28:41 | 10:53:15（DP3） | 10:57:22 | 4.1 min |

对照：K5 C32 / C48 / C64 的 KV 峰值只有 0.57 / 0.70 / 0.94，从没到满载；只有 DP 均衡 K5 C64 到过 1.00，那一轮没有崩溃（一个反例）。
K3 的 C88 / C104 / C112 每轮都到 1.00，从来没崩。日志里没有 retract、OOM 记录，KV 满时 decode 只是暂停接收新的传输。

**这两条说明什么（推断，未证实）**：`HSA_STATUS_ERROR_OUT_OF_RESOURCES` 是 ROCm 运行时在队列上申请资源失败时报的，最常见的情况是
内核需要更多 scratch（每个线程的私有内存）时，运行时去显存里临时申请、申请不到。这块显存不归 PyTorch 管，KV 池和 graph 池
之外剩下多少，它就只能用多少。高负载、KV 接近满载时，PyTorch 在 graph 之外的临时张量（调度、采样、DP 同步、传输元数据）
也会让缓存分配器多占一些显存。K5 的余量只有 2.1 GB，最先被耗尽；K3 有 6 GB，所以同样满载也不崩。这个解释和"只有 K5 + 高负载才崩"
"三次都在 26-29 min""换节点照样崩"都对得上，但还没有直接证据（比如崩溃前的显存曲线）。
