# 总体复盘（2026-11-12 07:15 UTC）

## 0. 最重要的结论

**这三天的 kernel 工作几乎都在 decode 侧，而最高分配置（PP8 1P1D，16 卡，56,593 tok/s/GPU）的吞吐瓶颈在 prefill。**

- 11-09 完整计分已经证明：decode 变快不会提高这个配置的吞吐。MegaMoeTP 的同节点对比又印证了一次：decode 每步快 2–4 ms，吞吐持平。
- decode 侧的优化只在 4+4 单节点（8 卡，瓶颈在 decode）上能变成吞吐，而且量级只有约 1–2%。
- 要提高最高分，应该把重心转到 **PP8 的长上下文 prefill**：
  - 第一步是做一次 prefill profile。11-09 起就被反复建议，但一直没做。
  - 按 11-09 的推算，如果 prefill 不再排队，同样 C208 下吞吐约 +15%（推算，未实测）。

## 1. 目标与现状

- **分数：**AgentX 吞吐（tok/s/GPU），其中 99% 以上是输入 token（大部分命中缓存）；交互度是辅助指标。AgentX 是闭环回放：每个 lane 发一个请求、等它完成、再发下一个。所以吞吐 = 并发 ÷ 每个请求的周期。
- **三个部署形态的现状**（11-04 ～ 11-09 的 3600 s 计分）：

| | PP8 1P1D C208（16 卡） | 2P1D C208（16 卡） | 4+4 C104（8 卡） |
|---|---|---|---|
| 吞吐 tok/s/GPU | **56,593**（11-06）/ 56,595（11-09 kopt-nocap） | 54,094 | 53,666（两节点）|
| 瓶颈 | **prefill**：长上下文计算 + 排队，88–92% 的时间有排队 | prefill | **decode** |
| TTFT 占请求周期 | **26%**（均值 10.8 s） | 19% | 19% |
| decode 占请求周期 | 38%（15.8 s / 41.3 s） | 40% | 48% |

- **PP8 的 prefill：**流水线是满的，没有调度空泡。但上下文涨到每批约 25 万已缓存 token 后，每级耗时从约 140 ms 翻倍到约 310 ms，而新 token 只多了约 20%。增加的部分取决于已缓存上下文的长度，可能来自三处，还没拆开：
  - DSA indexer 对全部上下文打分；
  - 稀疏注意力的 top-k 选择；
  - HiCache 回载。

  另外，排队等 prefill 的请求还提前占住了 decode 的 KV：decode 的 KV 九成时间是满的。
- **TP8 decode 每步的构成**（c160 合成负载，每个 verify 步每卡 32.1 ms kernel 时间）：

| 类别 | 占比 |
|---|---|
| MegaMoeTP | 46% |
| 稠密 GEMM | 23% |
| sparse MLA | 12% |
| MLA 的两个 BMM | 7% |
| indexer | 5% |
| norm | 3% |

  draft 图每步另有约 2.4 ms。

### 2.3 排除掉的方向

- lm_head 换 kernel（每步约 20 µs）；
- 窄 GEMM 换 aiter Triton kernel（全部更慢）；
- MTP 层 MoE（已在带宽上限）；
- draft 的 sparse kernel（价值低）；

- AKLR 现成 kernel（与生产持平，越过 CI 的测试点会算错）。

## 3. 为什么会错位

1. **证据早就有：**11-09 13:40 的瓶颈分析（`BOTTLENECK-PP8` 第 4b 节）从完整计分里得出"decode 变快不会提高吞吐"，并建议先做 PP8 prefill profile；KERNEL-PLAN 也写了"要提吞吐需要看 prefill，建议尽早做"。
2. **但工作排序是按 decode 每步的 kernel 时间定的**（11-09 的 kernel 待办表按"TP8 每步收益"排序）。之后的安排——TP8 MoE 优先、MegaMoeTP、sparse MLA 的 2 GiB 问题——都是 decode。
3. **我的问题：**每次排计划时，我没有把"这一项对计分有没有用"放在第一位、也没有明确提醒你。MegaMoeTP 计分出来"吞吐持平"时，我把原因解释成"PP8 吞吐由 prefill 决定"，但没有据此建议转向。这次复盘应该把这一点纠正过来。

## 4. 测量与验证的问题

- **节点对差异：**同样的配置换一对节点，PP8 吞吐能差 4%。差异出在 prefill 每块耗时（323 vs 362 ms），配置、镜像、负载、CPU、功耗都查过，没有找到原因。所以只能在同一对节点上背靠背比较。
- **抢占：**集群给新作业 30 分钟免抢占期，而一次 3600 s 计分要连续约 85 分钟，经常跑不完；1500 s 窗口的分数又不能和 3600 s 的直接比。
- **积压：**有 5 个实验配置没做端到端（q3、sparse2g、kvcap、gemmtab、gemmmerge），TP4 调参后的 MegaMoeTP 也没计分。
- **microbench 收益不能直接相加：**graph 内各卡到达不齐（MegaMoeTP 在 graph 内比单算子多约 10 µs）、调度、PD 交互都会吃掉一部分。

## 6. 建议的下一阶段

### 6.1 PP8 1P1D（最高分，prefill 受限）——建议作为主线

1. **先做 prefill profile**（约半天）。在 PP8 计分的长上下文阶段，或用合成负载复现"每批约 25 万已缓存 token"，抓 prefill 的 trace，把每级约 310 ms 拆成 indexer 打分、top-k、稀疏注意力、MoE、HiCache 回载、通信。之后的方向都取决于这一步。
2. **根据 profile 选 prefill 的 kernel 目标。**候选：
   - prefill 的 indexer logits / top-k（每个新 token 每层要在约 25 万个分数里选 2,048 个）；
   - 稀疏注意力的 prefill 路径；
   - HiCache 回载的重叠。
3. **dense FP8 只开 prefill：**11-06 在 4+4 上测过，prefill 满块快 8%，但当时 4+4 的瓶颈在 decode，所以吞吐没变（−0.1%）。**它从没在 prefill 受限的 PP8 上测过**，在 PP8 上可能直接变成吞吐。要过精度评测，需要你决定。
4. **减少排队请求占用的 decode KV**（例如晚一点预分配）：只有在 prefill 不再是上限时才会变成吞吐，排在后面。

### 6.2 4+4 单节点（decode 受限）

把 decode 侧的收益打包成一个组合配置：TP4 MegaMoeTP q3、GEMM 合并 + 调优表、absorb、K5 等。在同一台节点上和基线比一次 1500 s 计分，预期吞吐 +1~3%。这需要一个单节点作业，你之前选了暂不提交。

### 6.3 PP8 的 decode 侧项目

继续保留实验配置，只用于改善交互度，优先级排在 prefill 后面。正在排队的 indexer 分段调用测量也是 decode 侧的，可以跑完记录，但不再往下投入。

## 8. 端到端验证方案（建议）

- **先测组合，再拆分：**每个形态先用一个"全部打开"的配置和基线在同一次分配、同一对节点上背靠背比；有收益再决定要不要逐项拆开测。
- **同时记录 prefill 每块耗时：**用来判断两次运行的节点状态是否可比；prefill 差超过 3% 的比较不下结论。
- **应对抢占：**用 1500 s 窗口；decode 侧的效果用 graph 内合成负载 trace 确认，不依赖长计分。
- **形态与指标对应：**PP8 看吞吐时只评 prefill 侧的改动；decode 侧的改动在 PP8 上只看交互度，在 4+4 上看吞吐。
