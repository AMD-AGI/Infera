# 从原始 trace、日志和源码重做的 decode kernel 分析（2026-11-12 14:00 UTC）

对象：GLM-5.2 MXFP4，MI355X，SGLang PD 分离的 decode 侧（TP8 + DP attention 为主，TP4 对照）。
这份报告不沿用之前报告里的数字，全部从原始 trace（352 个文件）、计分运行的 decode 日志（35 个引擎）、镜像里的 SGLang / aiter 源码和 checkpoint 配置重新得出。
脚本、中间数据和明细表在 `kreview-20261112/`（本目录下的副本）和 `/perf_apps/liyingli/bench_agentx/kreview-20261112/`（含压缩后的 trace 数据）。

名词（全文只用这几个）：
- **graph batch**：DP attention 下每一步所有卡执行同一个 CUDA graph，它的 batch = 最忙那张卡的在跑请求数，向上取到已捕获的档位（TP8：1–8、10–32 步长 2）。
- **行**：每张卡注意力部分处理的 token 行数 = 每请求行数 × graph batch。MTP 3 步的配置每请求 4 行（模拟接受长度 2.99），MTP 5 步每请求 6 行（3.61）。当前 PP8 生产配置是 MTP 3 步。
- **M**：MoE 看到的全局 token 数 = 卡数 × 行。TP8、MTP 3 步时 M = 32 × graph batch。
- **合成负载**：`synth_decode_load.py`，固定并发、每个 prompt 约 2,048 token。**真实负载**：AgentX，每请求上下文 10 万–25 万 token。

## 0. 结论

1. **之前的优先级是在合成负载、graph batch 20–24 上排的，这两点都和真实运行不符。**
   - PP8 C208 计分运行里，graph batch 的中位数是 10，80% 的步在 7–16，95% 在 4–18；≥ 20 的步只占 2%。
   - 合成负载的上下文只有真实的 1–2%，所有随上下文增长的 kernel（indexer 打分、top-k 的一遍扫描、draft_extend 里的 indexer）都被低估了。
2. **MoE 仍然是第一位，而且在每个 batch 上都占 verify 的一半左右**（真实负载、生产路径 54–55%；合成负载、MegaMoeTP 50–56%）。但要处理的范围是 M = 128–576，不是之前写的 384–1024。
3. **indexer 是被低估最多的一项。** 真实负载下它占 verify 的 9–12%（graph batch 12 / 16 / 20：2.7 / 3.6 / 4.5 ms），之前按 5%（1.7 ms）排在第五。
4. **有两类开销之前没有单独列出来，量级和排名靠前的 kernel 相当：**
   - 每个 kernel 约 4 µs 的启动开销：一个 verify 图 1,191–2,082 个 kernel，其中 711–920 个短于 6 µs，合计 3.2–4.3 ms / 步。
   - verify 之外（两个 draft 图加图外 kernel）：真实负载 3.2–4.2 ms / 步，之前按 2.4 ms 算。
5. **低 batch 一端已经贴着显存带宽。** graph batch 1 时 verify 15.8 ms，约等于"读权重 11 ms + 1,191 个 kernel 的启动开销 4.8 ms"。这一端只有两种办法：少读字节（注意力权重现在是 BF16），或者少发 kernel。
6. **GB300 曲线（10-20 的六个点）对我们 decode 的要求：**
   - 最右边两个点（63.6k @ 89.4、55.5k @ 94.7）：交互度一侧要求 p90 步长 ≤ 33.4 / 31.6 ms。我们吞吐最高的那次（56.6k @ 70.9）p90 步长约 42 ms，差约 9 ms；带 kernel 调参和 KV 上限的那次（53.3k @ 80.7）是 36.2 ms，差 3–5 ms。MoE 一项加上把 DP rank 配平，量级上够。吞吐一侧差 11%，在 prefill，不是 decode kernel 的事。
   - 中间两个点（44.5k @ 114.3、28.4k @ 131.8）：需要步长 ≤ 26.2 / 22.7 ms，对应 graph batch ≤ 6 / ≤ 4。按步长曲线估算够得着或接近，但 PP8 只在 C208 测过，没有实测。
   - 最左边两个点（16.9k @ 184.8、8.9k @ 246.3）：需要步长 ≤ 16.2 / 12.1 ms，而我们每卡 1 个请求时就是 16.6 ms。当前权重精度和 kernel 数量下达不到。
7. **一个不是 kernel、但量级相同的因素：DP rank 不均衡。** PP8 运行里 graph 执行的行有 42% 是补齐行（最忙卡是平均卡的 1.64 倍）；补齐行在 MoE 里照样参与路由和计算。TP4 上打开 router 的按请求数均衡后补齐降到 18–22%。PP8 上没有开过。

## 1. 数据和方法

### 1.1 用了什么

| 数据 | 内容 | 处理 |
|---|---|---|
| trace（`/perf_apps/liyingli/vfix-logs/opt/trace/`，3.2 GB） | 35 组采集，每组 4 或 8 张卡 × 40 步。真实负载 10 组（2P1D C208 两组、PP8 C208 两组、TP4 C104 六组），其余是合成负载 | `extract.py` 把每个文件压成只保留 GPU kernel 事件的小文件（共 196 MB），之后不再读原始 trace |
| decode 日志 | 35 个 decode 引擎的 `Decode batch` 行（每卡每 40 步一行） | `logs_batch_dist.py`，结果在 `BATCH-DIST.md` |
| 源码 | 从生产镜像 `infera-sglang:v0522-fdbafb60` 拷出的 SGLang、aiter，加上 overlay 和补丁 | 逐项对照，带 `文件:行号`，结果在 `CODE-MAP.md` |
| checkpoint | `GLM-5.2-MXFP4/config.json` 和量化排除列表 | `hw_model.py` 算每步要读的字节 |
| GB300 | 仓库里 10-27 拉取的 InferenceX API 快照（GB300 的点日期是 10-20） | 直接读。11-12 没有重新拉取；11-13 用户确认先用这份快照 |

日志统计和源码对照是两个子任务做的，我抽查过：日志里的步长和计分文件、和 trace 里的步周期一致（graph batch 12：31.5 对 32.2 ms；16：35.5 对 35.5）；源码对照里的 kernel 名和我解析出的序列逐项对得上。

### 1.2 trace 本身的几个事实（之前没有写明）

- **graph 里的 kernel 是首尾相接的**：每个 kernel 的开始时间等于前一个的结束时间，所以"kernel 时间之和 = 图的墙钟时间"，按 kernel 分账是成立的。
- **GPU 没有空闲**：步周期 = verify + draft + draft_extend + 图外 kernel，剩余不到 0.2 ms。CPU 每步有约 32 ms 在等 GPU。
- **trace 里 GPU 时间轴比 CPU 时间轴晚约 42 ms**（常数偏移），不影响时长。
- **`step[VERIFY bs=N]` 里的 N 是这张卡自己的请求数**，不是 graph batch。同一步里各卡的 N 不同（例如 `[11, 13, 14, 10, 17, 22, 18, 11]`），但执行的是同一个 batch 22 的图。

### 1.3 新脚本和旧脚本的差别

- **按层内位置归类**（`ana2.py`）：沿着一层的执行顺序走状态机，35 组采集的每一步、每一层都能解析，没有落到"其他"的 kernel。旧脚本按名字归类，调优表选出的 GEMM 名字随 batch 变化时会归错或漏掉。
- **按 graph batch 分组**，不跨 batch 合并，也不按各卡自己的请求数分组。
- **集合通信里的等待单独算**：同一层同一步，各卡的 all-gather / reduce-scatter / MegaMoeTP 时长取最小值作为"必需"，其余算"等最慢的卡"。
- **步对齐**：用 verify 图时长序列对齐各卡，35 组都是零偏移。

前 3 层的第 12 步是稠密 MLP。78 层之后是最终 norm、lm_head（每卡 19360 × 6144，BF16，238 MB，输入是全部 M 行）和两次集合通信。

几点和之前说法不同或需要强调的：

- **MXFP4 checkpoint 里只有专家是 4 bit。** 量化排除列表有 1,319 项：所有注意力线性层、indexer、前 3 层 MLP、router、lm_head 都留在 BF16。
- **每步每卡要读的权重（全部专家命中时）是 74.0 GB：专家 48.3 GB，其余 25.6 GB。** 其余部分和 batch 无关，1 个请求也要读满。
- **补齐行在 MoE 里不被屏蔽**：M 行全部参与路由和计算。
- **≤ 48 行时的 4-kernel 融合 indexer 是 SGLang 自带的**（`Gfx950FusedIndexer`，`MAX_ROWS = 48`），不是 KF overlay 的。之前的文档把它记成了 KF 的编译期常数。
- **KF 的 MoE 路径在 M = 97–455 时启用**，对应 graph batch 4–14。在 TP8（每卡中间维 256）上，它做的是：用 KF 的一个 kernel 代替 aiter 的四个排序 / 量化 kernel，并让 aiter 选用 16 行 tile 的 gemm1 和不需要单独归约的 gemm2；KF 专门写的 gemm1 只在中间维 512（TP4）时启用。之前说"TP8 的 MoE 没用上 KF"，只对 graph batch ≥ 16 成立。
- **KF 的 indexer 打分 kernel 有一个"成对共用一遍页表"的版本**，默认要求行数是 6 的倍数且 ≤ 96。每请求 4 行时只有 graph batch 18 和 24 满足。PP8 的配置链里确实没有设置改成按 4 行分组的环境变量（`DSA_LPT_GROUP_ROWS=4 DSA_LPT_NG2=32`），之前查出的这个漏项属实。

### 3.2 换算成 kernel 的 shape

| 对象 | 变量 | 覆盖 PP8 的 95% | 加上 2P1D | 加上低并发点（曲线中段和左段） |
|---|---|---|---|---|
| 注意力侧所有 kernel（投影 GEMM、absorb、sparse MLA、indexer） | 每卡行数 | 16–72 | 到 96 | 4–32（MTP 3 步）；6–48（MTP 5 步） |
| MoE（TP8） | M | 128–576 | 到 768 | 32–256；48–384 |
| lm_head | 行 = M | 同上 | 同上 | 同上 |

实际会出现的取值是离散的：
- 每卡行数：MTP 3 步是 4、8、…、32、40、48、…、128（graph batch 档位 × 4）；MTP 5 步是 6、12、…、48、60、72、…。
- M：行数 × 8（TP8）或 × 4（TP4）。

和之前的说法对比：
- "TP8 需要覆盖的 M 是 384–1024"：PP8 实测 80% 在 224–512，≥ 640 的步占 2%。640–768 只在 2P1D 上常见。
- "繁忙时一步 37–43 ms（batch 16–24）"：PP8 实测步长中位 30.7 ms，p90 34.9 ms。

- **MegaMoeTP 在 graph batch ≤ 10 比生产路径慢 0.3–1.2 ms，≥ 14 才快 0.9–1.7 ms。** 两次运行不在同一对节点上，且生产这次带 KV 上限（sparse MLA 快 0.6–1 ms），所以交叉点有约 ±1 档的不确定。按 PP8 的 batch 分布加权，MegaMoeTP 的净收益在 1 ms 以内。

关于打分 kernel 在真实负载下的行为：
- 源码上，它对每一行遍历该请求的全部缓存 token（每 token 132 B），补齐行的长度只有 2–5。所以读的字节正比于"本卡真实请求的上下文之和"。
- 但实测时长并不随本卡请求数线性增长：PP8 的采集里 5 个请求约 42 µs，9 个以上基本平在 95–117 µs；2P1D 的采集里 9–23 个请求都在 105–125 µs。**更像是由本卡最长的那几行决定**（各行切成固定份数并行，最长的行决定结束时间）。这一点是从数据推的，没有在 kernel 里验证。
- 现有真实 trace 的上下文约是窗口末尾的 0.5–0.7 倍，所以稳态下这一项可能比表里更大。

## 5. 硬件下限和 GB300 目标

### 5.1 MI355X 上每步的下限

每步每卡必须从显存读的量（TP8 + DP attention）：

| 项 | graph batch 1 | 8 | 12 | 20 |
|---|---|---|---|---|
| 专家权重（按均匀路由估命中比例） | 约 30.9 GB（64%） | 48.3 GB | 48.3 GB | 48.3 GB |
| 其余权重（注意力、indexer、lm_head 等，BF16） | 25.6 GB | 25.6 GB | 25.6 GB | 25.6 GB |
| KV gather（行 × 92 MB） | 0.4 GB | 2.9 GB | 4.4 GB | 7.4 GB |
| 按 6 TB/s 读完 | 9.5 ms | 12.8 ms | 13.1 ms | 13.6 ms |
| 按 5 TB/s | 11.4 ms | 15.4 ms | 15.7 ms | 16.3 ms |
| 实测 verify（MegaMoeTP，合成） | 15.8 ms | 22.9 ms | 25.8 ms | 32.1 ms |

- 6 TB/s 的依据：trace 里见过的最好值是 o_proj 在 batch 1 时 5.8 TB/s，TP4 的 KF MoE GEMM 在真实负载下约 6.2 TB/s。显存标称约 8 TB/s（这个数取自 10-21 的对比报告，我没有另行核实）。
- 下限之外还有 kernel 启动开销（现在 4.8–5.9 ms，融合到每层 10 个 kernel 左右约 3 ms）、indexer 读缓存 key（随上下文）、verify 之外的 2–3 ms。
- 粗略地说：**graph batch 8–12 上，把所有 kernel 做到 5 TB/s 并把 kernel 数减到每层约 12 个，步长大约能从 28–31 ms 降到 22–24 ms（−20% ~ −25%）**。这是上界估计，不是承诺。
- 低 batch 一端：graph batch 1 的实测 15.8 ms 里，注意力投影已经是 4.59 ms / 23.4 GB = 5.1 TB/s，MegaMoeTP 约 4.75 TB/s（按均匀路由估）。这一端 kernel 效率的余量很小。

关于 MoE 的"有效带宽"要小心两点：
- 小 M 时并非所有专家都被读到，而真实路由的分布没有导出过。TP4 的 KF GEMM 在合成负载 M = 192 时算出来是 7.3 TB/s，接近标称峰值，多半是没读满。所以 M < 约 400 时的 TB/s 数字都只能当上界。
- MoE 的时间不只是读权重。MegaMoeTP 在 M 从 96 到 640 之间每多一个 token 多约 0.12 µs，TP4 的 KF GEMM 是 0.22–0.26 µs。**之前拿 TP8（M 640–768）和 TP4（M 约 344）比带宽，差距里有一部分是 M 不同造成的**，不全是 kernel 效率。

### 5.2 GB300 的六个点对步长的要求

GB300 用 MTP 5 步。交互度 p90 = 1 / ITL p90。我们要达到同样的 ITL，步长需要 ≤ 接受长度 × ITL。

| GB300 点（tok/s/GPU @ 交互度 p90） | ITL p90 | 我们需要的步长：MTP 3 步 / 5 步 | 对应我们的 graph batch（TP8、MTP 3 步、实测曲线） | 现状 |
|---|---|---|---|---|
| 63,647 @ 89.4（3P+1D，12+8 卡，C264） | 11.18 ms | 33.4 / 40.4 ms | ≤ 12–13 | PP8 C208：56.6k @ 70.9（p90 步长约 42 ms，由交互度反推）；带 kernel 调参和 KV 上限的一次 53.3k @ 80.7（p90 步长 36.2 ms，日志实测） |
| 55,488 @ 94.7（同上，C216） | 10.56 | 31.6 / 38.1 | ≤ 12 | 同上 |
| 44,453 @ 114.3（4P+1D，16+16 卡） | 8.75 | 26.2 / 31.6 | ≤ 6 | 单节点 4+4、MTP 5 步、C64：43.2k @ 81.6 |
| 28,407 @ 131.8（1P+1D，4+8 卡） | 7.59 | 22.7 / 27.4 | ≤ 4 | 单节点 4+4、MTP 5 步、C32：23.5k @ 106.8 |
| 16,924 @ 184.8（1P+3D，TP4 × 3） | 5.41 | 16.2 / 19.5 | 每卡 1 个请求时是 16.6 ms | 没有对应的点 |
| 8,942 @ 246.3（1P+5D，TP4 × 5） | 4.06 | 12.1 / 14.7 | 达不到 | 没有对应的点 |

逐段判断：

- **最右两个点。** decode 一侧的 p90 步长差 3–9 ms（看拿哪次运行比）。53.3k 那次差 3–5 ms，第 6 节的 MoE 一项或 DP rank 配平任一项就够；56.6k 那次差约 9 ms，两项都要。那次运行的 decode 日志没有保留下来，它的 batch 分布只能从计分文件看：在跑总数中位 58、最忙卡中位 12、p90 17，比 53.3k 那次高两档。吞吐差 11%（56.6k 对 63.6k），GB300 是 12 张 prefill 卡配 8 张 decode 卡，我们是 8 配 8，且吞吐受 prefill 限制；这不是 decode kernel 能补的。
- **中间两个点。** 按步长曲线，PP8 在并发降到约 165 / 105 时，每卡平均约 5 / 3 个请求，最忙卡约 8 / 5–6（不配平），步长约 27.3 / 24–26 ms，对应交互度约 109 / 115–125，接近但还没到 114.3 / 131.8。配平或 MoE 省 1.5–2 ms 后够得着第三个点；第四个点还需要 MTP 5 步（低 batch 时每 token 更划算）。**这一段全部是推算：PP8 只在 C208 测过，TP8 上也没有 MTP 5 步的数据。**
- **最左两个点。** 需要的步长低于我们每卡 1 个请求时的实测值。要到 12–15 ms，需要同时把注意力权重从 BF16 降到 8 bit（少读约 12 GB，约 −2 ms）和把 kernel 数减半（约 −2.5 ms）。GB300 在这一段用的是多个 TP4 小实例。我推测它的注意力权重也是 4 bit（配置里写的是 NVFP4 加专门的 GEMM kernel），**这一点没有核实**；如果属实，它每步每卡比我们少读约 19 GB。

和之前排序（`PLAN-REVIEW-20261112`）的主要差别：
- indexer 从第 4 / 第 6 位升到第 2 位，估计从"约 0.9 ms（待确认）"变成 1.5–2.5 ms。之前那个估计是在短上下文 trace 上做的。
- "曲线左端"之前写的是"MegaMoeTP 小 batch 回退 + norm 融合，1–1.5 ms"。实测左端是带宽和 kernel 个数两件事，对应上表第 3、5 项。
- MegaMoeTP 的调参（q3）、GEMM 合并、调优表补行这三项已做好的改动合计约 0.65 ms，方向没错，但都在 batch ≥ 13 才生效或才明显，而 PP8 有 78% 的步在 batch ≤ 12。
- MoE 的目标 shape 从"M 384–1024"改成"M 128–576"。在这个范围里生产路径的 GEMM 已经约 5 TB/s，差距主要在前处理、router 和通信上；MegaMoeTP 解决了通信，但小 M 时 GEMM 更慢。两条路径各有一半是对的。

不属于 kernel、但建议一起决定的两项：
- **在 PP8 上打开 router 的按请求数均衡。** TP4 上实测把补齐从 25–41% 降到 18–22%，交互度 p90 +5% ~ +10%，吞吐持平。PP8 上最忙卡是平均的 1.64 倍，如果降到 1.25 倍，graph batch 中位从 10–12 降到约 8，步长约 −3 ms。风险：PP8 的 decode KV 九成时间是满的，按请求数均衡可能和 KV 容量冲突；TP4 上权重设太大时 TTFT 变差。没有在 PP8 上测过。
- **MTP 步数按并发选。** 按步长曲线，每卡 ≤ 约 12 个请求时 MTP 5 步每 token 更快，超过约 20 个时持平。PP8 的最忙卡中位是 10。TP8 上没有 MTP 5 步的数据；之前在 TP4 的 C88 上 MTP 5 步崩过（`crash-k5-c88`）。

旧脚本的问题（`opt-aus-20261103/scripts/ana/`）：
- `step_cats.py`：按**各卡自己的请求数**分桶，不是按 graph batch；在各卡不均衡的真实 trace 上会把同一个图的时间分到不同桶里。"dense_gemm"一类混了五种不同的 GEMM。
- `kcat.py`、`kbybs.py`：按 kernel 名字匹配。o_proj 只认 `MT160x…` 这一种名字，小 batch 时 o_proj 用的是别的 kernel，会被漏掉；fused_qkv_a 的另一个变体（`…x5_ksd…`）同样会落到"其他"。
- `moe_bybs.py`：`router_topk` 的正则 `topk` 会把 indexer 的三个 top-k kernel 也算进 MoE 一侧（每步约 0.8–0.95 ms）。对"两条路径之差"没有影响，对绝对值有影响。
- `dtrace_deep.py`：按"每 3 次 graph 启动为一组"判断图的类型，顺序一乱就错；MoE 带宽固定按全部专家的字节算。
- `kdeep.py`：按 reduce-scatter 切层，MegaMoeTP 的 trace 里 MoE 层没有 reduce-scatter，层会连在一起。
- 这些脚本的加总本身没有算错。主要问题是拿哪些 trace、在哪个 batch 上下结论。

## 8. 没有做到的、不确定的

- **GB300 的数字是 10-27 的快照**（点是 10-20 的），不是最新的；11-13 用户确认先用它。
- **没有真实负载下的 MegaMoeTP trace。** 第 6 节里 MegaMoeTP 的真实构成是"合成 trace + 真实负载修正"拼的。
- **真实负载的 trace 都采自计分窗口的前 10–15 分钟**，上下文约是末尾的一半到七成。indexer 的数字可能偏低。
- **真实路由分布没有导出**，小 M 时 MoE 读了多少专家不知道；补齐行被路由到哪里也不知道。
- **8→10 这一档 3–4 ms 的台阶**没有定位到具体 kernel。
- **o_proj 的第二个 kernel（`PostGSU8`）属于同一次 hipBLASLt 调用**，这是从位置和名字判断的，库源码不在手上。
- **PP8 在 C208 以外的并发、TP8 上的 MTP 5 步、PP8 上的按请求数均衡**，都没有实测，5.2 的中段判断是推算。
- **B300 的注意力权重精度、MI355X 显存带宽的标称值**，取自之前的文档或推断，没有核实。
- prefill 一侧这次没有碰。最右端的吞吐差距在 prefill。

## 9. 建议接下来先做的测量（都不改生产配置）

1. 真实负载（或长 prompt 的合成负载，每请求 10 万–25 万 token）下，MegaMoeTP 和生产路径各采一次 trace，graph batch 覆盖 8、10、12、16。这一次采集同时回答：MegaMoeTP 的真实构成、indexer 在长上下文下的行为、8→10 的台阶。
2. 导出几步真实的专家路由，用它在 M = 128–576 上逐档测 MoE 两条路径。
3. PP8 打开按请求数均衡，做一次同节点对比。
4. PP8 做一次并发扫描（例如 C104 / C144 / C176），得到曲线中段的实测点。
