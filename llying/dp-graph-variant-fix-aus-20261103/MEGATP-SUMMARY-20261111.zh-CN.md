# MegaMoeTP 实验总结（11-09 ～ 11-11）

## 名词

- **MegaMoeTP**：aiter 提供的一个融合 kernel，把 decode 时每层 MoE 的"all-gather 收集各卡 token → 两个专家 GEMM → reduce-scatter 发回结果"
  合成一次启动。只影响 decode，不影响 prefill。
- **基线配置（文档里叫 kopt-nocap）**：生产 PP8 配置 + 两项已验证的 kernel 调参（MoE 调优表补一行；MLA absorb 的 BMM 配置），不加 KV 上限。
  MegaMoeTP 配置就是在它上面只多打开 MegaMoeTP，所以两者的差就是 MegaMoeTP 本身的效果。
- **同节点对比**：两个配置在同一次分配、同一对节点上背靠背跑。原因见第 3 节第 4 点。

## 1. 结论

- **TP8（两节点 PP8 1P1D，主要的生产形态）**：调过参数的 MegaMoeTP，在同一对节点上与基线相比——
  **吞吐持平（+0.4%）**；decode 在每卡 batch ≥ 16 时每步快 2–4 ms，**交互度慢尾 +7.7%、ITL 慢尾 −7.8%**；每卡 batch 2–7 时每步慢约 1 ms。
  精度门禁通过（GSM8K 196/200，长上下文 32/32 + 31/32，接受长度 3.61，与生产持平）。
  吞吐不涨是因为 PP8 1P1D 的吞吐由 prefill 决定，MegaMoeTP 只加速 decode。
- **TP4（单节点 4+4）**：调参后 graph 内每步在 batch 12 / 20 / 24 为 +0.7% / −3.0% / −3.8%，精度门禁通过；端到端计分还没跑（单节点作业一直没排上）。
- 改动只是三到四个环境变量（TP8：`AITER_MEGAMOE_TP_LB_MT=4 AITER_MEGAMOE_TP_LB_MT_SMALL=4 AITER_MEGAMOE_TP_LB_NPP=2 AITER_MEGAMOE_TP_LB_Q=2`），
  不改代码。**是否进生产需要你决定。**

## 3. 哪些是重复或浪费的（如实说明）

1. **TP8 3600 s 计分大量被抢占**：集群给新作业 30 分钟免抢占期，而一次 3600 s 计分（部署 + 预热 + 窗口）要约 90 分钟，
   默认参数和调参后的计分合计被打断十次左右。应该更早改用 20 多分钟能跑完的合成负载 trace（第 #4、#6 项后来就是这么做的）。
2. **调参中途停掉的两次**：第二轮扫参发现 q=2 更好时，q=1 版本的 trace 和计分已经开始，各跑了 1–2 分钟就停了。
3. **节点换来换去不是我选的**：每次被抢占或被管理员取消后，作业重新排队，调度器分到哪对节点就在哪对上跑。
4. **为什么基线要重测**：11-09 的基线分数 56,595 和 11-10 的 MegaMoeTP 分数 54,407 不在同一对节点上。后来发现同样的配置，
   换一对节点吞吐能差 4%（差在 prefill 每块耗时 323 vs 362 ms，配置、镜像、负载、CPU、功耗都查过，没有差异）。
   所以必须在 MegaMoeTP 用的同一对节点上重跑一次基线，这就是第 #8 项的同节点对比，**这一组已经完成并给出了结论**。
5. **正在跑的第二组同节点对比是可选的**：我想换一对节点再重复一次、估计波动大小；它不会改变结论，可以停。

## 5. 补充问答（11-11 14:00）

**问：MegaMoeTP 的 GEMM 比生产慢的原因是什么？**

更正：之前说"它内部 GEMM 比生产慢"是推断，不是测量。实际测到的是**整个 MegaMoeTP kernel（收集 token + 两个 GEMM + 发回结果）比生产
"只算两个 GEMM"多出多少**；MegaMoeTP 内部各阶段的耗时没有测过。单算子（真实权重，TP8）：

| 全局 token | 生产：只算 GEMM（不含通信） | MegaMoeTP 默认（含通信） | MegaMoeTP 调参后（含通信） |
|---|---|---|---|
| 384 | 132 µs | 173 µs（+41） | 160 µs（+28） |
| 768 | 183 µs | 220 µs（+37） | 188 µs（+5） |

默认参数下多出的约 40 µs ≈ 生产路径通信的开销（graph 内 all-gather + reduce-scatter 约 41 µs），即默认参数时融合没有把通信藏起来，
基本等于"GEMM + 通信"串行。可能的原因（都未逐一验证）：（1）阶段串行——all-gather 收齐才能开始 gemm1，gemm2 算完才 reduce-scatter，
每个阶段之间要等所有 CU、所有卡；（2）tile 与 token 数不匹配——384 token 时平均每个专家约 13 个 token，默认行 tile 48 行，大部分是填充，
调参能找回 13–33 µs 说明这部分存在；（3）生产 kernel 有针对这个形状的专门优化（KF gemm1 的激活预量化、shared expert 分散到所有 XCD 等），
MegaMoeTP 是通用实现。要确切知道，需要测 MegaMoeTP 内部各阶段的时间（硬件计数器，或在 aiter 源码里加阶段时间戳）。

**问："进生产配置"是什么意思？**

两层：（1）**作为后续实验的新基线**——之后做其他 kernel 优化时，对照组用"基线 + 调参后的 MegaMoeTP"，只影响我们的实验；
（2）**进入真正的部署配置（Infera 镜像 / 生产 recipe）**——目前 MegaMoeTP 是靠测试工具里的覆盖层在运行时替换 SGLang 内部函数
（MoE 前向、层边界的通信）实现的，适合实验、不适合直接上生产；要进生产需要把它正式实现进 SGLang / Infera（作为 DP attention 下
TP MoE 的一个后端），经过代码评审和完整精度评测。第（2）层需要用户决定。
