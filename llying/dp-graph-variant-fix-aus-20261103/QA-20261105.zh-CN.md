### （4）dense 层在线 FP8 转换哪些层？与 ATOM 的 PTPC 是否一致？

转换范围由 checkpoint 的 exclude 列表（以 BF16 存储的层）决定：

| 层 | checkpoint 精度 | 我们的处理 |
|---|---|---|
| 0-77 层 attention 的 `q_a` + `kv_a`（融合为 `fused_qkv_a`）、`q_b_proj`、`o_proj` | BF16 | **转 FP8** |
| 0-2 层 dense MLP（`gate` / `up` / `down`） | BF16 | **转 FP8** |
| 3-77 层 MoE（routed experts 和 shared experts） | 已是 MXFP4 | 不动 |
| `kv_b_proj` | BF16 | 保持 BF16（见第二节（2）） |
| indexer 的 `wq_b` / `wk` / `weights_proj`（22 层） | BF16 | 保持 BF16（见第二节（2）） |
| 路由 gate、`lm_head`、embedding | BF16 | 保持 BF16 |
| MTP 层（第 78 层：attention、`eh_proj`、experts） | BF16 | 不转：InferenceX Check 13 要求草稿按发布精度运行 |

"MLP 只转 dense 层"不是刻意挑选：MoE 层的 MLP 本来就是 MXFP4，只有前 3 层 dense MLP 是 BF16。

与 ATOM 的 PTPC 相比：

- **量化方式相同**：权重加载时按输出通道量化为 FP8 e4m3，激活运行时按 token 动态量化。
- **范围不同**：按之前核对的 ATOM recipe，它只排除 `*expert*`，其余 BF16 线性层全部量化，也没有排除 MTP 层。我们多排除了
  MTP 层（Check 13）、`kv_b_proj` 和 indexer（SGLang ROCm 代码路径的限制）。ATOM 具体如何处理 `kv_b` 和 indexer 未查证。

### （5）GEMM 调优的方法

1. **找出未调优的形状**：aiter 查不到配置时打印 `shape is M:…, N:…, K:… not found tuned config`。从 dense FP8 门禁的 decode
   和 prefill 日志汇总出 3 种 N×K：`o_proj` 6144×16384、`q_b_proj` 16384×2048、dense `gate_up` 24576×6144。
   `fused_qkv_a` 和 `down_proj` 未出现，镜像自带的 GLM-5.2 FP8 表已覆盖。
2. **M 的取值**：aiter 查表顺序为精确 M → M 向上取到 128 的倍数 → 下一个 2 的幂。所以取 decode 日志中实际出现的 27 个
   M（4-256，CUDA graph 批大小），加上 128-8192 之间所有 128 的倍数（覆盖 prefill）。
3. **调优工具**：aiter 自带 `csrc/ck_gemm_a8w8_bpreshuffle/gemm_a8w8_bpreshuffle_tune.py`。对每个 M×N×K：列出 CK、
   CK-tile、FlyDSL、asm 的候选内核并 JIT 编译；在 GPU 上用随机数据逐个计时，与参考结果比误差（> 5% 丢弃）；最快者写成
   一行（内核 ID、splitK、耗时、TFLOPS、带宽）。8 张卡各一个工作进程，每 100 组写一次结果。第一轮 2 小时内写出 100 行
   （超时后调优进程不响应 SIGTERM，手动删容器结束）；补充一轮 53 行。共 153 行，内核以 FlyDSL 为主，其次 CK、CK-tile。
4. **生效方式**：调优表挂到容器的 `aiter/configs/model_configs/`，文件名符合 `*a8w8_bpreshuffle_tuned_gemm*`，aiter 启动时
   与自带表合并；dense FP8 的 arm 自动挂载 `dense-fp8/tune/` 下的表。例：`o_proj` M=16 19.5 µs（5.2 TB/s），M=8192
   531 µs（3.1 PFLOPS）。
5. **验证**：调优工具不记录默认内核耗时，单个 GEMM 比默认快多少没有直接数据；看端到端同节点 A/B（单节点 10 号项对 09
   号项）以及日志中 "not found tuned config" 是否消失。差距不明显时用 aiter 单算子测试补测。
6. **补充**：起栈时发现其中 10 行（`q_b_proj` 的部分 M）与镜像自带表重复，aiter 合并时直接报 RuntimeError、prefill 起不来；
   去重后保留 143 行（原始结果在 `.raw` 文件）。镜像自带的那几行只比我们的慢约 4%。

## 二、05:33 的三个问题

### （1）单节点 4+4 理论上不应比两节点慢，差在哪里？

GPU 型号与计算量相同，差距只能来自 prefill 和 decode 同机时共享的东西。

**排除项（在单节点 dense FP8 计分的测量窗口内现场采样）**

| 怀疑方向 | 实测 | 结论 |
|---|---|---|
| GPU 降频 / 功耗受限 | sclk 2.33-2.39 GHz；功耗 312-890 W（上限 1400 W） | 不是 |
| CPU 被抢占 | 整机 CPU 利用率 7% | 不是 |
| GPU / NUMA 位置 | GPU 对调 41,395，对调前 41,124 | 不是 |
| v2 镜像 / kit | 同节点 pkg kit + fdbafb60 40,807 | 不是 |

**定位：KV 传输慢，占住 decode 的 KV**（Prometheus 直方图均值，按每个 prefill stage）

| | 单节点 4+4 C104（09 号项） | 两节点 2P1D C208（hrrn，prefill0 / prefill1） |
|---|---|---|
| 单次 KV 传输耗时 | **3.14 s** | 2.08 / 2.05 s |
| 单次传输速度 | **0.99 GB/s** | 1.35 / 1.70 GB/s |
| 等 decode 预分配（`prefill_bootstrap`） | **6.93 s** | 0.78 / 0.50 s |
| prefill 前向（`prefill_forward`） | 3.42 s | 2.61 / 2.53 s |

decode 侧"正在 decode + 正在接收 KV"的请求数，单节点 34 + 33、两节点 49 + 17，总数相近：decode 的 KV 容量一样，单节点时
一半被传输途中的请求占着，真正 decode 的少了；decode KV 满后，新请求在 prefill 侧多等约 6 s 拿预分配，prefill 队列积压
（prefill 满块节拍 560-572 ms 对 322 ms）。

**为什么同机传输更慢：yihou 已调研过（`yihou/samenode-kv-transfer-slow.brief.yihou.md`，10-22）**

- 同机时 KV **不走 RDMA 网卡**，走 Mooncake 的 **HIP 传输**（xGMI GPU 间拷贝）：Mooncake faae8dd4 在 `USE_HIP` 下总会安装
  HIP 传输，同主机路由优先级 hip > rdma > tcp。我们测到网卡 RDMA 计数几乎为 0，与此一致。
- kit 设置的 `MC_DISABLE_HIP_TRANSPORT=1`、`MOONCAKE_DISABLE_HIP_DMABUF=1` 在该版本代码中**没有被读取**（无效）；真正让同机
  不走 HIP 的是 `MC_DISABLE_HIP=1`（HIP 路由优先级置 0）。
- HIP 拷贝空载 57-63 GB/s，生产负载下每次拷贝约 4.9 GiB/s；原因未查清，怀疑拷贝引擎或 CU 被 prefill GEMM、HiCache
  拷贝内核、RCCL 抢占（同进程 GEMM 即可让速率减半）。他的 v0.5.21 1P1D 数据：同机 21.3K，跨节点 24.4-25.4K（-13~16%）。
- 他提出但**未验证**的方案：同机走 RDMA 回环（`MC_DISABLE_HIP=1`，两端用**同一块**网卡；同主机两块不同网卡之间的 RDMA
  会无声失败，同一块网卡回环约 40 GB/s）。

**更正**：我在 05:33 的回答里推测"`DEST_LOCAL_RAIL` 导致同机传输走跨 socket 网卡"，这是错的；KV 不经过网卡。

**实验（单节点 11 号项，`v2-aus/mc_intranode.sh`）**：同一节点 GPU→GPU 的 Mooncake 写带宽，HIP（kit 环境，空载）对
RDMA 同网卡回环（`MC_DISABLE_HIP=1`，目标侧网卡 / 源侧网卡），单对与 4 对并发。空载微基准测不出生产负载下的争用（yihou
空载 57-63 GB/s、生产 4.9 GiB/s），所以决定性实验是**单节点 C104 生产轮次加 `MC_DISABLE_HIP=1` + 两端同网卡**，需新的分配。

### （2）"实现限制"指什么？在线 FP8 是否都用 aiter 现成实现？调优结果是否方便 upstream？

**"实现限制"是 SGLang 的代码路径，不是硬件或 aiter 的限制：**

- `kv_b_proj`：加载后 SGLang 的 DeepSeek loader 把它拆成 `w_kc` / `w_vc` 供 MLA 吸收计算的 BMM 使用；拆分只认 BF16 或
  checkpoint FP8 的 scale 布局（block / per-tensor）。在线按通道量化后 scale 是转置的 `[1, N]`、权重被重排为 bpreshuffle，
  直接拆会出错。要支持需改拆分逻辑；收益约每卡 1.1 GB（每层 29 MB × 78）。
- indexer `wq_b` / `wk`：gfx950 融合 indexer 在 `__init__` 时决定是否启用，并缓存 BF16 的 `[wk ; weights_proj]`，要求
  `wq_b` 与 `wk` 同精度；在线量化在 `__init__` 之后，缓存会与实际权重不一致。要支持需量化后重新判断；收益约每卡 0.4 GB。

**在线 FP8 的计算全是现成实现，没有新内核：**

| 环节 | 实现 |
|---|---|
| 加载时权重量化 | SGLang `Fp8LinearMethod` 非序列化路径（`per_token_group_quant_fp8` 按通道），aiter `shuffle_weight` 转 bpreshuffle |
| 运行时激活量化 | `aiter.per_token_quant_hip` |
| GEMM | `aiter.gemm_a8w8_bpreshuffle`（按调优表在 CK / CK-tile / FlyDSL / asm 间选内核） |

我改的只有两处：`quark.py` 的路由（把排除层交给现有 `Fp8LinearMethod`，仅 ROCm + 环境变量时生效），`deepseek_common/utils.py`
的 block-scale 误判修复（只对带标记的层生效）。

**调优结果上游：方便，但有前提。** aiter 在 `aiter/configs/model_configs/` 按模型维护调优表（如
`a8w8_bpreshuffle_tuned_gemm_glm5.2.csv` 及 untuned 列表），上游即给 ROCm/aiter 提 PR，加入去重后的 143 行和形状列表。前提：
只适用于 gfx950 / 256 CU（MI355X）；内核 ID / 名字与 aiter 版本绑定，提 PR 前要在 aiter main 上重调；不能与已有行重复
（这次已因重复报错）；只有 SGLang 侧的在线 FP8 也进上游，这些表才会被用到，在此之前可像 yihou 的 BF16 表一样放进 Infera
example。SGLang 侧补丁可单独提 PR，`utils.py` 的误判修复本身是独立的 bug 修复。

## 四、10:42 的三个问题

### （1）`MC_DISABLE_HIP_TRANSPORT=1` 不起作用，是 Mooncake 版本问题吗？

不是上游版本差异，是 **Infera 给不同镜像打的 Mooncake 补丁不同**（同为 Mooncake faae8dd4）：

| 镜像 | Mooncake 补丁 | 同机关 HIP 的变量 |
|---|---|---|
| SGLang（我们用的） | `rdma_dest_local_rail`、`rdma_ack_timeout`（`build_mooncake_sglang.sh`） | 上游的 `MC_DISABLE_HIP=1`；二进制里只有 `MC_DISABLE_HIP`、`MC_HIP_NUM_EVENTS`、`MC_HIP_NUM_STREAMS`、`MC_USE_HIP_IPC`，没有 `MC_DISABLE_HIP_TRANSPORT` |
| vLLM、ATOM | 另加 `transfer_engine_impl.diff`（B.2：默认不装 HIP 传输，`MC_ENABLE_HIP_TRANSPORT=1` 打开，`MC_DISABLE_HIP_TRANSPORT=1` 强制关闭） | `MC_DISABLE_HIP_TRANSPORT=1` 有效 |

SGLang 的 kit、`bench/glm5p2_pd` 沿用了 vLLM / ATOM 镜像的变量名，在 SGLang 镜像里无效。跨节点时上游代码本就跳过 HIP，只有
同机部署受影响。v2 kit 已改用 `MC_DISABLE_HIP=1`。

### （2）DP 均衡 40 万的预期？是否值得在高吞吐区跑？

参照 4+4 C104 权重 100 万：吞吐 -0.9%（噪声内）、交互 p90 +7.7%、TTFT +22%。40 万是按本配置拟合的值（最忙 rank 多 1 个请求
≈ 多约 42 万 token 对每步的影响）。预期：吞吐 ±1%、交互 p90 +3%~6%、TTFT 代价小于 100 万时（约 +10%）。InferenceX 帕累托
图是交互 p90 对每卡吞吐，TTFT 不在图上，同吞吐下交互提高就是前沿右移，所以值得跑；已排为单节点 17 号项。

### （3）ATOM 按并发用不同的 MTP 模拟接受率，对我们是否有帮助？4+4 各点是否按点调 DP 均衡？

依据 `llying/gb300-atom-pd-analysis-20261021/README.zh-CN.md`：InferenceX 规定 agentic 推测解码用 golden AL 模拟接受，
GLM-5.2 K=3 → 2.99、K=4 → 3.33、K=5 → 3.61；**K 可自选，接受长度不能改**。ATOM 按并发选 K：1P1D（C56-C128）K=3，1P2D
K=4，1P3D K=5。对我们：高并发（大 batch、算力受限）K=3 每步只验证 4 个 token 更省（当前 C104）；低并发（小 batch、带宽受限）
多验证几个 token 几乎免费，K=5 每步多接受 21%，交互和吞吐都更好（旧 K=5 recipe 4+4 C64 32.5k @ p90 48.6）；中间点要实测。

4+4 扫点时 K 和 DP 均衡都按点选。全组合（3 K × 2 权重 × 4 点 ≈ 24 轮）太多，分两步：先定 K（C32 / C48 用 K=5，C104 / C112
用 K=3，C64 / C88 测 K=3 对 K=4）；再在选定的 K 上给 C64、C88、C104 各测一组 DP 均衡（0 对 40 万或 100 万）。约 12-14 轮，
两个单节点作业并行约一天。

## 五、10:56 的两个问题

### （1）DP 均衡权重怎么拟合？"最忙 rank 上多一个请求 ≈ 多 42 万 token"的含义

DP attention 下各 rank 每步同步，一步的耗时由最忙的 rank 决定。router 给 decode 分新请求时选"负担"最小的 rank：
`负担 = token 数 + W × 请求数`（W = `--decode-request-weight`，默认 0）。要让负担与真实步长成正比，需要知道 W。

`ana/decode_step_fit.py`：decode 日志每个 rank 每 40 步打一行 `#running-req: R, #token: T`，两行间隔 / 40 = 每步耗时；每 3 s 一个
窗口取各 rank 的 R、T 和步长中位数，最小二乘拟合
`步长(ms) = a + b·最忙 rank 请求数 + c·最忙 rank token(百万) + d·总请求 + e·总 token(百万)`。4+4 C104（权重 0）：
`21.3 + 0.70·最忙请求 + 1.66·最忙 token(百万) + …`，R² 0.878。即最忙 rank 多 1 个请求每步 +0.70 ms，多 100 万 token 每步
+1.66 ms，1 个请求 ≈ 0.70 / 1.66 × 100 万 ≈ **42 万 token**。

例：rank A 5 个短请求（各 1 万，共 5 万 token），rank B 1 个长请求（20 万）。只按 token（W=0）会把新请求给 A（5 万 < 20 万）；
W = 42 万时负担 A = 215 万、B = 62 万，给 B；按拟合，步长贡献 A ≈ 3.6 ms、B ≈ 1.0 ms，B 才对。之前的 100 万来自 1P1D C88
（decode TP8，1 个请求 ≈ 105 万 token），在 4+4 上偏大一倍多，过多把长请求压到 KV 余量少的 rank（等预分配翻倍、TTFT +22%）；
拟合不含 KV 池压力，所以取略低的 40 万。

### （2）K=3 接受率最高（2.99 / 4 = 75%），为什么不一定最划算？

K = 每步草稿 token 数（`speculative-num-steps`），每步目标模型验证 K+1 个位置。golden AL = 每步平均产出 token：K=3 2.99
（最多 4，75%）、K=4 3.33（最多 5，67%）、K=5 3.61（最多 6，60%）。决定性能的是 `每请求每秒 token = AL / 每步耗时(K)`，
`每步耗时 = 草稿（K 次小前向）+ 验证（一次前向，请求数 × (K+1) 个 token）`。

- 低并发：前向受显存带宽限制（主要是读权重），验证 6 个与 4 个 token 耗时相近；K=5 多两次便宜的草稿前向、每步多产出 21%，
  只要步长增加不到 21% 就更快（吞吐和交互都更好）。
- 高并发（每 rank 20-25 个请求，每次验证 100-150 个 token）：前向受算力限制、耗时随 token 数近似线性增长；K=5 多验证 50%
  只多产出 21%，K=3 更划算。接受率高（浪费少）只在这种情况下决定胜负。
- 例：当前 K=3 在最忙 rank 4 个请求时每步约 25 ms → 2.99 / 0.025 ≈ 120 token/s/请求；K=5 只要同负载每步 ≤ 30 ms
  （3.61 / 0.030 ≈ 120）就不差。中间并发需实测，所以 C64 / C88 测 K=3 对 K=4。InferenceX 允许每点自选 K，接受长度按 K 固定。

## 六、dense FP8 在对齐后的单节点上（11:04）

两侧 dense FP8 + `MC_DISABLE_HIP=1`，单节点 C104：**53,176**，同条件基线 53,209，吞吐持平；交互 p90 55.4 对 61.0（-9%）；
TTFT p50 / p90 3.67 / 7.36 s 对 4.25 / 9.64（更好）；prefill 满块 311 对 331 ms；decode 在跑 54 对 50，但最忙 rank 9-22 个请求时
每步慢 2-5 ms。所以 **dense FP8 现形态不是有效优化**：decode 多出的 KV 被每步变慢抵消，帕累托上是退步。之前单节点 +5.3% 是在
HIP 传输把 prefill 拖慢的情况下测的，那时 KV 容量能转化为吞吐。decode 变慢的可能原因：每个 FP8 GEMM 前多一次激活量化内核
（每层 3 个 GEMM，78 层共 234 个），部分 M 的 FP8 GEMM 不如调过的 BF16。下一步：只在 prefill 开 dense FP8（保留 prefill 和 TTFT
的收益、decode 不变），单节点 18 号项。

## 七、11:22 的三个问题

### （1）21.3、0.70、1.66 是什么、怎么来的

同一个线性回归的系数（`ana/decode_step_fit.py`）。decode 每个 rank 每 40 步打一行 `#running-req: R, #token: T`，两行间隔 / 40 =
这段时间的平均每步耗时；3600 s 按 3 s 切约 1,200 个窗口，每个窗口记 4 个 rank 的 R、T 和步长中位数，为一个样本。最小二乘拟合
`步长(ms) = a + b·max(R) + c·max(T)/10⁶ + d·ΣR + e·ΣT/10⁶`，4+4 C104 得 `21.3 + 0.70·max(R) + 1.66·max(T)/10⁶ + 0.096·ΣR −
0.089·ΣT/10⁶`，R² 0.878。

- a = 21.3 ms：截距，无请求无上下文时每步的固定耗时（读非 MoE 权重、3 次草稿前向、lm_head、rank 间同步、graph 启动）。
- b = 0.70 ms：最忙 rank 每多 1 个请求每步增加的耗时（每请求每步验证 4 个 token、路由到更多专家要多读专家权重、采样等）。
- c = 1.66 ms：最忙 rank 每多 100 万上下文 token 每步增加的耗时（与上下文成正比的工作，主要是 DSA indexer 扫全部历史 index-K）。
- d、e 很小：总负载几乎不影响步长，最忙 rank 决定步长。R² 0.878 即 88% 的步长波动可由该模型解释。

### （2）能否用已有数据算出每个 batch 该用哪个 K？之前的决策是否算出来的？

**之前"低并发 K=5、高并发 K=3"是定性判断加参考 ATOM，不是算出来的，可能有偏差。**

能算的：yihou 10-26 同 recipe 的 4+4 C96（`yihou/glm52.llrepro-k3-mtp.packup_20261026`）：K=5 每步 p50 55.3 ms、K=3 44.6 ms，比值
1.24。盈亏线是 3.61 / 2.99 = 1.207（K=5 步长之比低于它就更划算），C96 时 1.24 > 1.207，K=3 略好（每请求 67.0 对 65.3 token/s；
实际吞吐 K=3 +4.8%，K=3 的验证 graph 少占 3 GB 显存、可多放 KV）。

算不出的：每个 batch 选 K 需要两种 K 的完整"负载-步长"曲线；我们只有 K=3 的（最忙 rank 4 个请求 25 ms、12 个 37 ms、25 个
49 ms），K=5 只有 C96 一个点（yihou 包里只有每 rank 的中位数）。粗估（推测）：低负载时 K=5 多两次草稿前向约 3 ms，最忙 rank
4 个请求时约 28-29 ms，比值约 1.15 < 1.207，K=5 约好 4%；交叉点约在最忙 rank 10-15 个请求（4+4 的 C48-C80）。不确定性：C96
点来自另一组节点和镜像；草稿前向耗时是估的；K 影响显存进而影响 KV；每点差距只有几个百分点，与波动相当。

**做法改为直接测曲线**：一轮计分中最忙 rank 的负载在大范围波动（C64 时约 5-25），所以 C64 上 K=3、K=5 各跑一轮，就得到两条
整曲线，同负载下比较 AL / 步长即得交叉负载，再换算回并发给每个扫点选 K。已排单节点 19（K=3 C64）、20（K=5 C64）。

### （3）是否在 1P(PP4)2D(D4) 上尝试，还是先扫完 1P1D？

建议两条线并行：先在单节点把 1P1D（4+4）扫完；同时离线给 kit 加两个 decode 的支持，两节点作业到了测 1P2D；4+8（TP8）先放。

- 中段交互 1P2D 可能更好：4+4 C104 时 prefill 约 3.5 req/s 已近饱和。要提高交互需降低每个 decode rank 的负载：4+4 降并发会让
  prefill 空闲；1P2D 让 prefill 仍满负荷、每个 decode rank 负载减半。粗算同交互下 4+4 半负载约 27K/卡，1P2D 约 53.6K × 8 / 12
  ≈ 36K/卡（+30%），前提是那一段 prefill 是瓶颈，需实测。
- 1P2D 用 TP4 decode，可直接复用 KF 和 GEMM 调优；4+8 是 TP8，KF MoE 在 TP8 下回退 aiter，TP8 内核优化尚在进行。
- 4+4 扫描本身不可省（高吞吐端，也是中段比较的参照），单节点作业容易排上。
- 1P2D 需改 kit（第二个 decode 的端口 / GPU / 容器名、up / down、12 卡计数；参考 Infera 的 `sglang_1p2d_kimi2.6`）。放法：prefill 用
  一台节点 4 卡，两个 decode 用另一台 8 卡，KV 全部跨节点，不碰同机 HIP。

## 九、decode 在线 FP8 为什么没收益：trace 拆解（15:05）

单节点 C104，dense FP8（两侧）对基线（C trace），rank 0 每步内核耗时：

| 内核 | 基线 ms/步 | dense FP8 ms/步 | 说明 |
|---|---|---|---|
| dense 层 BF16 GEMM（hipBLASLt / hgemm 约 6 种） | 约 6.6 | 约 0.07 | 转 FP8 后基本消失 |
| FlyDSL FP8 GEMM `kernel_gemm_0`（约 219 次 / 步） | — | 3.70 | |
| CK-tile FP8 GEMM `FlatmmKernel` | — | 2.37 | |
| FP8 GEMM 合计 | — | 6.06 | 只比 BF16 快 0.5 ms |
| 激活量化 `_per_token_group_quant_8bit`（240 次 / 步，Triton） | — | 1.08 | 额外开销 |
| indexer `paged_mqa_logits_preshuffle` / `fused2` | 1.16 / 0.45 | 2.28 / 0 | 融合 indexer 没走到，+0.67 ms |
| 草稿 MoE（aiter `fmoe_bf16_pertokenFp8` 对 CK MoE GEMM） | 1.84 | 1.05 | 快约 0.8 ms（副作用） |

1. **主因是 FP8 GEMM 不够快**：10.9 GB FP8 权重每步 6.06 ms，等效约 1.8 TB/s；BF16 21.9 GB 6.6 ms，约 3.3 TB/s。decode 的
   M（每 rank 约 16-128）下 FP8 GEMM 带宽利用率低（调优工具测得最多约 3.4 TB/s，带宽上限 5-6 TB/s），约 2.5 ms/步的空间需要
   在 aiter FlyDSL / CK-tile 的小 M 内核上做。
2. **激活量化 1.08 ms/步**（Triton，每层 3 次）：融合进 RMSNorm 或走 block-scale 的现成融合路径，约可省 0.7 ms。
3. **indexer 换到更慢路径 +0.67 ms，不是 bug**：KF 融合 indexer `fused2`（`kf_indexer.py`）只在 batch 行数是 6 的倍数且 ≤ 96
   （`_LPT_GROUP_ROWS=6`、`_LPT_NG2=16`）时使用，否则回退 preshuffle。两次 trace 每步都是 22 次调用：基线 13.6 preshuffle + 8.4 fused2，
   dense FP8 全部 preshuffle——KV 多了、每 rank 在跑请求多了，batch 更常超出范围。该限制对基线同样存在（基线只有 38% 的调用用上
   融合路径）；把 fused2 扩展到非 6 倍数（补齐）和 > 96 行，每步约可省 0.5-0.7 ms，对所有配置有效，属于 KF 内核工作。
4. **意外收益**：`SGLANG_USE_AITER_FP8_PER_TOKEN=1` 让草稿 MoE 换成 aiter per-token FP8 内核，draft + draft_extend 约 -0.8 ms/步；
   可能单独设这个变量就能拿到（约 +1-2%），单独测一次。

三项都修好时，dense FP8 每步约比基线快 3-4 ms（约 7-9%），加上 KV +7.7%，同交互下吞吐约 +8%-12%（按内核耗时推算，需实测）。
先做 4（单独测 `SGLANG_USE_AITER_FP8_PER_TOKEN=1`，单节点 21 号项）；1 和 3 是内核优化，可与 TP8 内核优化一并交给做内核的同事。
