# 最高吞吐配置（1P(PP8) + 1D，C208，56,593）的瓶颈分析（11-09，讨论用）

数据来源：PP8 计分 `vfix-logs/opt/score-pp8.txt`（11-06 22:27-23:27，n04-25 → n04-29）、2P1D `score-2p1d.txt`（11-04）、4+4 `score-Cptpcfix.txt`（11-04，两节点）
和 4+4 单节点 C104 的 prefill 日志（`vfix-logs/runs-n02-33/c104-1105T0937/`）。**PP8 的引擎日志留在 n04-25 的 /scratch 上，现在拿不到**，所以下面
PP8 每级耗时的部分是推断，需要一次 PP8 运行来确认（见第四节第 1 项）。吞吐单位 tok/s/GPU。

## 一、结论

1. **瓶颈在 prefill，而且是 PP8 流水线的效率问题**：PP8 用 8 张卡，满块节拍（324 ms）和 4 卡的 PP4（322 ms）一样，现算速度只有 20,453 tok/s，
   2P1D 的两个 PP4（同样 8 张卡）合计 36,591 tok/s。PP8 的 prefill 排队均值 52.6（2P1D 每个实例 6），92% 的时间有排队。
2. **PP8 赢在缓存**：单一 radix 树 + 8 × 250 GB HiCache，缓存命中 96.98%（2P1D 95.79%），每个请求要现算的 token 约 4,060（2P1D 约 5,750，少 29%）。
   所以尽管 prefill 算得慢，吞吐仍比 2P1D 高 4.6%。
3. **decode 吃不饱**：在跑总数中位 58（2P1D 86），最忙 rank 中位 12，步长 33 ms；等传输（transfer-wait）85，多是在等 prefill 做完。
4. **TTFT 占了 lane 周期的四分之一**：如果 PP8 的 prefill 不再排队（TTFT 均值从 10.8 s 回到约 5 s），同样 C208 下吞吐约 +15%（推算，见第三节），
   而且 decode 还有余量可以加并发。
5. 吞吐指标里 99% 以上是输入 token（输出只占 0.76%），绝大部分命中缓存：提高吞吐 = 每秒完成更多（长上下文）请求，受 prefill 的未命中计算和 lane 周期约束。

**PP4 每级耗时**（4+4 单节点 C104 的 prefill 日志，同一个 8,192 token 满块在相邻两级打 `Prefill batch` 的时间差，6,4xx 个块）：
PP0→PP1 中位 250 ms（p90 476），PP1→PP2 274 ms，PP2→PP3 260 ms；PP0 上相邻满块的间隔中位 293 ms。**PP4 的流水线基本是满的**：节拍约等于单级耗时。

**PP8**：每级 10 层（最后一级 8 层 + LM head + NextN），单级耗时按层数应约 130-140 ms，节拍应降到约 150 ms；实测节拍约 320 ms，等于没降。两种可能：
- **流水线有空泡**：同时在途的块不够填满 8 级（`--pp-async-batch-depth 1`、调度器一次只往前排有限几个块），每块的总延迟（8 级 × 约 135 ms ≈ 1.1 s）
  被 2-4 个在途块分摊，节拍约 300 ms；
- **每级有不随层数缩小的开销**：例如每个块的调度 / radix 匹配 / HiCache 回载 / 向 decode 发 KV 的固定部分。

第一种的修法只是参数，第二种要 profile。区分方法：PP8 下同一满块在相邻两级的时间差——约 130 ms 是空泡，约 300 ms 是固定开销。

## 四、建议的下一步（按性价比）

1. **一次短 PP8 运行定位**（两节点，C208，测量 1200-1800 s，约 50 min；运行目录拷回 /perf_apps）：算 PP8 每级耗时与节拍、在途块数，判断是空泡还是固定开销。
2. **若是空泡**：PP8 的 `--pp-async-batch-depth` 2 / 4，或 PP8 用 16K 块（每级耗时回到约 270 ms，与 PP4 的 8K 块相当，在途块需求减半）；先 gate（正确性：
   pp-chunk-wait 补丁只在 PP4 / depth 1 下验证过）再计分。预期 prefill 现算 +30-80%，吞吐 +10-16%（推算）。
3. **若是固定开销**：对一个 PP8 prefill rank 做 torch profile，找不随层数缩小的部分（调度、HiCache 回载、KV 发送）。
4. prefill 解开后：PP8 加并发（C240 / C256），找新的前沿点；同时看 decode KV 池是否成为上限。
5. decode TP8 的 MoE：KF 内核只覆盖 TP4，TP8 回退 aiter，约 5.6 ms / 步（verify 的 13%）。prefill 解开前主要提升交互，解开后才转成吞吐。
6. 长请求公平性：SPF 下 > 128K 的冷请求在 2P1D 曾等到 1,000+ s（p99）；PP8 排队更长，可能更严重；`hrrn` 可选（2P1D 上吞吐 -4%）。

## 4a. 补充与更正（11-09 11:05，用内核会话 11-09 的 PP8 运行 + 4+4 单节点日志分阶段统计）

**更正**：第一、二节"PP8 的满块节拍与 PP4 相同，说明流水线没填满"不成立。"满块节拍"是相邻两个 8,192 token 满块的间隔，满块之间还夹着
非满块的批次，所以它比单级耗时长得多，不能直接说明有空泡。分阶段的实测：

| | 单级耗时（PP0→PP1 中位） | 满块节拍中位 | 每批已缓存 token 均值 |
|---|---|---|---|
| PP8 预热（11-09 kopt 运行，冷缓存，排队 105） | 126-137 ms（7 个相邻级） | **135 ms** | 约 0 |
| PP4 预热（4+4 单节点 C104，11-05） | 226 ms | 259 ms | 1.7 万 |
| PP4 测量（同上，3,600 s） | 266 ms | 448 ms | 10.5 万 |

- **PP8 在饱和时流水线是满的**：预热阶段节拍 = 单级耗时 = PP4 的一半，PP8 本身没有固定的空泡。
- **PP4 测量阶段**：PP0 每秒 2.40 个批次（间隔 417 ms），平均每批 6,976 个新 token、2.24 个请求；单级耗时满块 265 ms、1K-8K 的批 249 ms（几乎与批大小无关）。
  单级利用率约 62%；这个点 prefill 有 34% 的时间不排队，所以 PP4 C104 的空闲多半是没有活，不是空泡。
- **待确认（约 11:20 后，同一 PP8 运行进入测量阶段）**：PP8 测量阶段的批次间隔与单级耗时。间隔约等于单级（约 150-160 ms）就是算力受限，
  要靠 prefill 内核（长上下文 indexer / attention）或更多 prefill 卡；间隔明显更长而队列不空，才是调度空泡（第四节第 2 项）。
- 单级耗时几乎不随新 token 数变化，说明每个批次的开销主要来自已缓存的长上下文（indexer 对全部上下文打分、注意力、HiCache 回载）或固定开销，
  与 KERNEL-PLAN-20261109 第一节第 3 条"长上下文 prefill 里 indexer 可能是最大头"一致；需要一次 prefill profile 拆开。

**11:30 PP8 测量阶段（同一 kopt trace 运行，11:20:21 起前 583 s；decode 用的是内核会话改过的 kernel，且中途做 profile，与 11-06 计分不完全可比）**：

| | 数值 |
|---|---|
| 单级耗时（7 对相邻级） | 136-144 ms（满块 149、非满块 131）≈ PP4 测量阶段 266 ms 的一半 |
| PP0 批次间隔 | 中位 168 ms（p10 94、p90 478），均值 246 ms（4.07 批 / s） |
| 每批 | 新 token 6,449、请求 2.23、已缓存 14.5 万 |
| prefill 现算 | 26,254 tok/s |
| prefill 排队 / 等握手 / 已算完等传输（均值） | 12.4 / 2.1 / 12.9；有排队的批次占 52% |
| decode（n10-29，最近 10 min，每 rank） | 在跑 7.7、KV 用量均值 0.47（≥ 0.85 占 34%）、预分配 0.6、等传输 4.6；每 rank KV 上限 368 万 token |

- **PP8 的 prefill 没有调度空泡**：有活时批次间隔接近单级耗时；单卡效率与 PP4 相同。按每批约 6,400 新 token / 140-150 ms，prefill 上限约 4 万 tok/s，
  这次用了约六成。第一、二节"流水线没填满"的结论作废。
- **decode 的 KV 池是一个实在的上限**：PD 分离下 decode 端没有前缀缓存，每个请求要占满整段上下文（约 15 万 token）的 KV，每 rank 只能放约 24 个；
  三分之一的时间 KV 用量 ≥ 0.85。
- 11-06 计分时 prefill 排队均值 52.6、现算只有 20,453 tok/s，与这里的 12.4 / 26,254 差得多：要区分 prefill 算力、decode KV（握手等预分配）、
  KV 传输哪个在限，需要一次完整计分。内核会话的 `62-kopt-pp8-score`（C208，3600 s）约 13:20 出结果，届时在两节点上统计同样的指标并把引擎日志拷回 /perf_apps。
