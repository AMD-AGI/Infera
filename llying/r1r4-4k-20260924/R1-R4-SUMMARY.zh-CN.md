# R1–R4：实验规律与后续性能优化建议

整理日期：2026-09-28。本文总结已完成的代码验证和实验，不代表新增实验结果，也不改变策略默认开关。

后续补充：[Decode 有效并发对比与 InferenceX 公开成绩对应 Router 配方核查](router-followup-20260928/REPORT.zh-CN.md)。该核查发现相关 SGLang 配方启用了会话亲和，需与通用 KV 评分公式一起考虑。

**当前建议：本 case 优先保留 R1；R2 作为缓解 Decode KV 热点的可选策略；R3 尚需验证实际 host 回读收益；当前 R4 不建议启用。下一步应在保留缓存亲和性的基础上，改进 Prefill 排队和成本估计。**

这里 P 指 Prefill，D 指 Decode；TTFT 是首 token 延迟，ITL 是后续 token 间隔。性能结论主要针对 GLM-5.2、P/D 各 8 卡、C80、两端有效 chunk_size=4096、P 开启 HiCache 的配置。R3 的旁路观察使用 P 8K / D 4K，不能混作该配置的性能结果。

## 1. 四种策略分别说明了什么

| 策略 | 改动目的 | 已有验证与结果 | 当前判断 |
|---|---|---|---|
| R1 | P 响应体完成后释放 P 侧记账，避免一直占用到 D/客户端完成 | 历史 A0→G0：输出吞吐约 161.66→168.70 tokens/s/GPU（+4.4%），平均 TTFT 9.86→7.58 秒（−23.1%） | 支持修正负载记账生命周期；作为后续 P 优化的参考策略 |
| R2 | D 按在途输入 token 需求分配，减少长输入集中到同一 rank | 同口径前 43 分钟：KV 占用变异系数 0.444→0.184；分配等待超过 1 秒的请求 21→0；吞吐 156.37→154.79（−1.01%） | 改善了 KV 热点和少数长尾，但没有证明当前配置下的吞吐收益 |
| R3 | 区分 GPU 与 host 缓存，对不同层级的命中分别评分 | 1,139 次旁路决策未改变建议；事件接入、GPU 命中和分层评分检查通过；尚未验证主动选用 host 后的实际回读收益 | 尚无性能结论，不能认定有效或无效 |
| R4，与 R1 叠加 | P 按“在途有效输入工作量＋本次有效输入工作量”选择 rank | 完整一小时：相对 R1-only，吞吐 −31.32%，平均 TTFT 7.58→26.93 秒，未命中比例 4.55%→10.92% | 代码按预期执行，但当前成本模型和缓存/负载权衡不适合本 case |

R1 与 R4 解决不同问题：R1 改的是“什么时候结束记账”，R4 改的是“按什么成本选 P”。R1-only 保留原有 P 缓存偏好；R1+R4 的退化不能据此解释为 R1 无效。R4 的性能数据来自组合实验，没有单独 R4 的性能对照。

## 2. 可以总结出的规律

### 先保证负载账本反映实际工作，再优化评分

如果 P 已完成，但 Router 仍因 D 没结束而认为 P 很忙，那么评分公式再精细也建立在过期信息上。R1 的结果支持先修正这一问题。这里的释放点是 P HTTP 响应体结束，仍包含传输尾部，并非每个计算 chunk 完成就扣减。

因此要区分三件事：记账是否正确、选择是否符合公式、公式是否带来性能收益。R4 通过了选择最小分数和生命周期检查，却仍明显退化，说明功能正确性不能替代性能验证。

### 负载更均匀，不一定带来更高吞吐

R2 降低了同时刻各 D rank 的 KV 偏斜，却没有明显提高吞吐。原因是它改善的直接分配等待原本只影响少数请求：A0 同窗口平均分配等待约 15.26ms，而平均 TTFT 约 9.22 秒，主要等待仍在 P 相关路径。

累计每个 rank 分到相近数量的请求，也不等于瞬时负载均衡。R2 按输入长度分配后，请求数可以更不均匀，KV 却更均匀。后续应观察目标资源的瞬时占用、等待和整体收益，不能只看派单数量。

### 高前缀复用场景中，放弃缓存可能比排队更贵

R4 为追求较低的预约工作量，改变了原策略较强的缓存偏好。与 G0 匹配的 6,744 对请求中，平均新计算量约 5,775→12,392 tokens，P 平均排队约 2.82→19.08 秒。

尤其值得关注的是长尾：388 对请求（5.8%）额外未命中超过 32K tokens，贡献了全部新增未命中量的 77.7%。少数请求丢失大段缓存，可能增加共享队列的工作，连累自身缓存没有变差的请求；命中量基本相同的 4,400 对请求也出现了明显排队恶化。

这些结果支持优先保护大段前缀缓存，但不是逐次派单的反事实证明，不能精确断言每次换 rank 造成了多少延迟。

### “需要新算多少 tokens”还不是完整的 P 服务成本

当前 R4 的有效输入工作量为输入量减去命中前缀；主路径不再直接使用原来的 P overlap weight=20。预约工作量保留到 P 响应体结束，不随 chunk 进度递减。

它没有完整表达请求固定开销、长上下文 attention 成本、host 缓存回读成本，以及当前剩余工作量。同样的新计算 token 数，实际服务时间可能不同。借鉴 Dynamo 时可以采用“考虑新请求成本”的方向，但不能假定简化成一个 token 数就能复现它的收益。

### 单项指标变好，必须结合上下游解释

R1+R4 的 ITL 从 13.48ms 降到 12.44ms，但吞吐明显下降。此时 D 平均正在生成的请求数从 36.62 降到 23.61，等待 KV 的请求数从 17.46 升到 50.70，说明 D 更经常在等 P。

因此 ITL 改善可能只是 D 负载变轻。D 等待 KV 包含 P 排队、计算和传输，不能全部解释为网络慢，也不能与 P 阶段重复相加。

## 3. 后续优化的建议顺序

1. **以 R1-only 为参考，先保护原有 P 缓存亲和性。** 当前 R4 保持实验状态，不原样重跑，也不同时叠加多个未经验证的改动。已有历史结果继续作为参考，不因节点变化就机械重做基线。
2. **先用已有数据分析大段缓存损失，再设计受约束的排队修正。** 重点看哪些请求放弃了大量前缀、对应候选队列是否真的更短、少等的时间是否足以抵消新增计算或回读。不要直接用新工作量评分替换原有缓存偏好。
3. **把 P 成本估计逐步校准到时间。** 从输入长度、GPU/host 命中、新计算量和阶段记录入手。需要新观测时采用短时或抽样候选记录；现有正式实验没有完整候选反事实数据，不能离线精确重放所有替代选择。P forward envelope 包含调度间隙，也不能直接当作独占 GPU 服务时间。
4. **先验证 R3 的真实 host 回读路径，再校准其权重。** GPU 命中与 host 命中应有不同成本，但 host 权重需要依据实际回读耗时和节省的计算量。旁路公式正确只是第一步。
5. **在 D 压力成为显著问题时再评估 R2。** 更高并发或更重 KV 需求是值得研究的场景；目前没有这些场景的收益证明，不为补齐时长重复当前 C80 测试。

下一版 P 策略的核心判断可以用一句话表达：**换到另一个 rank，预计少排的时间，是否超过放弃缓存后多出的计算和回读时间？** 这是待校准的决策原则，不是已经验证可用的新公式。只有数据足以支持阈值后，再实施限制缓存损失或仅在明显拥塞时换 rank 的策略。

## 4. 实验执行上应保留的做法

- 新策略先跑关闭 HiCache 的短时 smoke，覆盖真实派单、账本释放、流式响应和压测客户端完整导出，再启动正式 HiCache 性能实验。
- 正式性能前核对镜像、二进制、模型、C80、两端有效 4K、HiCache、MTP、种子、策略开关和观测开销；配置须在既有授权范围内，变更按约定先确认。
- 一次只改变一个可解释因素。节点不同可接受，但须记录；统一统计窗口，保留预热错误和结束边界取消，不混入抢占后的错误。
- 周期性检查进程、引擎和请求进度。辅助型号识别或采样失败应留下诊断信息，不能因此自动终止仍健康的推理任务。
- 同时判断输出吞吐、TTFT、缓存未命中和 P 排队；D 优化还需看 KV 偏斜及分配长尾。不能仅凭平均 GPU 利用率或单个延迟指标宣称收益。
- 测试结束及时停止 P，让 HiCache 开始释放；停止容器后继续检查实际显存和进程，再释放资源。

## 5. 证据边界与详细报告

这些实验使用历史对照，节点和运行时间不完全相同；G0 复用了 A0 引擎，本轮 R1+R4 则重新启动。匹配分析只覆盖已完成请求的交集，相同长度也不等于字节完全相同。因此收益幅度和归因仍有边界，但当前数据已足以支持不启用现有 R4，以及不把 R2 的均衡效果宣称为吞吐提升。

R2 的正式有效窗口为 43 分钟，不能写成完整一小时；R3 只有有限旁路观察。空内容错误已复现“生成单个 `<think>` 后正文为空，被同版本客户端判为无有效响应”的机制，但历史三条缺少输出 token 记录，不能逐条归因。
