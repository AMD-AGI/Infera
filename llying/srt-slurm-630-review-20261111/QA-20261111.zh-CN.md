# srt-slurm#630 七个问题的回答（11-11）

依据：PR head `afefb95` 的代码、Infera `v0.3.3` 源码（`rust/router/src/config.rs`、`session_affinity.rs`、`decode_demand.rs`、`pool.rs`，`infera/engine/sglang/{__main__,worker,args}.py`、`infera/engine/readiness.py`），以及今天的真机冒烟和 GLM recipe 渲染结果。

**先说一处需要更正的地方（第 2、7 题会用到）：** 我按 review 加的那条加载时校验——"生效策略是 `kv-aware` 时，至少要有一个 role 开 `kv_events`"——**过于严格**。Infera 路由器的 `--decode-input-demand`（按 decode 的输入 token 需求均衡）只允许在 `kv-aware` 下使用，所以"只为用 decode 需求均衡而开 `kv-aware`、prefill 不发 KV events"是一个合法配置，现在会被这条校验拒掉。改法见第 7 题末尾，需要你决定。代码已经推送，但回复还没发，可以在回复前改掉。

## 1. 为什么 infera 只能配 sglang？

不是 Infera 只支持 SGLang，而是**这个 PR 目前只接通了 SGLang**：

- Infera 本身也有 vLLM 的启动器（`infera.engine.vllm`）。
- 但在 srt-slurm 里，"用一个包装模块代替引擎自己的 server 模块"这件事，要由各引擎的 backend 在拼命令时调用 frontend 的 hook（`worker_module()` 和 `worker_launcher_args()`）。目前只有 `SGLangBackend.build_worker_command()` 调用了，vLLM 和 TRT-LLM 的 backend 都没有调用。
- InferaFrontend 里关于端口的回答（metrics、endpoint、profiling 都用 leader 的 `http_port`）是按 SGLang 直连 worker 的布局写的；vLLM 有按节点的 DP 池等不同布局，需要单独核对。
- 而且 PR 只在 SGLang 上做过验证。

所以用 `required_backend = "sglang"` 在加载时挡住其他引擎（会检查每个 active role），避免出现"vLLM worker 没注册到 etcd、路由器永远等不到它"这种悄无声息的失败。以后要支持 vLLM，需要三步：在 `WORKER_LAUNCHERS` 里加一行；让 vLLM backend 调用这两个 hook；核对端口和 metrics 的回答。`docs/infera.md` 的 Engines 一节写了这一点。

## 2. 删掉 prefill 的 `kv_events: true` 为什么会报错？不能用 round-robin 吗？没有 KV events 就没有用 Infera 路由器的意义了吗？

**可以用 round-robin。** 这条校验只在生效策略是 `kv-aware` 时才触发：

| recipe | 结果 |
|---|---|
| 没写 `router-policy`，所有 role 都没开 `kv_events` | 报错。因为 srtctl 用 `python3 -m infera.server` 启动路由器，它的默认策略就是 `kv-aware` |
| 写了 `router-policy: kv-aware`，所有 role 都没开 `kv_events` | 报错 |
| 写了 `router-policy: round-robin`，没有 `kv_events` | 通过（单测里有这个用例） |
| prefill 开了 `kv_events`（GLM recipe 就是这样） | 通过 |

**加这条校验的原因：** `kv-aware` 拿不到 KV events 时，路由器不会报错，KV 视图一直是空的，相当于只按负载路由，只在连续多次没命中缓存后往日志里打一条 warning。用户以为在做 KV-aware 路由，压测结果会被误读。nv-kmcgill53 问的正是这一点。

**没有 KV events 时，Infera 路由器照样有用：**
- 从 etcd 自动发现 worker；
- PD 双发：同时把请求发给 prefill 和 decode，两边带同一个 `bootstrap_room`；
- 会话亲和（`--session-affinity`，按 `X-Session-ID`，和策略无关）；
- 按负载选 worker（`kv-aware` 在 KV 视图为空时就是按负载）；
- decode 需求均衡（`--decode-input-demand` / `--decode-request-weight`）。

**这就是需要更正的地方：** 最后一项要求策略必须是 `kv-aware`。所以有人只想要"会话亲和加 decode 需求均衡"、不需要 prefill 做 KV-aware 时，必须写 `kv-aware`，但又没有 KV events，现在的校验会拒掉这种合法配置（见第 7 题）。

另外，Infera 的 Rust 路由器只接受 `round-robin` 和 `kv-aware` 两种策略，其他值（比如 `least-load`）在路由器启动时就会报错。

## 3. mock 例子里 prefill 和 decode 的 HTTP 端口都是 6100，不会冲突吗？

不会，因为它们**不在同一台机器上**。srtctl 的端口分配器是**按节点**分配 HTTP 端口的（`allocator.next(HTTP_PORTS, node)`），不同节点各自从 6100 开始；同一节点上的多个 worker 会拿到不同的端口。今天渲染的 GLM 2P1D 计划就是例子：

| 进程 | 节点 | HTTP 端口 | bootstrap 端口 |
|---|---|---|---|
| prefill_0 | node-01 | 6100 | 7200 |
| prefill_1（和 prefill_0 同机） | node-01 | 6132 | 7201 |
| decode_0 | node-02 | 6100 | — |

真机冒烟也一样：prefill 是 `10.235.192.61:6100`，decode 是 `10.235.192.137:6100`。

注意：KV-events 端口不是按节点分配的，而是全局递增（3000、3001……），所以同机的两个 prefill 分别是 3000 和 3001；readiness 用的 system 端口同样全局递增（7500、7501……）。

## 4. readiness 端口是做什么用的？"没人连，只为不抢端口"是什么意思？

**它是什么：** Infera 启动器在 worker 注册到 etcd **之后**打开一个 HTTP 监听，注销**之前**关闭，只有当这个 worker 是路由目标时才回答"就绪"（`infera/engine/readiness.py`："A readiness port that answers only while the worker is a routing target"）。这是为 **Kubernetes** 设计的：k8s 的 readinessProbe 探测它，决定 Pod 是否接流量；代码注释也提到它在 `hostNetwork` 下和引擎端口共用节点的端口空间。

**在 srtctl 里为什么没人连：** srtctl 判断就绪是轮询**路由器**的 `/v1/workers`，不会去探测每个 worker 的 readiness 端口。

**为什么还要给它分配端口：** 启动器**总会**打开这个端口，Infera 没有提供关掉的开关：环境变量没设置、不是数字或者是 0 时，都会退回默认值 30090。于是有两个问题：
1. **同机多个 worker 抢同一个端口。** 2P1D 两个 prefill 在同一台机器上时，第二个绑定 30090 会报 "address already in use"。启动器会记一条日志，然后不带 readiness 端口继续运行，功能上没影响，但日志里有报错。10-30 的 AUS e2e 就出现过。
2. **违反 srt-slurm 的规则**："所有监听端口都来自端口分配器"。固定的 30090 可能和别的服务撞上。

所以 PR 把每个进程分到的 system 端口传给它（`INFERA_READINESS_PORT=<sys_port>`）。没有 Dynamo 时 system 端口本来就空着，是分配器分配的，每个进程一个，不会冲突。"没人连，只为不抢端口"就是说：这个端口对 srtctl 没有用处，给它分配端口只是为了让它不和别人冲突、不违反规则。今天的真机日志里，两个 worker 分别在 7500 和 7501 上打开了 readiness。

## 5. R2 新加的 hook 是做什么的，为什么要加？

**三个 hook 各管一件事**（都定义在 `Frontend` 基类上，默认值让其他 frontend 不受影响）：

| hook | 作用 | 默认 | Infera 的返回值 |
|---|---|---|---|
| `worker_module(backend_type)` | 用哪个 Python 模块代替引擎自己的 server 模块 | `None`（用 `sglang.launch_server` 或 `dynamo.sglang`） | `"infera.engine.sglang"` |
| `worker_launcher_args(backend, process, runtime)` | 这个包装模块自己的参数，放在引擎参数前面 | `[]` | `--discovery-backend etcd --etcd-endpoint ... --advertise-host ... --request-transport http --kv-event-transport zmq --kv-events off`，role 不发 KV events 时再加 `--no-enable-kv-events` |
| `worker_environment(process, runtime)` | 这个 frontend 需要给每个 worker 进程加的环境变量 | `{}` | `{"INFERA_READINESS_PORT": "<sys_port>"}` |

拼出来的效果：`python3 -m infera.engine.sglang <Infera 参数> <SGLang 自己的参数>`，环境变量里带 readiness 端口。

**为什么要加（替换原来的一个 hook）：** 原来只有一个 `direct_worker_launcher()`，直接返回整段命令开头：`env INFERA_READINESS_PORT=7500 python3 -m infera.engine.sglang --discovery-backend ...`，SGLang backend 把它原样拼在前面。nv-kmcgill53 指出两个问题：
1. **环境变量绕过了环境变量层**：藏在命令里的 `env KEY=VAL` 不会出现在 dry-run 的环境变量段和每个 worker 的 `Env:` 日志里，用户也没法在 recipe 里覆盖。现在走 `worker_environment()`，由 worker stage 统一合并：它在用户环境变量之前合并，所以可以被覆盖；snapshot 的 `env_to_set` 里也能看到。
2. **接口没有类型约束**：返回任意 argv，frontend 理论上可以往命令开头塞任何东西，backend 也不再掌控 `python3 -m <module>` 这一部分。现在 frontend 只提供"模块名"和"参数"，`python3 -m` 仍由 backend 拼。

## 6. prefill 同时有 `--kv-events off` 和 `--kv-events-config`，冲突吗？修复前 decode 也会广播 events，路由器怎么知道该不该收？修复后 Infera 会不会无视 `--no-enable-kv-events`，仍然分配端口？

### 6.1 三个名字很像的参数，管的是三件不同的事

| 参数 | 谁的参数 | 管什么 | 我们怎么设 |
|---|---|---|---|
| `--kv-events on/off/auto` | Infera 启动器 | Infera **自己的** "KV plane"：一个 Python 端的事件发布者（默认绑 `tcp://0.0.0.0:5557`）加一个 snapshot 服务，注册在 etcd 记录里一个叫 `kv` 的字段下，给 Python 版路由器用 | `off`：Rust 路由器的 `Worker` 结构体里**没有** `kv` 字段，读不到它；而且它会绑固定端口，违反"端口由分配器发放" |
| `--enable-kv-events` / `--no-enable-kv-events` | Infera 启动器 | 要不要让 **SGLang 原生**发布 KV events 并登记到 etcd（默认开） | role 不发 KV events 时传 `--no-enable-kv-events` |
| `--kv-events-config '{...}'` | SGLang | SGLang 调度器在哪个 ZMQ 端口上发布 KV cache 事件 | role 开了 `kv_events` 时由 backend 传入，端口来自分配器 |

所以 prefill 同时带 `--kv-events off` 和 `--kv-events-config` **不冲突**：前者关掉的是 Infera 自己那套 Python 事件通路，后者打开的是 SGLang 原生的发布者。Infera 启动器读到 `--kv-events-config` 里的端口（`explicit_kv_events_port`），把它登记为 `kv_events_endpoint`。今天真机上，路由器订阅的正是 prefill 的 `tcp://10.235.192.61:3000`。

（Infera 帮助文字里"`--kv-events off` 时路由器对这个 worker 退回 round-robin"，说的是 Python 版路由器；我们用的 Rust 路由器走的是 `kv_events_endpoint`。）

### 6.2 路由器怎么决定订阅谁

路由器不区分角色：**谁在 etcd 的注册记录里登记了非空的 `kv_events_endpoint`，就订阅谁。**

- **修复前**：decode 的启动器 `--enable-kv-events` 默认开启，命令里又没有 `--kv-events-config`，于是它用 `free_tcp_port_block()` 自己找一个空闲端口，给 SGLang 补上 `--kv-events-config`，并把这个端口登记为 `kv_events_endpoint`。路由器就去订阅 decode。GLM 的 decode 关掉了 radix cache，事件里没有可用的信息，所以 10-30 的 e2e 里路由器对 decode 报过 "kv event feed is not being applied"。问题在于这个端口不是分配器发的，可能和别的进程冲突。
- **修复后**：decode 带 `--no-enable-kv-events`，登记的 `kv_events_endpoint` 为空，路由器不订阅。

### 6.3 修复后 Infera 会不会无视 `--no-enable-kv-events`？

不会。Infera 0.3.3 的 `SglangEngine.start()`（`worker.py`）：

- 只有 `enable_kv_events` 为真时，才去读 `--kv-events-config` 的端口；
- 只有 `enable_kv_events` 为真且没有显式端口时，才会自己分配端口、补 `--kv-events-config`；
- 只有 `enable_kv_events` 为真时，才在注册信息里填 `kv_events_endpoint`。

`--no-enable-kv-events` 让这三步都跳过：不分配端口，SGLang 不发布事件，注册时端点为空。今天真机上完全符合：decode 的注册里 `kv_events_endpoint: null`；Infera 实际拉起 SGLang 的命令里没有 `--kv-events-config`；路由器只订阅了 prefill。

## 7. GLM-5.2 recipe 如果 prefill 用会话亲和、decode 用请求长度或请求数量均衡，这个 PR 支持吗？怎么支持的？

**支持，而且 InferenceX 的 GLM recipe 现在就是这么配的。** PR 对路由器只管理少数几个参数（发现方式、etcd 地址、监听地址和端口、传输方式），`frontend.args` 里其余的参数原样追加到 `python3 -m infera.server` 后面，由它转给 Rust 路由器。

需要用到的路由器参数（Infera 0.3.3）：

| 需求 | 参数 | 说明 |
|---|---|---|
| prefill 会话亲和 | `session-affinity: prefill` | 按请求头 `X-Session-ID` 把同一会话固定到上次的 prefill；`both` 时 decode 也固定。和路由策略无关 |
| decode 按请求长度均衡 | `decode-input-demand: on` | 路由器记录每个 decode 上在途请求的输入 token 数（拿不到 token 时按每 4 字节约 1 个 token 估算），选需求最小的。**要求 `router-policy: kv-aware`** |
| decode 按请求数量均衡 | `decode-request-weight: N` | 每个在途请求额外算 N 个 token。N 很大时（例如 1,000,000）基本就是按请求数均衡；0 表示只按 token。**要求 `decode-input-demand` 为 on 或 shadow** |
| prefill 的缓存命中权重 | `kv-prefill-overlap-weight` | 需要 prefill 发 KV events |
| decode 的缓存命中权重 | `kv-decode-overlap-weight` | 需要 decode 发 KV events。修复后 decode 不再发，这一项实际不起作用；GLM 关掉了 decode 的 radix cache，修复前也没有效果 |

InferenceX 的 GLM recipe 里 `frontend.args` 现在是：`router-policy: kv-aware`、`kv-prefill-overlap-weight: 20`、`kv-decode-overlap-weight: 2`、`session-affinity: prefill`、`pd-prefill-guard-release: completion`、`decode-input-demand: 'on'`；AUS kit 里还通过 `DECODE_REQUEST_WEIGHT` 设过请求数权重。它的 prefill 开了 `kv_events`，所以今天的渲染检查能通过。修复后 decode 的打分只剩负载和需求，正好就是"decode 按长度或数量均衡"想要的效果。

**问题出在这种变体上：** 如果有人想要"prefill 只用会话亲和、不做 KV-aware，decode 用需求均衡"，就会在 prefill 去掉 `kv_events`。但 `decode-input-demand` 要求 `kv-aware`，于是现在的校验会报"没有 role 发 KV events"，拒掉一个合法配置。现阶段的绕过办法是 prefill 保留 `kv_events: true`，再把 `kv-prefill-overlap-weight` 设为 0，代价是 prefill 白白多一个 ZMQ 发布者。

**建议的改法（需要你决定）：**

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | 只在 `kv-aware`、没有 role 发 KV events、**并且** `decode-input-demand` 没开（off 或没写）时报错；开了 `decode-input-demand` 时改为打一条 warning（说明 prefill 不会按缓存路由） | 只拦"kv-aware 毫无作用"的真正误配置，放行上面的合法变体；改动小，补两个单测 |
| B | 改成一律只打 warning，不报错 | 最宽松；reviewer 要的是"有提示"，warning 也满足，但可能被忽略 |
| C | 保持现状 | 合法变体需要用上面的绕过办法 |
