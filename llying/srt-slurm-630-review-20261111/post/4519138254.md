Taking the four points in turn:

- **KV events decided on both sides:** both flags now come from `get_kv_events_config_for_mode` (see Devin's thread).
- **Flag forwarding:** I didn't add a test in srtctl's CI. `infera.engine.sglang` takes its own flags with `parse_known_args` and hands the rest to SGLang's `ServerArgs`, so checking the forwarding needs SGLang installed. docs/infera.md now says that srtctl relies on the pinned release forwarding unknown flags unchanged, and that a new release should be validated on hardware before moving the pin.
- **SGLang facts in the frontend:** Infera discovers workers dynamically, as Dynamo does, but its workers are direct: the launcher starts SGLang's own server on the allocated `http_port` and only registers it, and the router sends requests straight to that port. The port answers follow the worker, not the discovery. Dynamo answers `sys_port` because every `dynamo.<engine>` rank runs the Dynamo system server there, whatever the engine; an Infera worker has no such server. So the endpoint, metrics and profiling ports are the leader's `http_port`, which is the `--port` the SGLang backend passes. Every direct frontend answers this way for every engine (`StaticRouterFrontend`, `trtllm_serve`), without asking the backend. The metrics path does ask the backend: `InferaFrontend.worker_metrics_path` overrides `DynamicFrontend`'s Dynamo `/metrics` and returns `Frontend.worker_metrics_path`, which reads `prometheus_metrics_path`. I left the ports as they are, but I'm happy to factor out a shared direct-worker helper if you prefer. Unlike `StaticRouterFrontend`, there is no gRPC branch: the router reaches workers over HTTP, so `validate()` now rejects a `grpc-mode` role, as llm-d does, instead of letting it wait out the health check unregistered.
- **`WORKER_LAUNCHERS`:** commented and documented as SGLang only, with what a vLLM row would also need: the vLLM backend calling the hooks, and the port answers checked against its layout.
