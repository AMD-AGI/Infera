# Dynamo 与 Infera Router：通俗解释及本次优化建议

保存日期：2026-09-24。本文保存会话中的通俗解释。Infera 指本次实验使用的版本和配置；Dynamo 指此前核查的固定版本 `ff3ac59e83c73e03b98a5d0ec192ec28847130f7`。

**可以借鉴，而且与我们观察到的问题直接相关。最值得借鉴的是：把 P、D 各自的负载算得更准确，再结合缓存选目标。** 目前没有证据说明整套换成 Dynamo 就一定更快。

先区分两件事：**Router 决定请求送到哪个 P、哪个 D；SGLang 决定请求何时能分配 KV、进入计算。** Dynamo 主要改进前一件事，仍受后一件事限制。

## 1. 选 P：两者都考虑缓存，但“忙不忙”的算法不同

P 负责处理输入。选 P 要权衡：这里缓存多，能少算一些；但这里如果已经很忙，也可能排很久。

| | 我们当前的 Infera | Dynamo |
|---|---|---|
| 缓存 | 命中越多越优先，当前配置给缓存命中很高的权重 | 把缓存命中折算成当前请求可以省掉的计算量 |
| 负载 | 综合活跃请求涉及的不同 KV blocks、最近派单情况 | 估算已经派过去、尚未完成的有效 Prefill 工作量 |
| P 什么时候不再算忙 | 原始路径一直记到 D 生成结束；G0 提前到 P 响应结束 | 独立 P 请求结束后释放自己的记账，不必等 D 全部生成完 |

Dynamo 的思路可以近似理解为：

> **选“已有待处理工作量 ＋ 新请求需要计算的量”更小的 P。**

举个简化例子，一个请求有 64K 输入：

| 候选 P | 缓存命中 | 新请求还要算 | 已有工作量 | 合计 |
|---|---:|---:|---:|---:|
| P1 | 48K | 16K | 32K | 48K |
| P2 | 32K | 32K | 8K | 40K |

Dynamo 会选 P2：虽然少命中一些缓存，但前面的工作少，总体可能更快。如果 P1 的队列变短，又会选择 P1。

这个数字是**工作量估计，不是精确的完成时间预测**。但它更容易解释为什么一次派单合理。

**对我们的意义：G0 已经验证了这个方向的一部分。** P 明明已经完成，却因为 D 还在输出而继续被记为繁忙，会影响下一次选 P。提前释放 P 记账后，我们观察到 P 排队和 TTFT 改善。因此，应继续保留这个改进，再研究如何更准确地记录 P 待处理的工作量。已有结果还不能证明 Dynamo 的整套评分优于 G0。

## 2. 选 D：Dynamo 能区分长短请求，我们当前的实测路径基本没有

D 负责生成输出，需要容纳输入 KV 和后续输出 KV。

我们这次采集的 D 路由记录中，缓存命中、active blocks、请求 blocks 都是零，因此实际上主要靠“最近给谁派过单”来分配。这样容易出现：

> 给 D1 派了一个很长的请求，给 D2 派了一个很短的请求；Router 看起来觉得各派了一个，负载差不多，但实际 KV 压力可能差很多。

Dynamo 的普通 P/D 分离路径会把**每个请求的输入 KV 需求记入 D 的负载**，也不会假设两个相同前缀的请求必然能在 D 上共享 KV。因此，它更有条件避开输入 KV 已经积压较多的 D。

**这很值得我们借鉴：让 D 按请求大小分配，而不仅按派单次数分配。** 不过，输入长度估算仍不等于实际剩余显存，还需要与 SGLang 的真实 KV 占用、待分配请求和输出增长对账。

## 3. 缓存：Dynamo 可以区分“已经在 GPU”和“还在 host”

这两种命中省下的时间不同：

- GPU 命中：可以直接使用。
- Host 命中：需要搬回 GPU，但通常仍有机会比重算划算。
- 都没命中：需要重新计算。

Dynamo 可以在评分中区别对待这几种情况。这对我们调查长尾 miss 有价值：某个 P 的 GPU 命中少，可能 host 中有很多可复用内容，未必应该被排除。

但前提是引擎把缓存位置和变化正确告诉 Router。**我们当前 Unified Radix 的事件是否完整，需要先核实；如果缓存信息不准，换评分公式也无法做出正确选择。**

**后续源码核查更新（2026-09-24）：已确认当前 Infera 的 Rust/Python KV-aware Router 都没有分层目录和分层评分。** Rust 忽略事件中的 medium，Python 虽保留该字段却未用于更新目录。因此，即使引擎已发送完整分层事件，当前 Router 也不能分别利用 GPU/host 命中。Unified Radix 与 HiCache 可同时使用，不能把它们当成互斥方案。详细解释及证据见 [分层缓存支持调研](CACHE-TIER-SUPPORT.zh-CN.md)。

## 4. 本次该怎样借鉴

建议按下面的顺序借鉴，分别验证：

1. **保留 G0 的 P 记账提前释放**：这是目前已有实验支持的方向。
2. **补齐 D 的输入 KV 需求记账**：先观察它会不会改变选 D、是否更符合实际 KV 压力，再启用新策略。
3. **核实 GPU/host 缓存信息，再试 Dynamo 式的 P 工作量评分**：避免继续只凭经验调整 overlap 权重。

至于我们关心的 **“D 提前占着 KV 等 P”**，Dynamo 的 Router **没有自动解决它**。在 SGLang 路径中，P/D 仍可并发推进；请求何时分配 KV 仍由引擎控制。借鉴这些算法有望减少选错目标和负载不均，但是否需要改变 D 的准入时机，要作为另一项优化单独判断。
