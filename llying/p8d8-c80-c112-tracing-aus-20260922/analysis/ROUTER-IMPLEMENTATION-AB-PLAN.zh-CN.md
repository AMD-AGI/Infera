## 实现顺序

以下开关名为拟议接口，当前不保证已存在。以本次使用的 Rust Router 为第一实现目标；Python 路径不自动宣称同步支持。

### R1：整理并正式验证 P guard 生命周期

把已存在的 `router-prefill-guard.patch` 整理成可构建、可回滚的独立提交，保留 `decode/completion` 开关。P guard 由 P 响应体消费任务持有，D guard 由 D 请求生命周期持有。

覆盖正常完成、响应读取失败、客户端断开、D 建连失败、任务取消、重试，验证记账恰好释放一次。客户端断开后 P task 若仍在执行，P 账本不能因客户端消失就提前归零。不要顺便引入 PR #173 的整套 abort 策略。

对照：原 guard 与 completion guard；同一二进制，只变开关。先取得可信的 R1 结论，再决定后续实验双方是否固定开启它。

### R2：D 输入需求账本，先旁路记录再选 rank

首先将“获取输入长度”和“查询缓存前缀”解耦。当前 `policy.rs` 依赖 worker 的 `kv_block_size` 建立 hash，D 没有相关元数据时会得到空 blocks。新增输入长度来源应使用与引擎一致的 tokenizer/template，或可信的预分词输入；缺失时明确标为 unknown，不能静默当成 0。

在每个 worker/rank 上累计每个在途请求的输入需求，不按前缀去重。第一版只做输入 token 总量；如使用 blocks，应验证 D 实际 block size 并向上取整。请求分词尽量一次计算、P/D 共用，避免双倍模板渲染开销。

状态至少包括 attempt ID、worker/rank、输入需求及释放状态。在一次短临界区内完成“读负载—选 rank—登记需求”，网络操作和分词不持锁；失败、结束和重试须正确撤销。首次派出至等待 P 的请求也应占账，不能到 D 开始生成才登记。

旁路模式保持原选 rank，只记录各候选账本、原选择、新算法建议选择，以及 unknown 比例。接入引擎 D allocated/pending/growth 指标作对照，但第一版不新增硬 admission 门槛。

第一版评分：选择 `当前在途输入需求 + 新请求输入需求` 最小的 D；相同容量各 rank 的新请求项是相同常数，真正区分候选的是已经积累的负载。相同分数的打破规则固定。输入不共享，无需 D Radix Cache；不同时加入输出预测、host cache 或 P 路由改动。

测试：两个相同前缀请求分别计费；长短请求不同计费；未知长度明确降级；并发派单不漏登记；重复完成不重复扣减；失败/重试/取消后账本无泄漏。对照双方保留相同的旁路记账与日志开销，仅切换选 D 策略。

**进入 GPU 实验的条件：** 输入长度与引擎吻合、账本正确，而且新策略确实会改变有意义的一部分选择。C1G1 记录中的 D alloc_wait p99 约 1.4 ms，说明收益空间不能仅由均值或算法直觉判断；先看慢请求和 rank 偏斜，必要时暂缓 D 性能实验。

### R3：GPU/host 目录，先修信息再加权

先核查本次 Unified Radix 的实际 Stored/Removed/Cleared 事件、medium、rank，以及 GPU→host 复制完成和 load-back 时序。有完整事件就补 Router；缺事件则另做引擎发布补丁，明确镜像变化。

Router 保留 medium，目录按 worker/rank/tier 分开。同一 block 可同时在 GPU/host；删除一个 tier 不删除另一 tier。查询按连续前缀计数，host 只计超出 GPU 命中的部分，避免重复加分；未知 medium 和丢事件的处理要显式记录。

必要测试：双层副本存续、先复制后淘汰、host 回读、前缀断裂、清空、序号缺口和 rank 隔离。未知状态不能当成肯定命中。

先输出全候选 GPU/host 命中和建议选择，保持原路由。确认数据有价值后，拆成两个可分别比较的步骤：

1. 分层目录但评分仅使用 GPU，检查目录修正本身的影响。
2. 同一分层目录上新增 host credit，比较 host credit 关闭/开启。

初始 host 权重根据本机回读与重算成本估计并在实验前冻结，不直接把 Dynamo 的默认值当作 MI355X 最优值。若涉及引擎补丁，对照双方都使用相同镜像和事件发布设置，避免把引擎改变混入 Router 算法收益。

### R4：P 工作量评分

此前的 cache 目录、guard 和 D 策略在双方保持一致，仅切换 P 的评分模型。记录各 P 已派但未完成的有效 Prefill 工作量，以“积压工作量 + 新请求有效工作量”为基础，按 GPU/host 命中给予成本折扣。

第一版不增加逐 chunk 进度预测；P 完成时扣账，明确它是估计而非真实剩余 kernel 时间。先比较旧评分与新评分，不同时扫描 overlap、host 权重、chunk 或容量。

## A/B 的执行方法

1. **廉价筛查**：单元/生命周期测试、事件回放、输入长度对账、全候选旁路日志。离线回放只能说明即时决策不同，路由改变会进一步影响缓存和队列，不能由回放直接推导端到端吞吐。
2. **正式对照**：每个通过筛查的候选先做一对可比启动的 A/B，每轮重启 P/D；优先同一分配、同一节点，固定镜像、模型、driver、GPU/host/D 容量、4K chunk、C80、数据 revision、seed、客户端版本和输出预算。相同二进制用开关切换。统一 884 请求 warmup、3600 秒正式窗口及收尾规则。
3. **防止混杂**：每轮验证 KV 初始状态、JIT 编译缓存清单、PID/startup_time、温度/时钟、GPU 所有权及实际容量。重启不能消除所有系统缓存和时序差异。历史 A0/C1 仅作参考，不能代替此次可信对照。
4. **控制实验数量**：不循环重跑旧基线。只有候选通过正确性和旁路门槛，才安排一次必要的配对对照；只有初次 A/B 有收益且顺序影响仍未排除时，才增加反向 B/A 确认。新增这类对照的目的，是满足最新的可比启动要求，不是重新搜集旧基线。
5. **固定容量**：C1 无已验证收益，后续新分配的推荐参考为原容量 A0/G0 设置。若因具体资源选择其他容量，也必须在该轮 A/B 双方固定并单独标记，不能把容量变化计为 Router 收益。

## 判断收益

- 共同指标：有效 output tokens/s/GPU、成功请求率、TTFT p50/p90/p99、ITL、错误/取消、实际输入输出长度。total tokens/s 包含命中输入，不单独作为收益判据。
- R1/R4 机制指标：P rank 待处理负载、P queue、forward、缓存命中与重算量。
- R2：各 D rank 在途输入分布、实际 allocated/pending KV、alloc_wait 的尾部及超长等待比例；关注负载是否只是转移到 P/KV 传输。
- R3：全候选 host 机会、选中目标 host 回读、miss/recompute、回读延迟和 P queue。
- 用输入长度/输出长度/会话阶段分层，配对交集只作辅助；请求不是独立重复实验，不能用大量请求样本掩盖只有一轮运行的问题。
- 提前截断输出、增加失败、排除慢请求或不完整采集带来的提速不算收益。抢占导致窗口不完整则标无效。
- 单轮方向一致只能形成候选结论；推广默认值需可重复的端到端收益和机制证据。每轮保存代码版本、构建哈希、开关、环境清单、原始证据和结论。
