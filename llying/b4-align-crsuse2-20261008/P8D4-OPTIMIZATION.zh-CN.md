# P8D4 的瓶颈分析与优化方案

对象：1P(TP8) + 1D(TP4) C80（`RESULT-P8D4.zh-CN.md`，运行
`b4-crsuse2-136-138-d4-20261009T0632Z`）。对照是同集群同配置的 P8D8（`RESULT.zh-CN.md`）。
数据来自 D 端 2 秒一次的引擎采样（正式窗口 07:07:20–08:07:20，1,791 个样本）、D 端诊断日志
和 aus 的 `analyze.py`；代码引用以 router commit `19a6c1d2` 和本次镜像的 SGLang 为准。

## 1. 瓶颈：D 的 KV 占用集中在个别 rank

按整小时累计，4 个 D rank 的负载均衡：

| dp3 | 1,787 | 215.9 |

但同一时刻的 KV 占用和排队长期集中在 dp2、dp3（后段加上 dp0），dp1 一直有约一半空闲：

| D rank | 被 KV 预算阻塞的请求 | 分配等待 均值 / p90 | 生成时间均值 | KV 占用均值 | 占用 >90% 的时间 | 预分配排队均值 |
|---|---:|---:|---:|---:|---:|---:|
| dp0 | 279 | 9.3 / 26.7 s | 16.3 s | 67.6% | 28.6% | 4.8 |
| dp1 | 66 | 0.3 / 0.0 s | 14.3 s | 50.2% | 6.6% | 0.13 |

- 4 个 rank 的平均占用约 72%；52% 的样本中最热 rank >90% 而最冷 rank <50%，4 个 rank 同时

## 2. 原因：会话亲和固定 D rank，router 之后不再看 D 的占用

- router 选 D rank 只看负载：D 以 `--no-enable-kv-events` 启动，router 记录的 D worker
  `kv_block_size=None`、`kv_events_endpoint=None`，前缀命中恒为 0，成本只有负载（在途块数 +
  最近派发且未命中的块数）；`--kv-decode-overlap-weight 2` 不起作用。
- 会话亲和 `both` 只在会话第一轮按负载选 D，之后固定。agentic 会话的上下文逐轮增长，几条长会话
  固定在同一 rank 上，该 rank 就持续满载；新会话会避开它，但已固定的会话仍一直送进去。
- R2（按 D 需求调度）只影响新会话的第一次选择，单独打开不能解决已固定会话造成的热点。

## 3. D radix 不是瓶颈，不应关闭

- 接纳判断把可淘汰的 radix 缓存算作可用空间（`decode.py` 的 `_allocatable_token_budgets`：
  "Include evictable decode-radix cache entries in the budget -- they can be freed on demand
  before allocation"）。radix 保存历史前缀不会让新请求更容易被阻塞。
- 命中时只需分配未命中的部分，传输量也相应减少；P8D4 仍有 35% 的复用。
- 真正占住接纳预算的是活跃请求的 KV，加上每个请求为后续生成预留的 KV（`min(max_new_tokens,
  4096)`，相对约 11 万的平均输入约 3.5%）。
- 前缀匹配不影响 D 选哪个 rank（router 看不到 D 的缓存），只影响选定之后的复用量。

## 4. 优化方案

| 方案 | 改动 | 预期作用 | 代价 / 风险 |
|---|---|---|---|
| A. D 每轮按负载选 rank | `INFERA_SESSION_AFFINITY=prefill`（只固定 P） | 把热点 rank 的排队分流到空闲 rank | D 复用下降（aus 的 B2 在只固定 P、D radix 开时约 24%），传输量增加；P8D4 的传输尾与 P8D8 持平，不是瓶颈 |
| B. D 绑定 + 拥塞逃逸 | router 改动：固定的 D rank 占用超阈值或排队时改选最闲 rank | 兼顾复用与均衡 | router 需读取 D 的实际占用；需开发与测试 |
| C. 增加每张 D 卡的 KV | D cuda graph 最大 batch 256→64（每 rank 实际运行 7–10 个，现 graph 占 7.7 GB/rank），D `mem-fraction` 0.85→0.90 | 每 rank KV 约 +13%（约 51 KB/token） | 需确认无显存不足 |
| D. agentic 淘汰策略 tlru | 需 SGLang 0917 之后的版本 | 优先保留影响 TTFT 尾部的前缀 | 偏离 B4 的软件版本 |
| E. 让 D 上报 KV 事件 | 改 `engine.sh` 对 D 写死的 `--no-enable-kv-events` | router 选 D 时成本 = −2 × 命中 + 负载：负载相近时回到有缓存的 rank，拥塞时自然避开，相当于内建的拥塞逃逸 | D 上报事件的链路在本集群未验证 |

不建议：关闭 D radix（增加 KV 需求，见第 3 节）；D 开 HiCache（与 MTP 不兼容）。

已执行：A + C 一起（运行 `b4-crsuse2-136-138-d4-ponly-g64-m090-20261009T0848Z`）。实测 D 每 rank
KV 从 2,111,808 增至 2,378,624（+12.6%），4 个 rank 合计约 951 万。

## 5. 能否超过 P8D8：门槛与估计

P8D4 只用 12 张卡，每卡超过 P8D8 只需总吞吐达到 P8D8 的 75%：

| | 总 token/s | Total token/s/GPU |
|---|---:|---:|
| P8D8（16 卡） | 360,343 | 22,521 |
| P8D4 调优前（12 卡） | 231,107 | 19,259 |
| P8D4 超过 P8D8 所需 | ≥ 270,257 | ≥ 22,521 |

即总吞吐比调优前提高 17% 以上（按 Output token/s/GPU 约 10%）。

调优前端到端时延均值 36.8 s，P8D8 18.4 s，差距来自 D 分配等待（均值 15.9 s，P8D8 0.04 s，调优
目标）和 D 生成变慢（17.5 s 对 13.6 s，D 每 rank 并发更高，调优不能消除）。

若负载均衡消除大部分分配等待，粗略推算：

- TTFT 回到约 4–5 s，D 生成约 16–17 s（热点与空闲 rank 平均），端到端约 21–22 s，比 P8D8 慢约 15%。
- P8D8 每个请求之间约有 9 s 客户端间隔（由 80 条会话与完成速率按 Little 定律反推：平均在途
  约 54 个），循环时间只慢约 10%，总吞吐约为 P8D8 的 90%，约 32 万 token/s，即约
  2.7 万 token/s/GPU，比 P8D8 高约 20%。
- KV 容量：按该吞吐，D 上同时驻留约 50 个请求、约 600 万 token，对 951 万容量平均占用约 60–65%。

风险：router 的 D 负载是它统计的在途块数而非 D 实际 KV 占用，长短请求差异大时仍可能有局部热点；
D 复用下降会多占一部分新增容量；D 的 ITL 可能比估计涨得多；两边都是单轮测量。

结论：预计调优后在 21k–27k token/s/GPU 之间，大概率追平或超过 P8D8 的 22.5k。验证时先看 D 各
rank 占用是否均衡、阻塞请求还剩多少。

## 6. 调优结果（A + C）与新的根因

运行 `b4-crsuse2-136-138-d4-ponly-g64-m090-20261009T0848Z`，正式窗口 09:53:29–10:53:58，数据在
`results/b4-crsuse2-136-138-d4-ponly-g64-m090-20261009T0848Z/`。

| 指标 | P8D8（16 卡） | P8D4 调优前 | P8D4 调优后 | 调优后对调优前 |
|---|---:|---:|---:|---:|
| Total token/s/GPU | 22,521 | 19,259 | 21,081 | +9.5% |
| Output token/s/GPU | 171.43 | 156.37 | 172.42 | +10.3% |
| 完成请求 | 10,644 | 7,287 | 7,990 | +9.6% |
| TTFT p50 / p90 s | 3.40 / 8.45 | 6.28 / 57.23 | 3.76 / 45.79 | −40% / −20% |
| ITL p50 / p90 ms | 14.16 / 21.45 | 19.45 / 22.00 | 19.89 / 22.50 | +2% / +2% |
| 被 D KV 预算阻塞的请求 | 40 | 1,597 | 1,427 | −11% |
| D 分配等待 均值 / p90 s | 0.04 / 0.003 | 15.9 / 52.3 | 10.5 / 41.4 | −34% / −21% |
| D 本地复用 % | 89.2 | 35.3 | 14.0 | −21 pp |

- 未达到第 5 节的估计：Total token/s/GPU 21.1k，仍低于 P8D8 6.4%；Output token/s/GPU 已略高于
  P8D8（+0.6%）。TTFT p50 接近 P8D8，但 p90 仍是 45.8 s。
- 负载只部分均衡：D 各 rank KV 占用均值 79.9 / 73.3 / 66.0 / 65.6%，一热一冷的样本从 52% 降到 36%，
  各 rank 平均差距仍有 42 pp；4 个 rank 同时 >85% 的样本只有 0.8%，总容量仍有余量。

**新的根因：router 对 D 没有按 token 的负载信号，实际在按请求个数轮转。** 4 个 D rank 分到的请求数
几乎相同（2,004 / 1,979 / 2,002 / 2,005），而单个请求从几万到几十万 token 不等。原因在 router
（`policy.rs`，`19a6c1d2`）：

- 负载 = 在途块数 + 最近派发未命中的块数。D 未上报 `kv_block_size`，请求切块为空：
  `on_request_started` 对空块列表直接返回，在途块数恒为 0；`record_dispatch` 对空块每次只记
  `UNKNOWN_COST_BLOCKS = 1.0`，按每次派发 0.97 衰减。
- 所以 D 的选择只取决于最近给每个 rank 派了几个请求，与请求长度和是否完成无关。只固定 P 之后，
  这种轮转让请求数均匀了，但 KV 占用仍随长请求的落点而不均。

**下一步：在只固定 P 的基础上打开 R2（`INFERA_R2_DECODE_DEMAND=on`）。** R2 在选择时按 token 记账：
每个请求派发时把自己的 token 数记到所选 rank，完成时释放；成本 = 该 rank 在途 token + 本请求 token，
取最小。D 每轮都重新选，R2 对每一轮生效，这正是缺的按 KV 用量均衡。router 不需改代码，config 新增
`B4_R2` 开关即可。

## 7. 记录中的数据缺口

P8D8 那一轮重跑测量时引擎/节点采样器因输出文件已存在而退出，缺少 D 的 KV 占用时间序列，无法与
P8D4 对照不均衡程度；客户端与诊断日志的分析不受影响。`run_b4.py` 已修复（`8286bf77`）。
