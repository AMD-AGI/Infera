# R1＋P-only 会话亲和：C80 / 4K 完整性能结果

2026-09-28。**代码复核及完整一小时性能实验已完成。相对历史 G0（R1-only），输出吞吐提升 2.15%，平均 TTFT 降低 14.04%，TTFT p95 降低 19.25%；平均 ITL 增加 6.68%。当前证据支持缓存利用和首 token 等待改善，吞吐增幅较小，尚不能视为已证明的稳定提升。**

## 配置与比较口径

本轮只增加 P 会话亲和：`INFERA_SESSION_AFFINITY=prefill`，空闲 TTL3600 秒，客户端由稳定的 correlation ID 生成 `X-Dynamo-Session-ID`。R1=completion，P/D权重20/2，R2/R3/R4关闭；首次选择仍使用 Infera 原评分，没有实现完整 Dynamo 成本公式或开启主动拥塞逃逸。

C80，P/D各8卡，TP8/DP8/EP1，有效chunk均为4096；P HiCache ratio1.5、write_through/kernel/page_first，D HiCache关闭；模型、MTP、种子、数据集和客户端依赖与历史配置一致。镜像 `infera-sglang:aus-0922-reqtrace`，image ID `sha256:4f125ff9096f75611fa24caad4c01c3707dd0892251680a6483b99ffaa2a88bb`。

最终代码提交 `d7c8cae3`，Router SHA256 `cd0000356c5150baac1f5551db7a485c05ab3b789df11ed14d04dad0c4129211`。此版本在已验证的会话亲和代码上补齐 NATS 终止帧失效处理，本轮使用 HTTP；330 项可运行离线测试通过。详见 [代码复核](REVIEW.zh-CN.md)。

使用用户 allocation31999：P=n10-29，D=n03-33。历史G0的P同样为n10-29，D为n02-21；G0使用复用引擎，本轮P重新启动、D复用本次smoke进程。未重跑基线，未执行weight40实验。不同D节点、运行时间和缓存历史仍是比较限制。

正式发送窗口为 **07:17:40.481–08:17:40.481 UTC**，随后按相同规则排空30秒并取消剩余请求。发送10,266条，完成10,252条，14条边界取消；正式导出错误0。预热884条中有5条空内容解析错误，另列统计，没有删除或记为成功。

## 功能确实生效，以及收益来自哪里

10,252条正式完成请求全部找到P/D记录，bootstrap room一致。以客户端 `x_correlation_id` 关联会话后：正式阶段有1,898个会话，其中490个具备多条P记录，**490个全部保持同一P rank，P rank切换次数为0**；487个会话的D记录分布在多个rank，符合P-only模式。P完成释放日志覆盖全部正式记录，观察到的11,150条P完成日志均为separated=true。

缓存改善主要来自更多host命中，而非GPU命中率大幅上升。请求级数据表明，更多前缀被复用，减少了新计算量，与P计算包络及排队下降的方向一致。D平均正在生成的请求更多，等待KV的请求减少；但ITL也更长，因此不能将本轮描述为所有阶段都加速。

匹配相同来源trace turn、输入差≤8 tokens且≤0.1%、实际输出长度相同的 **9,394对请求**：

| 匹配请求指标 | G0 | 本轮 | 变化 |
|---|---:|---:|---:|
| 平均未命中tokens | 5,636.8 | 4,730.8 | −16.07% |
| 平均TTFT | 7.677秒 | 6.627秒 | −13.68% |
| P平均排队 | 2.745秒 | 2.065秒 | −24.78% |
| P forward envelope均值 | 2.904秒 | 2.578秒 | −11.23% |

匹配结果支持收益并非仅由本轮输入/输出更短造成，但这是完成请求交集，仍有选择效应；同长度不等于逐字节完全相同，请求也不是独立实验重复。

## 验证边界与异常记录

- 两端各8个scheduler PID和启动信息在正式前后保持一致；模型与tokenizer元数据哈希与G0一致。该检查不等于重新哈希全部权重分片。
- AIPerf导出出现聚合计数器reset警告；未据此判定引擎重启。缓存收益采用请求级P记录，不使用有口径歧义的AIPerf聚合GPU/host命中率。
- 正式窗口每端引擎采样1788次，其中6次查询错误，有效并发统计使用1782次有效采样；节点采样每端719次。缺失不补零。
- 客户端第一次启动缺少共享Python及约束文件挂载，在发送负载前退出；补齐挂载后重试，模型服务未重启。采样器恢复及新节点known_hosts补齐发生在预热阶段，预热前半段资源采样不完整，正式窗口资源记录保留。控制端另有短暂工具沙箱启动故障，节点上的实验未中断。
- 5条预热空内容错误均有P/D同room、双方输出1 token的引擎记录，与此前已排查的错误类型一致；未保存这些请求的实际输出token ID，不能逐条断言具体token原因。正式请求没有此类导出错误。
- P forward envelope包含调度间隙；D等待KV包含等待P、计算及传输，不能称为纯网络耗时，也不能与P阶段重复相加。

## 判断与后续

本case可以保留P-only会话亲和作为候选策略。较一致的证据是缓存利用、P等待和TTFT改善；输出吞吐仅提升约2.15%，还伴随ITL增加，应按业务对首token延迟与后续生成速度的取舍判断，不自动将其提升为所有负载的默认策略。

本轮不支持直接推出both模式更优，也不证明完整Dynamo首次评分会带来相同收益。后续若继续优化，应先分析局部排队长尾，再决定是否增加受约束的重选；不要把本轮结果解释为需要立即加入任意拥塞阈值。
