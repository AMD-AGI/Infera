## 主表新增分位数带来的判断修正

- **Triton主要改善TTFT，不能概括成所有延迟分位数都改善。** 同节点TTFT p50 4.235→3.211秒（−24.18%）、p90 11.529→7.811秒（−32.25%）；ITL p50 14.60→14.46ms，但p90 20.13→20.16ms，基本持平且略升。对应Interactivity p90 49.68→49.61 tok/s，未显示生成慢尾提速。Total tok/s/GPU +5.94%与Output +3.38%也不是同一收益口径。
- **只开D radix改善的是TTFT尾部，p50未改善。** p50 4.069→4.118秒（+1.19%），p90 12.296→10.796秒（−12.20%）；ITL p50/p90均略差。此前只列平均TTFT会掩盖这种差别。
- **再加D绑定主要改善生成阶段分位数，TTFT p90没有改善。** ITL p50 14.43→13.82ms、p90 19.87→19.49ms，Interactivity随之改善；TTFT p90却10.796→11.027秒（+2.13%）。这与D侧节省未消除P侧等待相容；恢复数据限制仍适用。
- **P绑定改善TTFT，却牺牲了一些ITL。** 相对历史R1，TTFT p50/p90下降约10.53%/21.21%，ITL p50/p90上升约5.52%/4.72%；D running batch变大可能参与这种权衡，且D节点变化限制了因果判断。

## 维度一：有效 prefill batch 与 decode batch

这里将“efficient prefill batch”落到可直接验证的 **每个P本地batch实际新增计算tokens**，读取日志 `#new-token`，不把命中的前缀算进batch。它是工作量，不是效率评分：miss增加也会使batch更大。

- P新tokens/本地batch：每条Prefill batch日志的 `#new-token`，所有8个DP rank的日志合并统计；P序列数来自 `#new-seq`，含chunk续算，不能理解成新会话数。日志新token口径可能含重处理；有效新计算tok/s则独立使用剔除reprocessed tokens的 `prefill_effective_tokens_total{mode=input}` 差分。
- P满chunk占比：新tokens≥该实验chunk预算（4096或8192）的batch日志比例；不是GPU利用率，也不是DP/TP padding效率。
- D运行本地batch：Decode batch周期日志的 `#running-req`。日志按decode迭代间隔输出，偏向有执行的时间；并非每一步的完整GPU batch直方图。
- D采样running总数：约2秒一次读取8个rank的 `num_running_reqs` 并求和，排除缺rank的帧。这是各rank最近一次上报的运行请求数，非同一个同步forward的全局batch；因此不能由此反推出真实同步batch、padding或GPU饱和度。DP attention各rank仍参与TP协作，不能当作8个互不相关的GPU。
- “均值 / p50 / p90”顺序固定；所有行使用表头中同一单位。日志统计没有加入空闲零batch，不能与时间采样均值混用。

**可以看出的变化：**

1. **R1的收益没有依赖更大的P batch。** 原容量下，P平均新tokens/batch从3463降至3295，满chunk占比73.49%→66.16%；D采样running总数36.32→36.62，大致不变，而TTFT明显改善。结合P排队下降，这更符合减少无效等待、改善缓存选择，而非扩大batch。
2. **R4呈现“P更满、D更饿”。** 相对R1，P平均新tokens/batch3295→3993，满chunk占比66.16%→95.39%；有效新计算速率15.59K→24.33K tok/s，但D采样running总数36.62→23.61，D日志本地batch4.44→2.99。结合miss大增和吞吐下降，P忙在额外重算，不能把更满的batch判为优化成功。
3. **C112也没有把更多并发转成更大的D运行batch。** 相对C80，P平均新tokens/batch3490→3816，但D采样running总数35.42→32.62；新增并发主要堆在等待阶段。ITL较低可以与实际D运行batch变小相容，不能单独称为系统提速。
4. **8K确实增大了P本地batch，却没有带来性能提升。** 相对同节点4K，平均新tokens/batch3433→5768（约+68%），满chunk占比72.20%→55.32%，D running总数36.40→34.64。chunk上限翻倍不等于每个batch都翻倍；P服务窗口反而变长，主表的TTFT与吞吐均不支持8K。
5. **P绑定减少P工作，D获得更连续的供给。** 相对历史R1，P平均新tokens/batch3295→3073，有效新计算15.59K→13.26K tok/s；D running总数36.62→39.27。跨节点限制仍在，但方向与减少会话漂移和miss相符。
6. **D radix再加D绑定没有明显扩大D batch。** D running总数40.09→39.78，D日志本地batch4.82→4.75，P平均新tokens/batch也基本不变。这与“网络/缓存复用显著改善，但请求容量尚无明确增幅”的判断一致；后者还受输出长度变化及B3尾部缺失限制。
7. **Triton收益来自单位时间处理与排队改善，不能归因于更大的batch。** 同节点下，P平均新tokens/batch3053→2919，满chunk占比56.85%→51.63%；D running总数39.35→40.22，仅小幅增长。有效新计算速率13.08K→13.69K tok/s，同时完成量增加、P forward窗口与排队缩短。这里没有独立GPU kernel计时，不能给出纯算子加速比。

大多数4K轮次的P batch p50/p90都等于4096，因此**只看p50/p90会隐藏差异**；均值、满chunk比例以及有效计算总量是必要补充。当前没有保存每次TP协同forward各rank实际/padded token shape，不能计算严格的padding效率；该项不能用日志batch数替代。

## 维度二：Decode KV cache占用与局部压力

分母是同一采样中D各rank的 `max_total_num_tokens`，不是显卡总显存。已测轮次D容量均为每rank 3,003,264 tokens，共8个rank。三个概念必须区分：

- **不可淘汰KV（active）**：`kv_used_tokens / capacity`。包含正在使用/锁定、以及已分配但可能仍在等待P/KV的请求；不等于只有正在生成的请求占用。
- **resident KV**：`(kv_used_tokens + kv_evictable_tokens) / capacity`。包含能淘汰的历史radix cache。
- **空闲块**：`1 - resident`。理论可回收空间是“空闲＋可淘汰”，即 `1-active`，但不代表新的请求在任意rank都能立即分配成功。

“最热rank p90”是每帧先取各rank active占比最大值，再跨帧取p90；“一热一空”表示同一帧max active>90%、min active<50%，用于识别平均占用掩盖的局部压力。比例变化不是物理显存分配池大小的变化。

**可以看出的变化：**

1. **D radix使resident接近满，但active没有接近满。** P绑定基线active/resident均约34.11%；单开D radix后active约33.99%、resident约94.87%；再加D绑定active约33.82%、resident约97.25%。主要变化是多保存了可复用、可淘汰的历史前缀。不能因为resident>95%就断言D活跃KV已满。
2. **同节点Triton前后D active反而下降。** active均值34.00%→32.29%，resident约96.70%→96.89%；D running数量略增而active下降，两者不矛盾，因为请求上下文长度、等待KV驻留时间和共享前缀会影响每条请求的占用。当前数据不支持把Triton收益归因于增大D缓存容量。
3. **C112存在真实的局部压力上升。** active均值35.94%→56.08%，一热一空比例10.11%→46.59%，预分配队列均值0.089→2.146。与此同时D running batch减少，说明更高占用并不等于更多请求正在有效生成，等待与局部不均衡需要共同考虑。
4. **R4也出现“运行更少、占用更高”。** active均值34.28%→42.49%，D running总数36.62→23.61，而等待KV队列大幅增长。请求提前占住D空间后在P侧长等，与该现象相容；单看batch或单看全局平均cache都会漏掉问题。
5. **最新组合没有持续严重的D分配排队证据。** 新节点TileLang与Triton的预分配队列很低，一热一空样本分别约0.45%和0.63%。这不证明没有瞬时局部压力；只是现有采样不支持将D全局KV容量作为首要瓶颈。

**对P8+D4计划的含义：** 当前D存在可回收KV空间，值得做减少D卡数的实验，但无法据此判定4卡足够。TP8→TP4会同时改变KV分片、每卡模型/缓存预算、计算带宽与通信；容量不会简单按“34%×2”推算。驱逐历史cache还可能降低当前约92%的D复用。P8+D4仍需真实配置容量和C80数据验证。

## 维度三：排队、P服务窗口与D供给

P forward为请求的墙钟观测窗口，包含调度间隙，不是纯GPU kernel时间。P局部积压样本表示某rank排队≥4、同时另一rank队列为0；空队列不等于该rank对应一张独立空闲GPU。D“等待KV”来自transfer队列，覆盖等待P计算/队列/传输的时间，不能全部解释为网络传输瓶颈。
