## 已有数据的结论（v3 `fix-02`、v4 `fix-03`）

- 逐 rail 对账：两轮中，136 发出的 RDMA 包（ACK 方向）与发送端收到的完全相等，
  ACK 没有在网络上丢失；数据方向只有 v3 `ionic_3` 少 3,074 包、v4 `ionic_0` 少 3 包。
- v4 重传的包全部是接收端已收到的（`ionic_5` 3,134 / 3,134，`ionic_1` 796 / 796）。
  即 ACK 都送达了，发送端却在 4.3 s 内判定超时。
- 超时所在 10 秒窗里，所在 rail 的流量没有中断（每 10 秒仍有上百万包）；单个 QP
  的停顿在 rail 总量上看不出来。
- 节点的内核日志无权读取（journal/dmesg 需要 root）；超时时刻前后 Mooncake 没有告警。
- 两种解释：ACK 真的晚到 4.3 s 以上，或者网卡的 ACK 计时器不按配置的超时触发。
  B 轮用 69 s 区分：超时仍出现就是计时器问题，消失则说明存在 4.3–69 s 的 ACK 延迟。

## B 轮结果：69 s 超时让每次停顿变成失败

同一合同、同一镜像，只把两端 `MC_IB_TIMEOUT` 改为 24：

| | A 轮（超时 18，1.07 s） | B 轮（超时 24，69 s） |
|---|---|---|
| profiling 完成请求 | 2608 | 1387（结束时 102 个在途被取消） |
| 客户端错误 | 0 | 2 |
| transfer failure / session failed | 0 / 0 | 3 / 1（另 2 次 `session not alive`） |
| CQE12 / retry exhausted | 0 / 0 | 0 / 0 |
| ACK timeout | 71 | 46 |
| aiperf 结果 | 通过 | 失败：TTFT 只覆盖 63.7% 的窗口（要求 95%） |

- 05:01:35 prefill DP0 报 `Sync batch data transfer timeout after 30046007106ns`，随后
  `Session 10.245.154.168:15124 failed` 和 3 个 `Prefill transfer failed`：一次本可在 1 秒
  内恢复的停顿，在 69 s 超时下先触发了 Mooncake 自己的 30 秒同步传输超时。
- 之后 `ionic_6` 上同一个 QP 以 69、134、268 s 的间隔重传了 8192 包的窗口（共 57,344 包），
  这些包全部到达 136 的 MAC（该 rail 的 MAC 缺口只有约 800 帧本底），但没有进入 RDMA
  引擎，也没有任何错误计数。推测 session 失败后对端 QP 已被重建，旧 QP 的重传被静默丢弃。
- 结论：剩余的 ACK timeout 不是计时器在流量正常时误触发；每一次都对应一个真的停住、
  只能靠超时重传恢复的 QP，停顿时长等于超时时长。超时必须保持短：1.07 s 下全部自行
  恢复，69 s 下变成失败。

## 停顿发生在哪里

- 纯重复包事件：原包都已进入 136 的 RDMA 引擎，ACK 的发送数与接收数完全相等，但 136
  没有及时为这些包回 ACK，直到收到重传的重复包。
- 约 1.5 千包的事件（例如 B 轮 `ionic_4` 1,566 包）：包到达 136 的 MAC，却在网卡内部
  被丢弃，同样没有错误计数。
- 只有 A 轮开头的冷启动丢包在网络里（MAC 层就少了约 12 万帧）。
- 以上运行的接收端都是 136，于是交换角色（136 发送、138 接收）验证，见下节。

- 结论：两种现象跟着接收角色走，不是 136 这块网卡的问题；136 作为发送端也没有异常。

  定位需要网卡内部计数或固件日志（root/厂商）。
