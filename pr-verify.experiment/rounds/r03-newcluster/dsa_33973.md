## Why it does not reproduce, so far — a source-level explanation

The line the PR replaces is not on the ordinary decode path. `dsa_backend.py:790`:

```python
if forward_batch.seq_lens_cpu is not None:
    max_seqlen_k = int(forward_batch.seq_lens_cpu.max().item() + draft_token_num)
else:
    # needs_cpu_seq_lens=False nulls the host mirror for spec-v2 relay
    # batches; graph replay uses the static page-table width, so only this
    # eager (e.g. over-capture-bs) fallback needs a length here.
    max_seqlen_k = int(forward_batch.seq_lens.max().item()) + draft_token_num   # <- the defect
```

The faulting `.item()` runs **only when `seq_lens_cpu is None`**, which the comment
attributes to an *eager* fallback — e.g. a batch larger than any captured CUDA
graph. Measured on this decode leg: `disable_cuda_graph=False`, and the captured
batch sizes top out at **128 per DP rank** (`Capture draft decode CUDA graph begin
... bs=[1, 2, ..., 128]`). A single small request replays a captured graph and never
enters the branch at all.

That is consistent with the rig having served this whole session — the #33970 A/B,
the benches, every smoke test — on a DP8 + MTP decode leg without once deadlocking.
The branch simply was not entered.

## Attempt to force the eager fallback — inconclusive, and it found something else

Driving concurrency to 1600 (ISL 1024 / OSL 64) to push per-rank batch past 128
killed the decode engine, but **not with a deadlock**:


**This is not the #33973 defect.** The assertion is on `shape[0]`, the batch
dimension (`qo_len`), whereas the PR changes `max_seqlen_k`, the page-table
*width* (`shape[1]`). Different axis, different failure mode: a crash with a
traceback, not a hang. It is much more likely a capacity/batching problem at
concurrency 1600 on this deployment than anything to do with D2H syncs.

Worth reporting separately if it reproduces at a sane concurrency; **not** evidence
for or against this PR, and it must not be written up as such.

## The branch WAS reached — and still no deadlock. This narrows it sharply.

Rather than infer branch entry from batch sizes, I instrumented the defect site
directly (a one-shot stderr marker immediately before
`max_seqlen_k = int(forward_batch.seq_lens.max().item()) + draft_token_num`) and
relaunched the decode leg with `CUDA_GRAPH_BS=4`, so any decode batch above 4 falls
out of graph replay into the eager path.

32 concurrent requests, stock arm:

```
200 x32, wall clock 13 s
[DSA-EAGER-BRANCH] markers in the decode log: 229
distinct pids that printed it:                  8
```

So the situation is **not** "the branch was never entered". The defective
`.item()` D2H sync executed **229 times across all 8 DP ranks**, and the group did
not deadlock — every request completed.

**Why: all 8 ranks entered it together.** The deadlock the PR describes requires the
ranks to *diverge* — the PR's own comment says "an idle DP peer keeps its host
mirror and takes the arm above", so the hang needs some ranks in the `if` arm and
others in the `else` arm at the same step. A uniform benchmark load puts all eight
in the same arm, they issue the same collective sequence, and the sync is harmless.

That is a much more specific negative than before, and it points at exactly what is
missing: **rank divergence**, not branch coverage.

## What would actually settle it

The mechanism the PR describes needs three things at once:
1. `seq_lens_cpu is None` — i.e. the eager, over-capture-bs fallback, **not** graph
   replay;
2. DP ranks that **diverge** — an idle DP peer keeps its host mirror and takes the
   `if` arm, while a busy one takes the `else`;
3. the resulting per-rank difference in collective sequence.

Conditions 1 and 3 are now satisfied and measured; **condition 2 — divergence — is
the one that is missing.** The `CUDA_GRAPH_BS=4` trick already solves branch
coverage cheaply and should be kept; what remains is to make the ranks disagree.

### Divergence was attempted directly, and DP-attention prevented it

The obvious lever is a batch that is not a multiple of `dp_size`, so some ranks sit
idle. Tried: **3 concurrent requests against dp8**, which should leave 5 ranks with
nothing to do. Re-instrumented with a per-invocation batch-size tag first.

```
3 requests -> 200 200 200, wall clock 16 s, no hang
distinct pids entering the eager branch:  8   (i.e. ALL ranks)
batch sizes seen at the branch:           bs=1   (only)
```

**All eight ranks entered the branch, each with `bs=1`.** That is the answer to why
this will not reproduce by varying load: DP-attention **pads every rank to a uniform
batch**, so even a 3-request load has all eight ranks stepping together with the
same shape. They take the same arm, issue the same collectives, and the D2H sync is
harmless no matter how many times it runs.

So load shaping is the wrong lever entirely. Whatever produces the divergence in the
field is not "some ranks are idle" in this padded sense — the padding removes exactly
that. This is a genuine narrowing: two plausible approaches (bigger batches,
non-multiple batches) are now **ruled out by measurement**, not untried.

Concrete next steps, with the two ruled-out approaches removed:

- **Find what actually sets `needs_cpu_seq_lens=False`.** That is the *other* door
  into this branch, and it does not depend on load at all.
  `deepseek_v4_backend.py:611` computes it as
  `not spec_alg.is_dspark() and (...)`, and `:512` defaults it to `False`. If a
  spec-decoding configuration makes this backend null the host mirror for **relay**
  batches only, that is a per-batch-kind divergence — some batches carry
  `seq_lens_cpu`, others do not — which is much closer to the PR's "spec-v2 relay
  batches" wording than anything load-shaped. Start by reading :611's full
  condition and finding which server flags flip it.
- **Check whether MTP relay/verify batches differ from plain decode batches** in
  whether they carry `seq_lens_cpu`. The instrumentation should log
  `forward_batch.forward_mode` alongside the batch size; a mix of modes at the same
  step is the divergence signature to look for.
- **Ask the reporter for the configuration.** The local patch record says this was
  seen in the field; the fastest path to a reproduction is the exact server flags it
  was seen under, rather than re-deriving them.

Keep `CUDA_GRAPH_BS=4` and the instrumentation — both worked and made the negative
result precise rather than ambiguous. Log `forward_mode` next time as well as pid
and batch size.

## Source-level review, which is done and holds

Independent of the hardware, the PR's two removals check out on current `main`:

- **`metadata.seq_lens_sum` has no readers that this path reaches.**
  `dsa_backend.py:994` reads `forward_batch.seq_lens_sum`, but it sits inside the
  `elif forward_batch.forward_mode.is_extend():` arm at :905 — and DRAFT_EXTEND_V2
  is **not** `is_extend()`, because `include_draft_extend_v2` defaults to `False`
  (`forward_batch_info.py:133`). The other reader, :3356, is gated on
  `is_blackwell()` and `ForwardMode.EXTEND`.
- **`extend_prefix_lens_cpu`** is likewise consumed only in that same `is_extend()`
  arm.
- **The over-allocation argument is sound.** Using `self.req_to_token.shape[1]`
  widens the page table; the extra columns are never selected because top-k masks
  per row by `cache_seqlens`.

So the code change is defensible on reading. What is missing is only the hardware
demonstration that the deadlock it prevents actually occurs.
