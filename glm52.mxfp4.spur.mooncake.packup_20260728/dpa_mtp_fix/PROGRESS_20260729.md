## 2. Bug 3 is unreachable in our topology — MEASURED

The upstream fix guards on:

```python
tp_group = get_attention_tp_group() if is_dp_attention_enabled() else get_tp_group()
if tp_group.world_size > 1:          # <-- never true for us
```

With `tp_size=8, dp_size=8`:

```python
attn_tp_size = tp_size // attn_dp_size // attn_cp_size = 8 // 8 // 1 = 1
```

Runtime-confirmed in-image:
`compute_dp_attention_world_info(True, 0, 8, 8, 1)` → `(0, 1, 0, 8)` → guard is **False**.

**In pure DP-attention (`dp_size == tp_size`) each attention-TP group holds exactly one
GPU, so there is nobody to broadcast to.** #31071 fixes divergence *within* an
attention-TP group; ours is *across* DP ranks. Different axis.

**This also resolves the `--disable-custom-all-reduce` contradiction** flagged as
UNRESOLVED in `ECOSYSTEM_glm52_amd_mtp.md` §7. The answer is neither of the two
hypotheses recorded there: **the #31071 lead never matched our topology at all.**
→ **ECOSYSTEM_glm52_amd_mtp.md §7 needs updating with this third answer.**

Consequence: PR #31683's value to us drops. Its broadcast hunk is a no-op here; only
its **idle-DP-rank empty-tensor** commits remain potentially relevant (those are
independent of `attn_tp_size`).

The patch is left applied — harmless, correct upstream behaviour, and needed if we
ever run `dp_size < tp_size`. But **it earns no credit for any future pass.**

## 3. Bug 4 falsified

Real defect, correctly diagnosed, **not the cause**. `publish()` early-returns for
idle ranks *before* lazily constructing the event, so `publish_ready` stays `None`
forever on those ranks; `resolve_seq_lens_cpu`'s `if publish_ready is not None:`
guard is then False exactly there. Upstream has never touched it (12 PRs touch the
file, none change the early return).

Fix applied in two required parts (`scripts/fix_bug4_uniform_event.py`):
- **part 1** — `publish()` creates+records the event unconditionally; only the buffer
  write stays gated on having work. Ordering preserved (record still after write).
- **part 2** — hoist the wait above the early returns in `resolve_seq_lens_cpu`.

Part 2 alone was tried earlier (`scripts/hoist_sync.py`) and failed *because the guard
itself is the divergence* — part 1 is what makes part 2 meaningful. Both together:
**hang unchanged.**

Keep or drop? It is a genuine latent bug and still worth upstreaming, but it is **not**
this deadlock. Do not count it as a fix.

## 4. The actual unexplained observation

Stable across every run, before and after Bugs 3 and 4:

```
DP0: draft_forward           (eagle_worker_v2.py:697)   <- still in draft
DP3: _draft_extend_for_decode(eagle_worker_v2.py:965)   <- already in draft_extend
```

All 8 ranks block in the *same* `all_gather_into_tensor`
(`dp_gather_replicate` ← `_gather_hidden_states_and_residual` ← `prepare_mlp` ←
`deepseek_v2.py:2242`), but from **different MTP pipeline stages**, so the collectives
can never pair. GPU use splits (some 100 % spinning, some 0 %).

These three stages are sequential calls inside one function
(`eagle_worker_v2.forward_batch_generation`): `draft()` → `verify()` →
`_draft_extend_for_decode()`.

Earlier, with the loop probe installed, the split matched `global_num_tokens` exactly
(`gnt=[1,1,1,0,0,0,0,1]` → ranks 0,1,2,7 in `draft()`; ranks 3,4,5,6 in
`_draft_extend_for_decode`). The scheduler itself agreed: all 8 ranks logged identical
`gnt`, identical `will_run=True`, idle ranks correctly assigned `IDLE`. **So the
divergence is created inside the MTP worker, not by the scheduler.**

**Nothing has yet measured *why* the stages diverge.** Three fixes in a row addressed
*how to resynchronize after* divergence; none addressed *why it occurs*.
