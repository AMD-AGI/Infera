# GLM-5.2 DPA + MTP + PD on gfx950 — results as of 2026-07-29

**Status: the decode-leg deadlock and the two crashes are fixed and stable.
One correctness issue remains open.**

Everything below was measured on the live cluster. Where a claim is unverified
it says so explicitly.

## 2. What was actually wrong

Four distinct defects, found in this order. Three of the four are the same
family: **a DP-padded row count meeting an unpadded one.**

### Bug 1 — `dsa_indexer.py::_get_topk_paged` (fixed earlier, shipped)

The aiter/HIP MQA-logits path sized `logits` from the DP-padded row count while
`lengths` was always the real count → `fast_topk_v2` assert. The CUDA path
already sliced to the real count. Fix: slice on HIP too, restore padding after.

### Bug 2 — `dsa_backend.py` rank-divergent D2H syncs (fixed)

`max_seqlen_k = int(forward_batch.seq_lens.max().item())` is a host sync on a
branch only *some* DP ranks take. Replaced with the sync-free
`self.req_to_token.shape[1]`, the idiom already used at `_graph_page_table_width`.
Two further unconditional `.cpu()` syncs removed.

**Measured effective**: after this fix no rank ever appears in `dsa_backend`
again in a py-spy dump, and PD warmup passes on all 8 ranks.

### Bug 2b — the draft CUDA graph is rank-divergent (localized, not fixed)

`eagle_worker_v2.py:517`:

```python
if (can_cuda_graph
    and not forward_batch.forward_mode.is_idle()   # <-- differs per DP rank
    and self.seed_dsa_topk_from_draft_extend
    and draft_input.dsa_topk_indices is None):
    can_cuda_graph = False
```

Under DP-attention each rank is independently busy or idle, so this guard picks
the graph path on some ranks and the eager path on others *within one collective
step*. Measured: dp7 took 6 graph / 2 eager while every other rank took 8 / 1.

Only two graphs are captured on this HIP + tilelang config —
`Capture draft decode CUDA graph` ×1 and `Capture target verify CUDA graph` ×8.
The draft-extend graph is **never** captured here (its HIP gate needs an
`AiterMultiStepDraftBackend`; tilelang is not one).

Forcing `can_cuda_graph = False` unconditionally (Variant B) removes the hang
while leaving the target-verify graph enabled. See §4 for why this is not the
final fix.

### Bug 5 — `dsa_backend.py` decode: page_table rows vs topk rows (fixed)

```
deepseek_nextn.py:271 (the MTP draft model)
  -> dsa_backend.py:2154 forward_decode
  -> transform_index.py:138
     assert page_table.shape[0] == topk_indices.shape[0]   -> AssertionError, all 8 ranks
```

`metadata.page_table_1` is `req_to_token[req_pool_indices]`, one row per
**request**. `topk_indices` was just padded to `q.shape[0]`, one row per
**token**. Equal for plain decode; unequal under MTP. The prefill sibling solves
this with an explicit `output_num_tokens` argument; the decode entry point has
none.

Fix: a helper that expands page_table rows to match, via `repeat_interleave`.
Padded topk rows are all `-1` and are masked out by the triton kernel
(`valid_topk_mask = mask & (loaded_topk_indices >= 0)`), so only the row *count*
matters. Applied at **both** call sites (`:2154` and `:2724`) — the traceback
named only the first, but the second has the identical defect.

### Bug 6 — the Bug-1 slice skipped DP-idle ranks (fixed)

```
eager_runner.py:409 _execute_idle          <- an IDLE DP rank
  -> dsa_indexer.py:989 _get_topk_paged
RuntimeError: Expected lengths.size(0) == B to be true, but got false.
```

**This one was caused by my own Bug 1 fix.** It guarded the slice with
`if 0 < q_offset < q_fp8.shape[0]`. A DP-idle rank has no requests, so
`q_offset == 0` and the slice was skipped — leaving aiter to size `logits` from
the padded row count while `lengths` had 0 rows.

The `0 <` lower bound was defensive, meant to avoid an empty tensor. But
`q_fp8[:0]` is a legal empty slice and is exactly what an idle rank should pass;
the CUDA path slices unconditionally. Fix: drop the lower bound.

Only surfaced at 64-way concurrency, because it needs a rank to be idle while
others are busy.

## 4. Why Variant B is not the final fix

Variant B disables the draft CUDA graph on every rank. It removes the hang and
costs the draft graph's speedup (not measured). The real fix is to make the
graph/eager decision **uniform across the DP group** while still allowing the
graph when all ranks agree. Options:

1. all-reduce the boolean before acting on it — correct, costs one small
   collective per draft call;
2. derive the decision only from rank-invariant quantities;
3. make graph and eager issue identical collective sequences.

A narrower attempt (Bug 2b: delete just the `not is_idle()` term) was tried and
**failed** — the surviving terms (`can_cuda_graph` from `prepare_for_draft`, and
`dsa_topk_indices is None`) are themselves rank-divergent, measured as dp0 16/3
vs dp7 14/4 *with that fix applied*.

## 5. Open issue — ~2 % degenerate output under concurrency

Responses like `1.1.1.1.1...`, `3.3.3.3...`, `2.1.3.2.1.3...`. HTTP 200, correct
token count, wrong content — a silent error, which is worse than a crash.

What is established:

* **Rate is unstable across rounds**: 4 / 2 / 4 / 0 / 2 out of 128. Round 4 had
  zero with identical inputs.
* **The same prompt run solo is coherent.** `part 11` degenerated in a 128-way
  burst and produced normal text when sent alone. So it is concurrency-induced.
* **The system is non-deterministic even at `temperature=0`.** Same dp_rank,
  same prompt, greedy, 3 runs → 3 different outputs, diverging from the first
  token.
* **`temperature` does not reach the MTP verify path on HIP.**
  `eagle_utils.py:620`:
  ```python
  if sampling_info.is_all_greedy or _is_npu or _is_hip or _is_xpu:
      target_predict = torch.argmax(next_token_logits, dim=-1)
  ```
  The `or _is_hip` forces argmax regardless of sampling params. Confirmed
  empirically: `temperature=0.9` gave 7/128 degenerate vs 2–4/128 at
  `temperature=0` — no improvement, consistent with the flag being ignored.
  This is a separate defect in its own right: **user-supplied
  temperature/top_p are silently discarded during MTP verify on HIP.**

What is *not* established: whether the degeneration is (a) greedy decoding
falling into a repetition loop, which sampling would mask, or (b) genuine
content corruption from a concurrency/DP race. Some non-determinism is expected
from batch-dependent GEMM reduction order and DP all-gather; whether its
magnitude explains outputs that diverge from the very first token has not been
measured.

Next experiment to separate them: **MTP off, `temperature=0.9`, conc=128.**
- sampling works + degeneration gone → it is greedy looping; `_is_hip` is the
  only defect
- sampling works + degeneration remains → real corruption
- sampling still ignored → forced-greedy exists in more than one place

### Ruled out: AMD-AGI/Infera commit `854ebf70`

That commit ("fix long context correctness issue by add mooncake sync") fixes
chunked-prefill KV being transferred before the writing forward completes. The
symptom looks similar (retrieval degenerating into repeats), but it cannot apply
here:

| | that bug needs | our runs |
|---|---|---|
| prompt length | > one prefill chunk | ~10 tokens |
| `chunked-prefill-size` | small enough to split | **65536** (context 32768) |
| chunks per prefill | ≥ 2 | **1** |

Its own README states the final chunk is always correct because it goes through
the sampling path's real `copy_done.synchronize()` — and we only ever have that
one chunk.

**However**: our tree does *not* have that patch (`wait_event` count is 0 in
`mooncake/conn.py`, `mori/conn.py` and `common/utils.py`). Short-prompt testing
cannot hit it, but **any long-context run on this deployment would need it.**
Worth applying before any needle-in-a-haystack or >32 k input work.

## 6. Method notes

Two deployments were kept alive side by side, the eager pair as control
(`xcheck.sh`). Reproducing on both means it is not a graph problem; appearing
only on the graph side localizes it.

Three fixes were falsified before the cause was measured, all because they
addressed *how to resynchronize after divergence* rather than *why it occurs*:

* **hoist_sync** — moving the sync above the early returns; the guard itself was
  the divergence.
* **Bug 3 broadcast** (backport of PR #31683's eagle_utils hunk) — proven a
  **no-op**: `attn_tp_size = tp_size // attn_dp_size // attn_cp_size = 8//8//1 = 1`,
  so the `if tp_group.world_size > 1` guard is never true. This also dissolved
  the apparent contradiction around `--disable-custom-all-reduce`: PR #31071
  fixes divergence *within* an attention-TP group; ours is *across* DP ranks.
* **Bug 4 uniform event** — not merely ineffective but **actively harmful**:
  with it applied all 8 ranks deadlocked in `overlap_utils.py:292`, the wait that
  fix itself hoisted. Reverted via `git checkout`. Do not reapply.

The breakthrough was instrumenting the *count* of LM-head all-gathers per rank
(`probe_stage_count.py`) and the graph/eager decision (`probe_graph_path.py`),
rather than reading source.

**Probe blind spot, important**: a replayed CUDA graph executes no Python, so
Python-level hooks see nothing inside it. "0 collectives on the graph path" is a
measurement artifact, not a fact. An earlier version of this document drew a
conclusion from that and was wrong; see the CORRECTION block in
`ROOTCAUSE_bug2b_graph_eager_divergence.md`.

See `PITFALLS_20260729.md` for the operational traps (stale `.pyc`, binary logs,
decorator-adjacent code insertion, etc.).
