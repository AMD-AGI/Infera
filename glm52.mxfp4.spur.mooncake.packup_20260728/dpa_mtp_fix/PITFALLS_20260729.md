Written so the next person does not spend the same hours. Each entry says what
happened, why it happened, and what to do instead.

## A. Traps that silently invalidate a measurement

### A1. Stale `.pyc` runs your *unpatched* code

**What.** A full experiment was run, analysed, and written up before it emerged
that the fix had never executed. The source file showed the patch; the runtime
behaviour did not.

**Why.** The patch script restored a backup with `shutil.copy2`, which
**preserves the original mtime**. The rewritten `.py` therefore had a timestamp
matching the cached `__pycache__` entry, so CPython considered the bytecode
valid and ran the *old* code.

**How to avoid.** Every patch script must, after writing:

```python
os.utime(path, None)                       # bump mtime
# and delete the module's cached bytecode
for fn in os.listdir(pycache):
    if fn.startswith(basename + "."):
        os.remove(os.path.join(pycache, fn))
```

**How to verify** — check the bytecode, not the source:

```bash
strings <module>.cpython-310.pyc | grep -c YOUR_MARKER    # must be >= 1
```

Or nuke everything before a critical run:
`find /sgl-workspace/sglang/python/sglang -name __pycache__ -type d -exec rm -rf {} +`

### A2. Inserting code next to a decorator

**What.** A helper function was inserted using `src.index("\nclass ")` as the
anchor. It landed **between `@dataclass(frozen=True)` and the class it
decorates**, so the decorator was applied to the helper. Every scheduler died at
import with `AttributeError: 'function' object has no attribute '__mro__'` —
discovered only after a 10-minute boot.

**Why.** `py_compile` proves a file *parses*; it says nothing about whether the
insert is semantically in the right place.

**How to avoid.** Walk back over contiguous `@`-prefixed lines before inserting,
**and** actually import the module in a subprocess as part of the patch script:

```python
subprocess.run([sys.executable, "-c",
    "import sys; sys.path.insert(0,'/sgl-workspace/sglang/python');"
    "from ...module import my_helper as f; assert f(...); print('IMPORT OK')"])
```

A boot cycle is far too expensive a way to discover a bad insert.

### A3. Server logs contain binary bytes

`grep` reports `binary file matches` and `grep -c` returns **0** — a silent lie
that reads as "no occurrences". Always `strings <log> | grep ...` or `grep -a`.

### A4. `grep -c` on a missing file prints `0` *and* exits non-zero

`grep -c pat missing.log || echo 0` emits **two** lines and breaks any
single-line parse. Pipe through `| head -1`.

## B. Operational traps

### B1. `pkill -f <pattern>` can kill your own shell

`pkill -f "watch.sh 9006"` matched the parent shell and killed the session. Same
class as the already-documented ban on `pkill -f launch_server`. **Kill by
explicit PID.**

### B2. A container recreate silently drops in-container patches

A `3072 vs 6144` weight-load crash was reproduced **twice** before the cause was
found: recreating the container dropped a fourth, undocumented patch
(`deepseek_nextn.py` MTP bf16). Found by diffing `git status` against the other,
untouched container.

**A recreate is never necessary.** Killing the launcher plus the 8 scheduler
PIDs releases all VRAM (86 % → 0 % on every GPU).

If you must recreate, diff the container's **source files** first, not just
mounts/env/devices.

### B3. `spur exec` quoting

`spur exec <job> "<cmd>"` fails with `No such file or directory`. Use
`spur exec <job> bash -c "<cmd>"`.

Backslash line-continuations do **not** survive the spur → docker → bash
nesting; they truncate the command silently (a `curl` lost its URL this way).
Keep each remote command on one line, or put it in a script file on the shared
mount.

### B4. Never background a long docker client inside `spur exec`

The exec namespace teardown kills it. Use `docker exec -d`.

### B5. Router circuit breaker

After the decode leg dies, the router returns
`503 No available decode workers (all circuits open or unhealthy)` even once
decode is healthy again. Kill it by PID and relaunch on **fresh**
`--port` / `--prometheus-port`.

## C. Wrong turns in the analysis

Three fixes were falsified before the cause was measured. The common thread:
**all three addressed how to resynchronize after divergence, not why divergence
occurs.**

### C1. `hoist_sync` — falsified

Moved the D2H sync above the early returns so every rank would reach it. The
hang simply moved to the next line. The *guard* was the divergence, not the sync.

### C2. Bug 3 broadcast backport — proven a no-op

Backported PR #31683's `eagle_utils` hunk. Its guard is
`if tp_group.world_size > 1`, and here
`attn_tp_size = tp_size // attn_dp_size // attn_cp_size = 8//8//1 = **1**` — so
the branch is never taken.

Checking that arithmetic first would have cost a minute instead of a boot.

It also dissolved an apparent contradiction: PR #31071 fixes divergence *within*
an attention-TP group; ours is *across* DP ranks. That lead never matched our
topology.

### C3. Bug 4 "uniform event" — not merely useless, **harmful**

Made the publish event unconditional and hoisted the wait. With it applied, all
8 ranks deadlocked in `overlap_utils.py:292` — **the wait that fix itself
hoisted**. It converted a benign state into a hard hang and contaminated every
measurement taken while it was live.

Reverted with `git checkout`. **Do not reapply.**

Sub-trap: the first revert attempt deleted *upstream's own* HIP wait block along
with the addition. Caught because `git diff` showed `-7` lines where it should
have shown zero. **`git checkout <file>` beats hand-reverting.**

### C4. "The graph path issues 0 all-gathers" — a probe blind spot

A per-rank counter hooked into `LogitsProcessor._get_logits` showed the eager
draft path issuing 2 all-gathers and the graph path issuing 0, and the
conclusion drawn was "the collective *counts* diverge".

**Wrong.** A replayed CUDA graph still performs the collectives captured into
it; it just executes no Python, so the hook never fires. Zero was an artifact.

**Rule: Python-level probes are blind inside a replayed CUDA graph.** Prefer
instrumentation over source-reading, but know where the instrument cannot see.

### C5. A defective variant definition, then a fabricated reason to drop it

Variant C was specified to the user as "disable only the draft-extend graph" but
was actually dispatched as `--cuda-graph-max-bs 0`. It was then cancelled on the
stated grounds that "max-bs 0 equals disabling graphs" — an assertion that was
never checked and is probably false (`--cuda-graph-max-bs` bounds the captured
batch-size buckets).

Net effect: a variant that tested neither the advertised thing nor a useful
thing, discarded for a made-up reason.

As it happens, the intended variant C was moot anyway — the log shows the
draft-extend graph is **never captured** on this HIP + tilelang config (its gate
requires an `AiterMultiStepDraftBackend`). Only two graphs exist here:
`Capture draft decode CUDA graph` ×1 and `Capture target verify CUDA graph` ×8.
That should have been checked in the log before designing three variants around
three graphs.

### C6. Variant A never took effect and was reported as if it had run

`--speculative-attention-mode decode` was launched, but the log showed
`speculative_attention_mode='prefill'` and the process was `Killed` before
becoming ready. **Always grep the resulting `server_args` line to confirm a flag
actually took effect** before interpreting anything downstream.

### C7. One fix created the next bug

The Bug 1 fix guarded its slice with `if 0 < q_offset < q_fp8.shape[0]`. The
`0 <` lower bound was defensive — and it made the slice a no-op on exactly the
DP-**idle** ranks, where `q_offset == 0`. That became Bug 6, surfacing only at
64-way concurrency.

**Lesson: a defensive lower bound on a padding-related quantity deserves the
question "what does the degenerate case actually mean here?"** `q_fp8[:0]` is a
legal empty slice and was the correct behaviour all along; the CUDA path had no
such bound.

## D. Things that cost time but were correct to do

* **Keeping an eager control pair alive** (`--disable-cuda-graph`) as a
  differential baseline. It is what established that CUDA graphs are implicated,
  and it repeatedly prevented mis-attribution.
* **Verifying `temperature` actually reached the model** before drawing
  conclusions from a temperature sweep. It did not —
  `eagle_utils.py:620`'s `or _is_hip` forces `argmax` regardless. Same dp_rank +
  same prompt + greedy gave 3 different outputs across 3 runs, which is what
  proved it.
* **Checking a proposed root cause against the actual config before testing it.**
  AMD-AGI/Infera commit `854ebf70` (mooncake chunked-prefill KV race) has a very
  similar symptom, but our prompts are ~10 tokens against a
  `chunked-prefill-size` of 65536 — never more than one chunk, and the final
  chunk is always correct by that commit's own account. Ruled out on paper in
  minutes instead of a boot.
  **But note**: our tree does not have that patch, and any long-context work on
  this deployment will need it.
