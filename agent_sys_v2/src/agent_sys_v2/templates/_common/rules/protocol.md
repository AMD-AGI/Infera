# 任务约定

我用 agent_sys 管理这个项目的任务：每个任务有一个 prompt 文件 `tasks/<类型>/<任务名>.md` 和一个工作区 `workspaces/<类型>/<任务名>/`，当前目录是项目根目录。下面是我希望你在每个任务里都照着做的事。

## 工作区里的文件

- `progress.md`：当前进展，我和下游任务靠它知道做到哪了。格式固定：开头两行，空一行，之后只用无序列表，一条一行，只写结论：
  ```
  状态: 进行中
  下一步: <一句话>

  - 关键事实或决定（分支、确认过的原因、已按默认做的选择）
  - [x] 做完的步骤
  - [ ] 计划要做的步骤
  ```
  状态只用"进行中""阻塞""已完成"三种写法。全部做完时把状态改成"已完成"，并加第三行 `完成时间: YYYY-MM-DD HH:MM`；时间用 `date '+%F %H:%M'` 取，不要自己写。之后系统运行本任务的验收检查（首条消息里会列出；没通过会把输出发给你），需要审核的任务再等我审核；都通过了任务才算完成，下游任务接着开始。
  开始时就把计划的步骤列成 `- [ ]`，做完一项勾一项，计划变了就改列表；任务完成时不留未勾选的项（不做了的，写明原因后删掉）。过程和细节放 `log/` 或 report.md，不写进 progress.md。
- `report.md`：给我和下游任务看的报告，以"## 结论"开头。结论之后写"## 交接清单"，一行一条 `` `路径` — 一句话说明 ``：下游要用的产物（数据、脚本、截图目录等，路径相对工作区）和工作区里主要目录的用途；分支、commit、PR 也写在这里，但不以反引号开头（例如"分支 `dev/x`，PR #5"），以免被当成路径。下游先看这份清单，不用翻整个工作区。
- `issue.md`：遇到的问题和修复方案，一个问题一个 `##` 小节。
- `log/`：长命令的输出用 `tee` 写到这里；详细的实验记录也放这里，不要堆在 progress.md 里。

## 语言和任务引用

- 工作语言跟我写的任务 prompt 一致：prompt 用英文写，progress.md、report.md 等文件和回复就用英文；用中文写就用中文。本约定的语言不决定工作语言。progress.md 开头的字段既可以写"状态/下一步/完成时间"和"进行中/阻塞/已完成"，也可以写 `Status`/`Next`/`Finished` 和 `In progress`/`Blocked`/`Done`。
- prompt 里的 `@<类型>/<任务名>` 指本项目的另一个任务：它的 prompt 是 `tasks/<类型>/<任务名>.md`，工作区是 `workspaces/<类型>/<任务名>/`。需要时读它的 report.md 和 progress.md。
- 运行环境里有这些变量，验收检查也在同样的环境里运行：`$AGENT_SYS_PROJECT`（项目目录）、`$AGENT_SYS_TASK`（本任务，`<类型>/<任务名>`）、`$AGENT_SYS_WORKSPACE`（本任务工作区的绝对路径）、`$AGENT_SYS_MACHINES`（本任务可以使用的机器，逗号分隔）、`$AGENT_SYS_SKILLS`（agent_sys 自带的 skills 目录）、`$AGENT_SYS_PYTHON`（运行 agent_sys 自带工具的 Python）。

## 需要我决定的时候

- 把问题写进 progress.md（状态写"阻塞"，下一步写清楚要我做什么），然后结束这一轮，等我回复后接着做。
- 问题超过 2 个时，写一个 `questions.md` 表格，列为 `# | 问题 | 建议 | 你的意见`，最后一栏留空给我填（单元格里的 `|` 写成 `\|`）；我没填的行，按你的建议处理。再次提问时写新的 questions.md，旧的改名保存（例如 `questions_1022.md`）。
- 不重要的选择不用停下来问：选保守的默认值继续，在 progress.md 写"已按默认：……"，并在 report.md 里列出"替你做的决定"，我事后确认。

## 等作业、文件或远程状态

- 用后台命令（`run_in_background`）跑一个条件满足才退出的检查脚本，`timeout` 设够；在 progress.md 写明在等什么，然后结束这一轮。命令结束时会自动开始新的一轮，等待期间不需要你做任何事。不要在前台用 sleep 循环等。
- 收到 "reached its background time limit" 时，按提示用更长的 timeout 重新启动检查。

## 边界

- 只写本任务的工作区（以及任务要求修改的代码仓库），不要写别的任务的工作区。临时文件也放在本任务的工作区里，不要放到 `/tmp` 等其他地方。
- 需要拆子任务时，在 `tasks/<类型>/` 下写一个草稿 prompt（frontmatter 写 `parent` 和 `summary`），不要自己开始执行，我确认后会把它加进来。
- push、提交集群作业、删除数据等不可逆的操作，先在 progress.md 写明要做什么。

## 经验

- 值得留给以后任务的经验，写到工作区的 `lessons/<名字>.md`，我审过后会收进经验库。只写不能从代码或文档直接看出来、换一个任务也用得上、已经验证过的内容；按机制写，不按机器写。
- 我在对话里给出的长期规则（"以后都……"），当场照做，同时写一条 `type: rule` 的 lessons。这个环境没有开 memory，这是记下它的唯一办法。
- 格式：
  ```markdown
  ---
  name: <英文短名，用短横线连接>
  description: <一行说明，会出现在经验索引里>
  type: pitfall   # pitfall | env-fact | method | negative-result | rule
  source: <类型>/<任务名>
  ---
  **做法**：…  **原因**：…  **适用范围**：…
  ```
