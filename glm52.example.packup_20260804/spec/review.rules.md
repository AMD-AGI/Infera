本文档是**规则驱动的代码修复协议**：不是给代码打分的 review，而是拿规则库逐条对着代码/补丁执行，并**产生真实的修改**。上半部分（一、二）规定 Claude Code 必须如何逐条执行并落地修复；末尾《规则库》是被执行的规则本体。每条规则都要落到真实改动，或有据的「无需改动」结论——不得略读，不得甩手打分。

<aside>
🚫

**反打分铁律**：规则库每一条都要在《执行台账》里有独立一行，并落到**真实动作**——要么给出实际改动（diff / 文件:行号），要么给出「无需改动」的机械证据（命令输出 / AST 比对）。只写 pass/fail 评分、既无改动也无证据，一律视为**未执行**，不得收工。

</aside>

## 一、执行协议

**顺序不可跳。每步都有硬性产出，缺产出即该步未完成。**

### 0 准备

- 通读末尾《规则库》全部条目。
- 把每条规则展开成《执行台账》一行（模板见二）。少一行 = 漏审。
- 定范围：默认 `git diff origin/main HEAD`；信息清理只审新增（见 R5）。

### 1 逐条执行（检查 → 修复，不是打分）

- 对台账每行**实际执行**检查动作，禁止凭阅读下结论。
- 命中问题的默认动作是**当场修复**并记录实际改动（diff / 文件:行号）；只有「修」「不修」都站得住的决策级分歧，才按 2、3 先汇总交决策。
- 每行必填「检查方式」+「证据」。证据 = 可复现命令及其真实输出 / diff / 文件:行号 / AST 比对。
- 未命中的，必须给出机械证据证明确实无需改动（扫描类先自证有效，R4.5），不能只写「pass」。
- 当场无法定性的：填「挂起」，写明已排除的候选，不要猜（R7.3）。

### 2 汇总（仅决策级分歧）

- 只有决策级分歧才先汇总后改（R7.1）；不要拿它当拖延修复的借口，其余问题在步骤 1 就地修掉。
- 每个待决策项标注：严重度 / 本次新引入 or 既有惯例 / 有无仓库先例（R7.2）。

### 3 汇报与决策

- 「修」「不修」都站得住的分歧：给建议、交决策，不擅自改。
- 产出《发现汇报》（模板见二）。

### 4 修复

- 只改已确认项，每处改动回指台账行号。
- 注释改动守 R2；上游归属守 R3；信息清理守 R5；commit 守 R6。

### 5 验证（证明，不是自述）

- 每条「我只改了 X」断言必须机械证明（AST dump 逐文件比对，R4.1）。
- 真验证 = 干净 pinned 源码树实际 apply + 字节编译 + 端到端跑真实脚本；`--dry-run` / `git apply --check` 不算（R4.3 / R4.4）。
- 改动产物与「最后一次真实验证过的产物」对拍（R4.2）。
- 推送前跑 DCO 自查（R6.1）。

### 完成闸门（全满足才算 done）

- [ ]  台账每行都落到真实改动或有据的「无需改动」，无空行、无「未执行」、无纯打分。
- [ ]  每个命中项已修复并验证，或已挂起并说明。
- [ ]  中途自己的错误结论已更正并说明影响面（R7.4）。

### 发现汇报

每个 finding 一条：

- **编号 / 位置**：文件:行号
- **严重度**：阻断 / 重要 / 次要

- **问题**：一句话
- **证据**：命令输出或 diff
- **建议**：修 / 不修 + 理由
- **状态**：待决策 / 已修 / 挂起

## 规则库

一套从实战 review 中沉淀的硬性规则。每条都是「踩过的坑 → 可机械执行、可验证的要求」。**每一条都必须被检查、执行，并落到真实的代码/补丁改动（或有据的「无需改动」），不是拿来打分的清单。**人和 agent 都应能逐条照做。上方协议以 R 编号引用这些规则。

<aside>
⚙️

约定：**规则** = 必须做的动作；**为什么** = 一句话理由；命令块中的 `OWNER/REPO`、`<sha>`、`Name <email>` 等为占位符，按实际替换。

</aside>

### R2 注释与文档

#### R2.1 行间注释 ≤ 3 行

- **规则**：除文件级注释外，行间注释不超过 3 行，按 what / why / how / before / after / context 组织。写不下的移到 patch 头部或设计文档。

#### R2.2 详情移走，不是删掉

- **规则**：压缩注释时，被移出的论证必须落到明确去处（patch 头部 / README / 状态表），并在原地留一句指路。
- **为什么**：否则下一个人会把已排除的方案重试一遍。

#### R2.3 记录已被证伪的路径

- **规则**：「不要这样写」与「要这样写」同等重要，尤其当错误写法能通过全部功能测试时，必须写进注释。
- **为什么**：能过测试的错误写法会把修复悄悄降级成「关掉特性」的 workaround 而不被发现。

### R3 Patch 上游归属

#### R3.1 每个 patch 标注四项

1. upstream **issue**
2. upstream **他人 PR**
3. upstream **本人 PR**
4. 本 patch 与本人 PR 的差异：base、实现形式、本地化/去本地化内容、取舍（各自更强在哪）、各自验证依据

#### R3.2 「没有上游」要写清怎么查的

- **规则**：写明检索方式与局限。「未找到」≠「不存在」。
- **为什么**：`gh search` 匹配标题/正文，不匹配 diff 内容，上游可能改了同一处却没提到它。

#### R3.3 上游状态现查，不凭记忆

- **规则**：用 `gh` 现查，写明查询日期，并注明状态会漂移。

#### R3.4 已合并 ≠ 可删本地 patch

- **规则**：删除判据是「已合并**且**已进入 pinned base」。已合并但 base 未跟进的，保留本地 patch。状态表须区分这两种。

#### R3.5 建立全仓库上游索引表

- **规则**：一张表覆盖所有 patch，列：路径 / 一句话问题 / upstream issue / upstream PR / 该 PR 是否本仓库作者发起 / PR 状态。
- 表是索引，不是记录；完整论证放各 patch 头部。

### R4 验证

#### R4.1 证明，而不是自述

- **规则**：「我只改了注释」这类断言必须机械证明。示例做法：改前/改后 patch 分别应用到 pinned base，比对 AST dump（AST 天然忽略注释，docstring 文本单独归一化），要求逐文件完全相同。

#### R4.2 对拍已验证产物

- **规则**：改动后的产物必须与「最后一次真实验证过的产物」做等价比对，而不是只跟自己上一版比。

#### R4.3 `--dry-run` 不算验证

- **规则**：真正验证 = 拉一份 pinned commit 的干净源码树，实际应用，再字节编译。
- **为什么**：`patch --dry-run`、`git apply --check` 默认允许 fuzz，可能在「检查通过」下静默丢 hunk。

#### R4.4 端到端跑真实脚本

- **规则**：改了任何被构建脚本消费的东西（包括被脚本 grep 的注释文本），必须完整跑一遍该脚本，而不是只跑片段。
- **为什么**：改了注释原文但没同步脚本的 grep 串，会在别人机器上才炸。

#### R4.5 扫描先自证有效

- **规则**：用数组 `"${F[@]}"` 而非裸变量；先用一个**已知必然命中**的模式验证扫描本身有效，再相信它的「零命中」。
- **为什么**：「零命中」可能是真干净，也可能是命令根本没生效（如 shell 未做词分割，grep 没收到文件列表）。

### R5 进入公开仓库前的信息清理

范围：只审查本次 PR 的新增内容（`git diff origin/main HEAD`），不追究历史遗留。

#### R5.1 必查清单

| 类别 | 示例 |
| --- | --- |
| IP / 主机名 | 集群节点名、`*.compute.internal` |
| 本地绝对路径 | `/home/<user>/...`、共享存储挂载点 |
| 调度器 / 集群标识 | 调度器命令、分区名、预约名、集群代号 |
| 个人分支 / 实验目录名 | 对外部读者是死链，且常含集群代号 |
| 他人姓名 / 账号 | 尤其挂在未经我方验证的数据上 |
| 私有仓库链接 | 暴露其存在与 issue 编号 |
| 凭据 | token、密钥、密码 |

#### R5.2 以仓库既有惯例为准

- **规则**：不要自作主张地「更精确」。更精确未必更合适。
- **为什么**：把内部引用「订正」成带链接的私有仓库编号，会连带暴露私有仓库的存在与编号。

#### R5.3 删可追溯性时留替代路径

- **规则**：不要直接删证据指针。改成「内部复现套件，含 X/Y/Z 各一份，向作者索取」——读者仍知证据存在及覆盖面，只是拿不到路径。

#### R5.4 保留证据强度标注

- **规则**：去掉人名，但保留 second-hand / 未实测 / 单次观察 等限定语——那是判断该条论断可信度的依据。

#### R5.5 公开产品名不清理

- **规则**：公开产品名（公开芯片/架构代号等）已广泛使用，不清理。清理要有边界，否则文档被削得没信息量。

### R6 DCO / Commit 卫生

#### R6.1 校验的是 author email，不是「有没有 trailer」

- **规则**：author 邮箱不对时，补 sign-off 也修不好，必须改写 authorship。
- **为什么**：`git rebase --signoff` 只按本地 config 追加 trailer，从不改写 authorship。
- **推送前自查**：

```bash
git log --format='%h A=%ae SOB=%(trailers:key=Signed-off-by,valueonly)' origin/main..HEAD
```

- **改写 author 并接上后续 commit，确认只改了 authorship**：

```bash
git checkout <bad-sha>
git commit --amend --no-edit --author="Name <you@example.com>"
git rebase --onto <new-sha> <bad-sha> <branch>
git diff <old-branch> <new-branch>   # 必须为空
```

- **预防**：每个新容器 / checkout 里先设 `git config user.email`。

### R7 Review 的沟通方式

#### R7.1 有决策价值的分歧，先汇总再执行

- **规则**：不要边发现边改。把发现分档（严重度 / 是否本次新引入 / 是否有仓库先例），给建议，交由决策——尤其当「修」和「不修」都站得住时。

#### R7.2 区分「本次新引入」与「早已存在」

- **规则**：给结论必须带这个区分（某模式在 main 上已有 N 处 = 既有惯例；本次 0→X 新增 = 新引入）。两者处置门槛不同。

#### R7.3 证据不足就挂起，不要给判断

- **规则**：无法立即定性的问题，如实写「已排除 N 个候选，根因未定」，不要为收尾给猜测。

#### R7.4 自己的错误要更正，并说清影响面

- **规则**：即使「结果恰好一样」，无效的中间结论也要主动讲明，包括它当时漏报了什么。
