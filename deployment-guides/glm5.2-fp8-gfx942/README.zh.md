# GLM-5.2-FP8 gfx942 部署文档

在 gfx942（MI300X / MI325X）上部署 GLM-5.2-FP8 的两种方式，以及用来衡量两者的多轮
agentic 基准。选一种读就行，两份文档各自独立完整。

| 文档 | 什么时候用 | English |
|---|---|---|
| [`docker.zh.md`](docker.zh.md) | 你已经有两台节点，想用最短路径拿到一个能跑、能调的部署。每节点一个长期容器 + shell 脚本。 | [`docker.md`](docker.md) |
| [`kubernetes.zh.md`](kubernetes.zh.md) | 你要通过 Infera operator 部署。四种拓扑，各自只需 1–4 处 `sed` 替换。 | [`kubernetes.md`](kubernetes.md) |

**两者跑出来的是同一个引擎。** 对两边真正产生的 argv 做逐 flag 比对，prefill、decode、
router 三个组件零处实质差异；同一负载下 decode 侧延迟相差在 1.2% 以内。在任一边调出来
的结论可以直接沿用到另一边。

## 最该先看的一条结论

在 2× MI325X 上、prefill/decode 分离、多轮 agentic 负载（60 个会话、448 个请求、输入
中位 68k token）实测：

| | 批量 / 高并发 | 交互 / 低并发 |
|---|---|---|
| 配置 | 默认（DP-attention 开，chunk 8192） | DP-attention **关**，chunk 2048 |
| 并发 16 聚合吞吐 | **182.7 tok/s** | 139.4 tok/s |
| 并发 1 单用户速度（中位） | 62.5 tok/s/user | **133 – 159 tok/s/user** |
| 并发 16 平均 TTFT | 12.4 s | 22.2 s |
| 缓存效率 | 100.00% | 100.00% |

同一份权重、同一个镜像，只差一个开关。**DP-attention 是一个并发档位的取舍，不是"开着
总是更好"的优化。** 在动其他任何参数之前，先确定你要服务的是哪一列——本次实测中没有
其他参数的影响接近这个量级，而另外三条看起来有希望的方向都已试过并证伪。

## 已验证的范围

- **2× MI325X 上的 prefill/decode 分离**，两种部署方式都做了：448/448 请求成功，缓存
  效率 100.00%，零驱逐。
- **Kubernetes 的四种拓扑**（aggregated 与 disaggregated，各含开/不开 KV 卸载）在
  2× MI300X 上：并发 1/8/16/32 全程零失败、零 GPU 故障、零 Pod 重启。
- **两种部署方式之间的对照**，静态（逐 flag）和动态（同一负载）都做了。

## 开始之前

这个栈上有三件事**是静默失败的**——返回 HTTP 200，日志里什么都没有。两份文档里都会讲
到，但值得先知道：

1. **RoCE GID index。** 选错是慢 4–110 倍，不是坏掉。而且这个值不能跨集群抄。
2. **base 镜像与主机驱动的搭配。** 不匹配时会正常加载权重、捕获 graph，然后在负载下的
   某处报错，而报错位置看起来像引擎 bug。
3. **KV 交接损坏。** decode leg 读到损坏的前缀，返回一段通顺但与提问无关的文本。只有
   核对已知答案才抓得到。
